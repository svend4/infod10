# Работа с репозиторием

- Retry source study расширяет предметный материал существующими source-adapter/source-promise-coverage без изменения их грамматики и полномочий. Новый корпус копирует закреплённые исходник и MIT license, явно отделяет четыре выбранных объявления от четырёх вручную записанных excluded_before_analysis кандидатов. Исключения не являются полученными analyzer unresolved и не задают полный знаменатель документации. Сохраняйте raw header names до lowercase преобразования и integer AST0 при float annotation; не вычисляйте Name/default0.0 ради match. Намеренно ошибочная единица total в авторском документе может дать 4/4 coverage/current_for_human_review: это иллюстрация непроверенной семантики. Независимой человеческой разметки, semantic benchmark, runtime execution, Store writes и измеренной ёмкости агентов нет. Все старые Python кроме init/main integration неизменны, в том числе 58 закреплённых recovery/source модулей.

- Source promise coverage связывает новую явно составленную опись с точными ID/digest полного source-adapter-1 отчёта. Не подменяйте прежний coverage-1 искусственным review-set. Покрытие требует уникальной цитаты captured document вне fenced blocks, разрешимого поля и точного совпадения scope/type/всех селекторов со всеми ссылками; одного ID или значения недостаточно. Сохраняйте partial quote evidence при пересечении fence, все Comparison4 и все upstream blockers, включая неиспользованные mappings. Coverage и satisfaction различаются; пустая опись блокируется с null fraction, дубликаты требований/shared mappings видимы и не означают независимости. HTML/inline/indented code и смысл прозы не распознаются; outside_fenced_blocks не равно prose verification. Новые отчёты совещательные, auto_accept/live_state/runtime_binding/prose_semantics/atomic_capture=false; нет Store writes. Все прежние Python, кроме __init__/__main__ integration, corpus/examples/старые части сессии неизменны; 55 прежних recovery/source-adapter модулей byte-for-byte.

- Source adapter сравнивает только явно выбранные AST-объявления исходника, строгие литералы авторского адаптера и поля одного JSON fence документа. Полные captured inputs и profile закреплены digest; load/show пересчитывают observation без живых файлов. Новая грамматика отделена от прежнего obligations extractor. Frozenset call — синтаксическая форма, отсутствие обнаруженного shadowing не доказывает runtime name binding; параметры, единицы, область прозы и полнота выбора остаются авторскими метаданными. Сохраняйте pair mismatch даже при unresolved другого endpoint, bool не равен integer. Не исполняйте upstream/proposed code, не импортируйте его и не используйте отчёт как допуск Store.accept. Corpus/examples/старые session parts и 52 прежних recovery модуля byte-for-byte. Новые сравнения совещательные: human review обязателен, auto_accept/live_state/runtime_binding=false.

- Sealed job сохраняет полный логический Guard11 и issuance evidence в одной immutable Seal14 с общим digest. Новые intent/lock имена обязательны: прежние legacy и guarded control files никогда не создаются; отдельной issuance directory нет. Новый step требует FULL Seal14, holder credential и отсутствие отзыва до result bodies/live review; результаты и revoke связаны с seal_digest. Receipt и exact issue replay читают только seal/closed names, поздние result/revoke bodies не разбирают. Show/status/revoke проверяют marker и все present results; cached step после auth повторяет исторический ответ без live sources. Issue использует прежний S39 issuer/admin/policy, общий60s и locks issuer→newjob→review (+короткий plan capture); запись Seal14 завершается и проверяется под этими locks. Старый native guard не публикуется отдельно. Partial/absent seal и bootstrap закрыты для продолжения, усыновление/ремонт не реализованы. Ошибка после полного commit может оставить действующий seal с issuance evidence; откат и все power-loss сценарии не доказаны. Гарантия относится к новому sealed пути: parent policy не запрещает старую выдачу другого fresh native job, старые форматы не обновлены. Предыдущие49 модулей byte-for-byte; private Seal14/fullGuard11/request7/anchor4/pins/digests/key hashes не публикуются. Новый own job нужен для receipt, referenced issuer/plan/review могут отсутствовать. Изоляция FS owner, внешняя identity/fencing и смысловое одобрение не добавлены.

- Guarded issuer закрепляет immutable policy из 1..16 exact rule5: principal, actor, verdict и plan_id плюс rule_id. Admin credential отличается от holder key. Новая управляемая выдача создаёт только свежий native Guard11; держите issuer→issuance→job→review locks с общим60s, при capture кратко добавляется plan lock. Native guard сохраняется до Issuance16: ошибка выдачи может оставить действующий guard и fsynced holder key, поэтому общего all-or-nothing результата нет. Существующие jobs, review и partial issuance не усыновляются и не ремонтируются. Exact issue replay после admin-auth сверяет собственную квитанцию и полную issuer binding, работает после issuer revoke без live plan/job/review; own receipt lookup не требует issuer. Отзыв issuer блокирует будущую выдачу, прежний guard отзывается отдельно ключом holder. Policy_authorized описывает историческую выдачу; native issuer_policy_enforced=false сохраняется, отдельный guarded prepare остаётся поддержанным owner API. Нет внешней identity, OS isolation, глобального registry или смыслового принятия. Issuer12/revoke7/issuance16/request7/anchors и digests/key hashes частные. Прежние46 модулей сохраняются byte-for-byte.

- Guarded write job — отдельное семейство: прежние intent/lock никогда не создаются и не усыновляются. Обязательный credential и отсутствие отзыва проверяются в новом step до result-slot и live review/stage; собственная job lock держится до fsync результата и валидации ответа, live locks job→review. Три immutable result6 закрепляют operation ID каждой фазы; точный saved replay исторический и не читает текущие plan/review. Новый шаг в точном POST сохраняет только expected_phase_observed; более поздняя фаза блокирует новую квитанцию. Отзыв сериализуется той же lock, не отменяет допущенный эффект и блокирует выдачу cached step; show/exact prepare/revoke имеют отдельные own-only правила. Guard11 с nested oldintent13, result6/revoke7, pins/digests/hash/credential частные. Legacy APIs отвергают новый формат, но owner FS, произвольный Python и private helpers не изолированы; прежние lease/issuer policy на новое семейство не переносятся. Нет TTL, ремонта bootstrap/partial controls, восстановления старых заданий либо OS fencing. Прежние43 модуля остаются неизменными.

- Write issuer вводит отдельную immutable policy1..16 rule7 и admin credential. Новая выдача проверяет admin/отзыв/точный scope, держит issuer→issuance→permit→action locks с единым60s; holder secret отличается от admin. Native grant13 сохраняется перед отдельным issuance15, lock nativepermit удерживается до receipt fsync. Окно между ними не атомарно: существующий nativepermit не усыновляется, lock-only/partial issuance не ремонтируется. Полный exact issue replay после admin-auth и проверки request/issuer binding возвращает исторический receipt даже после issuer revoke, без native/action live reads. Own receipt lookup читает только issuance controls. Отзыв issuer останавливает новую выдачу, не отзывает прежние nativepermits и не создаёт общего registry/fencing. Правила не ограничивают поколение lease; childpermit по-прежнему закрепляет исходный точный claim/action. Administrator/principal/worker самозаявленные, ownerFS и прежние APIs вне guard. Private issuer12/revoke7/issuance15/request4/anchors/digests/secret hashes не публикуются. Прежние40 модулей не изменяются.

- Write permit связывает один локальный bearer credential с точным action22 и его immutable pins. Issue/replay читает собственные grant13/revocation7, show20 описывает active/revoked permit, не текущую lease либо pending работу. Новый protected execute22 всегда проверяет credential и отсутствие отзыва ДО доступа к action/result, включая saved replay; затем держит permit→action→ledger→job→review locks с единым deadline. Отзыв тем же holder сериализован permit lock, не отменяет уже допущенный эффект/возвращённые bytes, marker не перезаписывается. Stable response не содержит нового clock/authlog: credential_verified относится к текущему вызову, historical_effect_authenticated=false сохраняет историческую границу. Выдача доверяет private FS owner; principal/worker не удостоверяют человека. Нет TTL, общей registry/уникальности credential, unrevocation либо запрета старых action APIs/direct step/других permits/копий. Credentials только в private sibling .credential0600/uid/nlink1; token/hash и grant/marker/pins/digests не публикуются. Частичный grant/marker и bootstrap не ремонтируются; owner tampering не является поддержанным API.

- Write action закрепляет одну исходную/целевую фазу по выбранному member каталога. Новый execute либо новая POST observation требуют последнюю действующую captured lease; держите action→ledger→job→review locks до fsync результата, закрывайте read-only SQL до файлового эффекта. Проверяйте полные captured pins до разбора live ledger/catalog/job. Точный saved-result replay читает собственные controls до live/time checks. При точном POST записывается expected_phase_observed с effect_performed=false; более поздняя фаза блокирует повтор. Не выдавайте такое наблюдение за доказательство причины либо fsync чужого шага. Поддержанный PRE может выполнить ровно один прежний примитив, с source-supported prepared→staging prefix continuation. Lease действительна в момент допуска; expiry во время операции не отменяет начатый эффект. Intent15/result6, anchors и digests частные; компактные action22/wrapper18/observation7 не реконструируют отсутствующее полное тело catalog/job. Частичный intent/result и bootstrap не ремонтируются. Прежний прямой step и другие ledgers остаются вне проверки; общей SQL/FS транзакции, аутентификации worker, внешнего fencing и смыслового разрешения нет.

- Локальные write leases координируют только явно выбранный индекс одного отдельного ledger. Не переносите их исключительность на другой ledger, копию DB либо прежний прямой write step. Immutable manifest11 хранит source7 с catalog16 и descriptor7; append-only SQLite history до 1024 успешных операций выводит головы без отдельной таблицы heads. Claim/release и operation-ID replay согласуются в одной транзакции; точный replay возвращает историческую квитанцию без продления, до проверки текущей головы/clock/лимита новых записей. Новое назначение увеличивает поколение, stale release с новым ID отказывает; последний совпадающий lease можно освободить даже после истечения. Worker самозаявленный, внешнего fencing и проверки step нет. Новые мутации блокируются при clock раньше последнего decided_at; страницы вычисляют срок по локальному checked_at. Bootstrap и остаточный journal не ремонтируются. Частные manifest, DB, pins и digests не публикуются; completed job тоже может получить назначение, pending work этим не доказана.

- Каталог write jobs закрепляет только явно выбранный порядок до 256 участников и компактные исторические descriptor7 с полными частными pins intent/lock. Show и точный replay читают собственные controls. Страница до 16 позиций освобождает catalog lock до текущих job/review-наблюдений и передаёт один общий deadline. Изменённая привязка проверяется до разбора intent; недоступная текущая цель сохраняется отдельной строкой, не удаляет участника и не меняет membership. Available не означает completed либо разрешение действий. Каталог не выполняет step, не обнаруживает задания автоматически, не выдаёт leases и не удостоверяет actor; checked_at обозначает последовательный проход, не общую транзакцию.

- Поэтапная запись review использует отдельный private write job и неизменяемый intent, закрепляющий точную будущую review14, lock назначения и inode собственного staging. Prepare/status/step не предоставляют доменных полномочий. Один step заполняет и fsync stage, следующий устанавливает exclusive hardlink, третий удаляет только доказанный собственный alias после подтверждения сохранности назначения. Состояние linked с двумя ссылками остаётся незавершённым; прежний review reader должен отказывать до completed. Status только наблюдает, завершённый step возвращает прежний результат. Частичный intent, изменённый inode и окна до durable intent не ремонтируются; source-supported prefix continuation не выдавайте за выполненную демонстрацию прерывания или гарантию при потере питания.

- Рассмотрение retention plan сохраняйте отдельной неизменяемой advisory-записью с самозаявленным actor и полным историческим планом. Show/replay проверяют собственные controls и точную offline-реконструкцию известного plan14, без чтения живых источников. Revalidate отдельно наблюдает plan/catalog bindings и captured cases на одном новом checked_at с прежней policy; равенство недоступных наблюдений не подтверждает unchanged basis. Сохраняйте исходные причины, отсутствие аутентификации actor и запрет архивирования/удаления; revalidation не является разрешением действия или новым сохранённым планом.

Это репозиторий архива, исследовательской документации и локального прототипа agentwiki. Текущий runtime использует SQLite и управляемые Python workers; внешние LLM и промышленная многоагентная вики не реализованы. Рабочие границы описаны в docs/development/README.md.

## Сохранность переписки

- Канонический текст сессии находится в docs/sessions/<session>/transcript.jsonl.
- transcript.md и manifest.json создаются scripts/build_session_archive.py.
- Сохраняйте содержание сообщений без сокращения и исправления задним числом. Исправления фактов оформляйте отдельно в тематических документах со ссылкой на исходное сообщение.
- Не включайте скрытые системные и служебные инструкции, внутренние рассуждения, секреты или необработанные журналы инструментов в пользовательский архив.
- Не выдавайте ручной перенос доступного контекста за полный экспорт платформы. Указывайте границу снимка и известные пробелы.
- Не выдумывайте даты и время сообщений. Новые части истории добавляйте с явной фиксацией покрытия либо оформляйте следующей сессией.
- При изменении исходного архива обновляйте метаданные покрытия и производные файлы.

## Технические материалы

- Различайте результаты выполненных проверок, заявления внешних источников, наши проектные предложения и открытые вопросы.
- Каждое существенное внешнее утверждение сопровождайте источником. Историческое прочтение страницы не означает свежую проверку её содержания.
- Возможности Git, очереди заданий, поиска, графа знаний и редакционного согласования описывайте отдельно.
- Не представляйте проверку ссылки как доказательство истинности текста, а согласие нескольких моделей — как независимое подтверждение.
- Не описывайте предложенную архитектуру как готовое или развёрнутое приложение.
- Различайте исторический архитектурный проект и реализованный прототип. В текущем runtime каноничен SQLite; экспорт в Git не является общей транзакцией с БД.
- Предложенный агентами код является данными; не добавляйте его автоматическое исполнение в доверенный процесс.
- Существующий результат examples/multi-agent/results относится к конкретному запуску. Новые запуски сохраняйте отдельно; не выдавайте размер пула за измеренную ёмкость или число LLM.
- Граф влияния содержит только объявленные зависимости. Списки render_files и review_files могут пересекаться; их объединение не является измеренным ускорением.
- Выпуски schema 2 содержат зависимости с базой после принятия. Не удаляйте проверку stale accepted query/read при экспорте; старые schema 1 не дают полного покрытия provenance.
- Корпус semantic-v1 содержит проектные примеры и аннотации ИИ-агентов без экспертной проверки человеком. Не выдавайте их за независимый эталон; annotation не должна поступать в compare_statements.
- Семантическое сравнение описывает явно заданные поля, не устанавливает истинность текста и не выполняет Store.accept. Сохраняйте requires_human_review=true и auto_accept=false в текущем ограниченном инструменте.
- Редакторский журнал отделён от runtime Store. Решения привязаны к точному пакету; stale решения не переносятся на новый вход. Обновление решения должно сохранять историю и проверять supersedes вместе с packet digest в одной транзакции.
- actor_kind в журнале самозаявленный, не аутентификация. agent_agreement не означает независимой экспертизы или разрешения публикации. Хеш-цепочка без внешнего заверения не доказывает авторство или полноту истории.
- Досье связывает предложение с редакторским пакетом совещательно. Снимки runtime и журнала последовательны, общей транзакции нет; не переносите результат досье в разрешение Store.accept.
- Точное совпадение before.text/after.text с шаблонами не доказывает соответствие структурированных полей смыслу текста. Показывайте непокрытые writes, изменения read/query оснований и последних решений; нерелевантная revision сама по себе не означает устаревание.
- Составное предложение создаётся через Store.compose по аренде integrator. Проверки компонентов, сохранение lineage и завершение задания должны оставаться в одной транзакции. Одобрения исходных предложений не переносятся на составное.
- Комплект рассмотрения всех writes использует один захваченный runtime-контекст и один снимок журнала. Не собирайте его из наблюдений разных моментов; повтор пакета не является независимой проверкой. Сохраните загрузку прежнего context schema 1 и примеров прошлых этапов.
- Межфайловые обязательства сравнивают явно заданные поля захваченных кандидатов. Не выдавайте match за подтверждение поведения программы, смысла всей прозы или актуальности живой базы. Сохраняйте исходные блокеры комплекта и live_state_checked=false.
- Экстрактор конфигурации использует ограниченную грамматику AST без исполнения. Вызовы, мутации, импорты и вычисляемые выражения должны оставаться unresolved. Направление code_subset_of_document означает код ⊆ документ; true не равно 1.
- Покрытие обещаний относится только к явно заявленной описи. Пустой перечень не означает 100%; повторяющиеся требования и общие проверки показывайте отдельно от независимых оснований.
- Привязка обещания требует точной уникальной цитаты, разрешимого поля и совпадения обоих селекторов, типа, области и отношения с обязательством. Сохраняйте различие покрытия, match/mismatch и исходных блокеров; полное покрытие не предоставляет права принятия.
- План переноса сохраняет все прежние ID обещаний, порядок и число записей. Не удаляйте проблемные записи ради улучшения доли; очищайте неподтверждённые ссылки в черновике и показывайте причины остановки. Переносятся описания, не решения участников.
- Реальные источники и написанная авторами адаптация — разные основания. Для urllib3 total имеет единицу retries; default allowed_methods не является универсальным запретом POST во всех ветках ошибок. Не выдавайте литеральный адаптер за анализ поведения исходной библиотеки.
- Пересмотр описи — предложение автора. Сохраняйте исходные ID, порядок и число записей, но не объявляйте равенство смысловых знаменателей после revise. Неудачный reaffirm и незавершённые записи остаются блокирующими; целевые upstream blockers сохраняются независимо от обоснования автора.
- Разбор изменений требования сравнивает дескрипторы после явной карты ID. Вывод equals → code_subset_of_document относится к схеме предиката над множествами; изменение числа или меток scope не задаёт направления гарантии. Внимание редактора отделено от действующих upstream blockers и не является новой политикой принятия.
- В явно включённом governance-режиме проверяйте полномочия, текущее поколение политики, последние решения по каждой записи и существующие проверки runtime в одной транзакции принятия. Допуски привязаны к конкретному grant; отзыв и повторная выдача не восстанавливают старые голоса. Проверка bearer credential подтверждает владение локальным допуском, а не личность человека, авторство proposal или независимость экспертов.
- Секреты governance сохраняйте только в частных файлах .credential с правами 0600 вне публикации. Не включайте токены, их хеши, credential-файлы и SQLite-базы в отчёты или Git. Историческое принятие после включения политики не получает разрешение задним числом; replay требует действующего допуска и возвращает прежний факт.
- В отдельно включённом authorship-режиме связывайте worker с principal, ролью, областью записи и исходным grant конкретной аренды. Новый допуск того же principal не продолжает старую попытку. Повтор submit/compose требует текущего действующего исходного допуска, но не переоценивает уже завершённую аренду или компоненты.
- Проверяйте происхождение по реальному графу компонентов, включая промежуточных integrator. Все участники составного предложения исключаются из его review, редакторских решений и нового координирования. Сохраняйте исторические доказательства после отзыва авторского допуска; включение режима не создаёт доказательства задним числом. Локальное авторство не устанавливает личность человека, независимость моделей или истинность текста.
- В отдельно включённом content-режиме политику комплекта, обязательств и обещаний задаёт администратор. Не переносите в принятие внешний совещательный отчёт или искусственно одобренный review-set. Вычисляйте пакет из текущего состояния той же SQL-транзакции; решение закрепляйте точным packet digest, а финальный пересчёт выполняйте до свежей проверки сроков полномочий. Исторический replay не создаёт нового действующего голоса.
- Политика content schema 1 охватывает фиксированный комплект целиком. В schema 2 выбирайте все разделы, затронутые реальными writes, и вычисляйте транзитивное замыкание пересечений комплектов. Требуйте полный замкнутый набор записей; непокрытая запись блокирует принятие. Не добавляйте выбор первого правила, приоритетов или раздела, выбранного автором.
- Пустая опись, пропущенная запись, mismatch, unresolved и устаревшее основание блокируют новое принятие. Точная цитата и совпадение полей не устанавливают истинность прозы, поведение программы, полноту выбранной описи или факт внимательного рассмотрения участником. Локальные ID правил разных разделов не объединяются в одно доказательство. Без отдельно включённого continuity смена каталога инвалидирует все голоса через общие поколения политик.
- В continuity-режиме сохраняйте голос только при совпадении полного локального основания и доказанной цепочке каждого промежуточного изменения каталога. Проверяйте контекст выбранных разделов на обоих концах каждого перехода; изменение с возвратом не восстанавливает прежний голос. Прямой сброс governance, отзыв grant и повторная выдача не оживляют старое мнение. Не переписывайте исходные решения и их полные packet pins.
- Одинаковые правила continuity применяются ко всем verdicts. Непроверяемая из-за предела истории действующая голова решения должна блокировать принятие до явного свежего решения или отзыва допуска; не удаляйте возможное возражение ради кворума. Все сравнения истории выполняются до финальной свежей проверки сроков полномочий. Хеш цепочки не является внешней подписью или удостоверением человека.

- Пошаговый history-audit закрепляет точное исходное решение и фиксированный целевой пакет; каждый шаг проверяет не более 64 переходов. Сохраняйте неизменяемые checkpoints, CAS головы и исторический replay. Его заключения совещательные: не используйте audit rows как разрешение Store.accept и не снимайте ими непроверяемые возражения. Повреждённая история отличается от установленного прямого сброса политики.

- Восстановление history-audit по operation ID сверяет точные неизменяемые параметры, исходный admin grant и сохранённый request digest; оно возвращает исторический checkpoint без записи нового события или операции. Каталог использует индекс start-событий и cursor из after_seq/snapshot_max_seq: фиксируется состав, головы наблюдаются на каждой странице. Ошибки отдельных записей сохраняйте явно; не выдавайте восстановление ответа за ремонт или резервное восстановление базы.

- SQLite backup, intent, manifest и их контрольные суммы сохраняйте только в частных каталогах вне публикации. Копии сразу содержат persistent quarantine table; её присутствие, включая повреждённую запись, никогда не разрешает новые изменения. Store должен распознать копию до WAL/schema initialization, открывать её mode=ro/query_only и блокировать write=True и publish. Не добавляйте API активации старых grants/leases; чтение квитанций и audit recovery отражает историческую авторизацию. Незавершённый intent не должен приводить к созданию новой активной базы.

## Рабочий процесс

- Retention plan сохраняет совещательную оценку непустого диапазона до 16 участников явного каталога. Используйте один сохранённый момент и срок от case.created_at, сохраняйте все причины held в фиксированном порядке. Неизвестная identity, изменённые/недоступные свидетельства и незавершённая попытка остаются блокерами. Review_candidate не разрешает архивирование или удаление. Replay/show читают прежний снимок без live catalog/case/job; отдельные планы не создают общей транзакции либо исключительной аренды обработчика. Подробные наблюдения выполняются после освобождения catalog lock, с единым пределом времени и не более одной case/job-блокировки. Частные plan/source anchors и digests не публикуются.

- Каталог случаев закрепляет явно переданный упорядоченный состав в отдельной частной записи. Не добавляйте автоматическое обнаружение каталогов или вывод неизвестных путей. Публичный cursor привязан к catalog ID и позиции; он не является допуском или общей транзакцией. Страница наблюдает только управляющие записи case/link, без old evidence, job status или DB. Ошибка одного участника сохраняется отдельной строкой вместе с исторической квитанцией. Текущий available не устанавливает здоровье восстановления. Case/link/restore протоколы сохраняются; приватный каталог, pins и digests не публикуются.

- Case record сохраняет историческое наблюдение одного из ограниченных ранних отказов отдельно от job и bundle. При недействительном plan исходная identity остаётся null; не выводите пути и параметры из его префикса. Link-attempt фиксирует явную операторскую ассоциацию с уже созданным проверяемым job, без заявления, что caseAPI создал эту попытку либо доказал совпадение запросов. Исторические квитанции и текущие наблюдения разделяются; изменение либо исчезновение файлов не переписывает причину отказа. Original jobs не ремонтируются и не удаляются. Частные fingerprints, case/link records и их контрольные суммы исключаются из публикации.

- Resume-preparation завершает только метаданные индексов 0–2 и их собственный staging по сохранённому действительному плану, без доступа к исходному backup. Не затрагивайте staging данных или финальный workspace manifest. Upfront status сохраняет обычные проверки; при уже установленных данных команда только возвращает прежний status. Частичный plan/owner и target без доказанного владельца не ремонтируются. Окно mkdir → первый intent остаётся неподдерживаемым: не открывайте там Store и не утверждайте, что snapshot guard уже существует.

- Демонстрация прерываний восстановления использует только фиксированные внутренние checkpoint names и отдельный доверенный worker. Обычные API/CLI не должны принимать fault callbacks, произвольный код или включающие прерывания переменные среды. Реальный SIGKILL локального процесса не доказывает сохранность при потере питания, сбое ядра или хранилища. Различайте наблюдение status и исправление доказанной собственной staging-пары через step.

- Поэтапное восстановление использует отдельный private job directory и неизменяемый план, привязанный к точному источнику и назначению. Завершённый комплект сохраняет прежние шесть записей формата workspace backup. Не перезаписывайте несовпадающие готовые файлы; очищать допускается только доказанный собственный staging. Блокировка job охватывает изменения, а status остаётся чтением. Повтор завершения возвращает факт из фиксированного плана и проверенного назначения без нового времени или активации полномочий. Не выдавайте поддерживаемые контрольные точки за восстановление после всех возможных сбоев.

- Полный workspace backup сохраняет текущую карантинную DB и все архивы предков в одном частном комплекте. Стандартный snapshot intent записывается первым, общий workspace manifest — последним. Восстановление сохраняет карантин и прежний origin; оно не активирует старые grants/leases. Полный inspect сверяет все файлы, цепочку и импортные anchors без обращения к прежним путям. Обычное чтение уже завершённой внутренней DB остаётся историческим даже при незавершённом внешнем комплекте; полноту истории устанавливает отдельный workspace inspect. Прежний DB-only формат не расширяйте неявно.

- Повторный source transfer сохраняет все архивы предков в новом частном каталоге. Проверяйте их полные контрольные суммы, квитанции, fence и непрерывную цепочку до необратимого закрепления назначения. Старшие standalone SQLite-файлы копируются точно, текущий источник — через native backup. Сохраняйте совместимость частного schema 1 и публичных квитанций; schema 2 связывает полный перечень архивов и совокупный запрет credentials всех поколений. Отдельный lineage status публикует только безопасные квитанции и счётчики.

- Source transfer создаёт новую базу с новыми полномочиями; прежняя source fence не снимается. Единственное назначение закрепляется отдельной control-plane reservation, которая не разрешает обычные Store writes. Сохраняйте исходные зависимости принятого содержания в привязанном к digest baseline и всю историю в fenced archive. Частные denylist, origin, manifest и request digest не публикуйте. Незавершённое назначение и обычная копия active DB по другому пути должны блокироваться; текущий checksum изменяемой рабочей базы не сравнивается с первоначальным manifest.

- Постоянная source fence хранится в зарезервированном ключе meta; частный request digest не публикуется. Проверяйте её под writer reservation до тела write=True, включая replay, и до всех файловых эффектов publish. Конструктор не должен обходить её через WAL или executescript с неявным COMMIT. Метка необратима через API; source_epoch обозначает локальный факт, не глобальный запрет для старых бинарных версий, прямого SQL или иных копий.

- Сверка восстановления является read-only наблюдением живого источника, а частный план не является разрешением переключения. Сохраняйте карантин копий, текущую авторизацию и полный частный отпечаток SQL, включая изменения heartbeat без событий и sqlite_sequence. Не публикуйте планы, отпечатки строк или request_digest. Неизменность данных по SQL отделяйте от истечения сроков по часам и будущих изменений источника.

- Используйте существующий checkout. Задача уже выполняется в изолированной среде; не создавайте Git worktree без явного запроса пользователя.
- Сначала проверяйте состояние Git и локальные инструкции. Сохраняйте существующие изменения пользователя.
- После изменения архива выполняйте python3 scripts/build_session_archive.py --all --check и git diff --check.
- Проверьте относительные ссылки в добавленных документах.
- Фиксация локальных файлов, создание коммита и публикация на удалённом сервере — разные действия; сообщайте о фактически выполненном.
