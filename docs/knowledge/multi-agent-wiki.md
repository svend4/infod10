# Проект многоагентной вики и портала документации

Это систематизированное архитектурное предложение из сессии. Оно не является описанием уже реализованной платформы. В репозитории сохранена документация; приложение, база, очередь и интеграции агентов этим документом не создаются.

**Последующее развитие:** после нового поручения пользователя создан [локальный прототип](../development/README.md). Он реализует часть механизмов этого проекта; SQLite является каноническим runtime-хранилищем, Python workers не вызывают LLM. Нижеследующий текст сохраняет более широкое историческое предложение; его будущие возможности не следует приписывать прототипу.

Полный ход обсуждения — в [транскрипте](../sessions/session-001/transcript.md), статус решений — в [реестре решений](decisions.md), ссылки на внешние проекты — в [реестре источников](sources.md).

Основные сообщения: [обзор проектов — m0024](../sessions/session-001/transcript.md#m0024), [предлагаемая архитектура — m0027](../sessions/session-001/transcript.md#m0027), [смысловое слияние — m0030](../sessions/session-001/transcript.md#m0030), [надёжное исполнение — m0033](../sessions/session-001/transcript.md#m0033).

## Задача

Несколько агентов параллельно собирают источники, извлекают сведения, пишут статьи и проверяют правки. Портал должен сохранять происхождение информации, историю решений и согласованность связанных страниц. Текстовое слияние файлов решает только часть задачи: разные файлы могут содержать несовместимые рекомендации.

Смысловое согласование требуется уже при повторном обновлении связанных страниц одним агентом. Параллельная работа увеличивает количество пересечений. Необходимость отдельного масштабируемого хранилища уровня Scion определяется фактической нагрузкой, а не одним лишь числом агентов.

## Три состояния знания

| Слой | Содержимое | Назначение |
|---|---|---|
| Источники | Снимки документов, спецификаций, страниц и метаданные версий | Возможность проверить основание и восстановить контекст |
| Предложения | Извлечённые утверждения, черновики, исправления, результаты проверок | Рабочая область, где сведения ещё не приняты |
| Принятое содержание | Версионированные утверждения и тексты, прошедшие установленный процесс | Основа публикации, таблиц и пользовательских ответов |

Поиск для обычного пользовательского ответа должен по умолчанию использовать принятую опубликованную версию. Проверяющим агентам нужен доступ к предложениям и конкурирующим версиям, причём статус каждого фрагмента сохраняется.

Если неподтверждённый черновик становится «источником» для следующих агентов, одна ошибка может многократно повториться. Взаимные ссылки производных страниц не дают независимого подтверждения.

## Роли и права

| Роль | Результат | Разрешённая область записи |
|---|---|---|
| Сборщик | Снимки и метаданные источников | Хранилище источников |
| Аналитик | Предложения утверждений, сущностей и условий | Рабочие предложения |
| Автор | Черновики статей и связанных материалов | Черновики |
| Проверяющий | Замечания, результаты сопоставления, заключение | Отчёты проверок |
| Координатор принятия | Согласованный принятый пакет | Каноническая версия |
| Публикатор | Проверенный выпуск сайта и индекса | Артефакты выпусков и активный выпуск |

Роль не требует отдельной модели и не означает постоянно работающий процесс. Одно приложение может исполнять несколько ролей, сохраняя границы полномочий.

Ограничения записи должны обеспечиваться API и правами инструментов. Инструкция в запросе к модели сама по себе не заменяет проверку полномочий сервером. В начальном варианте только один координатор имеет право передвигать каноническую ветку.

## Представление утверждения

Структурировать прежде всего полезно версии, даты, числовые показатели, единицы, параметры, ограничения, поддерживаемые возможности, сущности и связи. Каждое формальное утверждение должно сохранять исходный текст и основание.

Условная запись:

```yaml
id: api-v2.default_timeout
revision: 8
subject: Example API
scope:
  product_version: "2"
property: default_timeout
value: 60
unit: second
kind: specification
source_snapshot: S-381
supporting_fragment: "..."
status: accepted
used_by:
  - reference/timeouts
  - guide/setup
  - guide/troubleshooting
```

Это иллюстрация схемы, а не действующий формат репозитория.

Область применимости включает продукт, версию, конфигурацию, период и условия. Тип высказывания отличает спецификацию от измерения, рекомендации, мнения и цитаты. Числовое значение без этих условий часто недостаточно для сравнения.

Не каждый абзац стоит превращать в формальную запись. Сложный вывод о влиянии реформы или исторического события требует аргументации, атрибуции, методики и альтернативных объяснений. Поле `улучшила: да` утратит значительную часть содержания.

### Два времени

Полезно различать:

- время применимости сведений к предметному миру;
- время, когда система получила и приняла эти сведения.

Если настройка изменилась 1 июля, а портал узнал об этом 20 июля, возможны два разных запроса: «что действовало 10 июля?» и «что портал сообщал 10 июля?». Их ответы могут отличаться. Исправления не должны бесследно переписывать историю принятия.

## Источники и основания

Для существенного утверждения нужны конкретная сохранённая версия источника, подтверждающий фрагмент, время получения и описание происхождения.

Проверка различает как минимум:

1. Ссылка существует и открывается.
2. Конкретный фрагмент действительно поддерживает формулировку.
3. Источник достаточен для принятия по правилам проекта.

Пересказ может превратить внутреннее испытание в общую гарантию, а рекомендацию — в обязательное требование. Рабочая ссылка этого не обнаруживает. Ссылки нескольких сайтов на одно исходное сообщение не дают нескольких независимых подтверждений.

LLM помогает искать противоречия и основания. RAG выбирает доступный контекст. Граф знаний фиксирует связи. Редакционная политика определяет достаточность подтверждения и правила представления разногласий. Голосование одинаково настроенных моделей не создаёт независимое свидетельство.

## Три состояния для смыслового слияния

Предложение сравнивается с:

- **базовым состоянием**, которое прочитал агент;
- **текущим состоянием**, куда уже попали другие изменения;
- **предложенным результатом**.

Так восстанавливается намерение: дополнение, исправление, уточнение области действия, отзыв либо переформулировка. Исчезновение абзаца само по себе не объясняет причину удаления.

| Формулировки | Возможная трактовка |
|---|---|
| 30 секунд и 30 000 миллисекунд | Эквивалентность после проверяемого преобразования |
| Значение по умолчанию 30 секунд и максимум 30 секунд | Разные свойства |
| Версия 1: 30 секунд; версия 2: 60 секунд | Совместимые сведения разных версий |
| Поддерживается Linux; поддерживаются Linux и Windows | Возможно, дополнение |
| Поддерживается только Linux; поддерживается Windows | Противоречие при совпадении условий |
| Рекомендуется проверять подпись; необходимо проверять подпись | Изменение обязательности |
| В испытании получено 10 мс; задержка никогда не превышает 10 мс | Необоснованное усиление измерения до гарантии |

Автоматическое принятие подходит для узких проверяемых случаев: одинаковой нормализации, независимых дополнений, добавления действительного основания к неизменному утверждению. Неоднозначная сущность, потеря основания и изменение обязательности требуют разбора.

Следует различать равенство, доказанное правилом; соответствие спецификации; предположение модели о похожести; редакционное решение. Эти основания имеют разную воспроизводимость.

## Зависимости: прочитанные записи и результаты запросов

Проверять только ревизию редактируемой страницы недостаточно. Агент мог использовать параметр с другой страницы, а тот уже изменился.

Предложение сохраняет значимые прочитанные зависимости — read set: идентификаторы утверждений и их ревизии, версии источников, исходную страницу, а также результаты запросов, определившие вывод.

```yaml
proposal: P-104
target:
  page: guide/retries
  base_revision: 17
read_claims:
  - id: api-v2.default_timeout
    revision: 8
source_snapshots:
  - S-381
status: awaiting_review
```

Если существенная зависимость уже имеет новую ревизию, предложение проверяется заново в затронутой части.

### Отсутствующая запись тоже может быть зависимостью

Запрос вернул платформы A и B; автор написал «поддерживаются только A и B». Пока он работал, другой агент добавил платформу C. Ревизии A и B не изменились, но результат исходной выборки изменился. Это пример конфликта из-за новой записи в области запроса — query phantom.

Нужно сохранять смысл значимых выборок, например «полный перечень платформ продукта X версии Y», и проверять их актуальность. Кроме того, отсутствие записи в вики не доказывает отрицательное утверждение о мире. Для слова «только» требуется источник, задающий исчерпывающий перечень.

## Совместные ограничения

Две независимо правильные правки могут нарушать общее ограничение. Условный пример предполагает последовательные вызовы без дополнительных задержек:

| Состояние | Тайм-аут | Максимум вызовов | Максимальное ожидание |
|---|---:|---:|---:|
| База | 30 с | 3 | 90 с |
| Только агент A | 40 с | 3 | 120 с |
| Только агент B | 30 с | 4 | 120 с |
| Объединение | 40 с | 4 | 160 с |

При общем пределе 120 секунд объединение не проходит проверку, хотя каждый вариант отдельно проходит. Правило расчёта и предел должны иметь владельца и источник. Неверно заданное правило само способно блокировать корректную работу.

В технической документации также полезны проверки по API-схемам, наличию команд и исполнимости примеров. Для энциклопедических выводов предметных формальных правил меньше, а значение источников и редакционного разбора выше.

## Процесс проверки и принятия

1. Восстановить намерение относительно базовой версии.
2. Сопоставить сущности, свойства и условия; неоднозначности вернуть на уточнение.
3. Проверить подтверждающие фрагменты и применимость источников.
4. Временно объединить предложение с текущими принятыми сведениями.
5. Проверить ограничения, определения, зависимые тексты, таблицы и примеры.
6. Выбрать исход: принять, исправить, разделить по условиям, сохранить разногласие либо отклонить с основанием.
7. Непосредственно перед записью повторно проверить актуальность зависимостей.

Длительные поиск, генерация и проверка проходят без удержания общей блокировки. Операция согласованного принятия остаётся короткой.

Проверяющему полезен содержательный отчёт: что предложено; какие исходные условия использованы; что изменилось с начала работы; какое ограничение нарушено; какие материалы затронуты. Отчёт объясняет причину, не выбирая произвольно между увеличением предела и уменьшением числа попыток.

### Разногласие как допустимый результат

Для энциклопедии разные даты, методики, оценки и позиции могут оставаться в принятом содержании с атрибуцией. Система не обязана сводить спорные источники к единственному числу. Основания редакционного решения и отклонения сохраняются, иначе новые агенты будут заново предлагать уже разобранную правку.

## Хранение первого рабочего варианта

| Компонент | Предлагаемая ответственность |
|---|---|
| Git | Принятые Markdown-страницы, компактные структурированные утверждения, манифесты источников |
| Устойчивое хранилище файлов | Снимки документов и крупные вложения |
| SQLite или PostgreSQL | Задания, попытки, предложения, проверки, намерения принятия, индексы зависимостей |
| Генератор портала | Сборка определённой версии содержимого |
| Поисковый индекс | Производное представление с идентификатором исходного выпуска |

При таком выборе коммит Git обозначает каноническую принятую версию. База управляет процессом; производные индексы восстанавливаются. В дальнейшем версионируемые структурированные данные могут стать центральным объектом и потребовать другой модели. В обсуждении названы TerminusDB, Dolt и собственная модель в SQL, но выбор не сделан.

Права и существование объектов по хешам рассматриваются отдельно: знание адреса содержимого не должно само по себе предоставлять право его чтения.

## Три жизненных цикла

| Объект | Примеры состояний |
|---|---|
| Задание | Получено, выполняется, завершено, требует повтора, остановлено |
| Предложение | Черновик, проверяется, требует исправления, одобрено, принято |
| Выпуск | Собирается, проверен, опубликован, заменён |

Завершённое задание может дать непригодный текст. Одобрение ещё не означает принятие. Принятие в каноническую историю ещё не означает публикацию сайта.

## Повторяемые задания, аренды и запоздавшие результаты

Очередь следует проектировать с возможностью повторного выполнения. Если агент сохранил результат, но погиб до подтверждения очереди, задание будет получено снова.

Нужны постоянный идентификатор задания, номер попытки, аренда с ограниченным сроком, подтверждения продолжения работы и сохранённые результаты завершённых этапов. Операции принятия должны безопасно переносить повторные вызовы.

Истечение аренды не останавливает старого исполнителя физически. Когда он вернётся позже нового, сервер должен проверить актуальность номера попытки или эквивалентный токен полномочий. Запоздавший результат не получает права переписать принятый результат актуальной попытки.

Вызов LLM может повториться и стоить денег ещё раз. Если ответ сохранён, его переиспользуют. Если провайдер выполнил запрос, но ответ потерян до сохранения, устранение повторного вычисления зависит от поддержки ключа операции провайдером. Реалистичная цель системы — одно принятое изменение при возможных повторных вычислениях.

### Одобрение относится к точному содержимому

Проверка фиксирует:

- ревизию и digest предложения;
- версии источников;
- значимые прочитанные записи и выборки;
- версию правил;
- результат и объяснение.

После изменения проверенного текста старое одобрение автоматически не распространяется на новый вариант. При изменении зависимости повторяют относящиеся к ней проверки. Постороннее изменение другой темы обычно не требует нового полного исследования.

## Восстанавливаемое принятие между Git и БД

Обновление Git и запись статуса в PostgreSQL не образуют одну общую транзакцию. Например, Git обновился, процесс погиб, а БД всё ещё показывает незавершённое предложение. Без протокола восстановления повтор способен применить правку ещё раз.

Предложенный в сессии протокол:

1. Проверить одобренную ревизию и зависимости относительно коммита `H`.
2. Подготовить полный новый коммит `C`; использованные снимки источников должны быть устойчиво сохранены.
3. Устойчиво записать намерение принятия: идентификатор операции, предложение, ожидаемый `H`, подготовленный `C`, идентификатор проверки.
4. Условно передвинуть каноническую ветку с `H` на `C`, только если прежнее значение всё ещё `H`.
5. Подтвердить принятие в БД и запустить обработку события сборки.

После сбоя координатор сначала разбирает незавершённые намерения. Если `C` уже включён в каноническую историю, он восстанавливает статус, не применяя правку повторно. Если обновления не было, продолжает по правилам протокола. Если история изменилась иначе, повторно проверяет основания.

Подготовленный коммит должен находиться в устойчивом Git-хранилище. Временная папка исчезнувшего агента недостаточна. Условное обновление есть у `git update-ref`; для удалённого сервиса нужна операция с проверенными эквивалентными гарантиями.

Доставка события сборки тоже требует устойчивого учёта: транзакционной записи события вместе со статусом в БД либо восстанавливаемого сканирования принятых коммитов. Повторное событие не должно повторно публиковать один и тот же выпуск. Конкретный механизм в сессии не выбран.

## Согласованные выпуски портала

Выпуск связывает коммит знаний, страницы, таблицы и поисковый индекс. Пока готовится `R43`, читатели продолжают получать согласованный `R42`. После необходимых проверок переключается активный выпуск. Неизменившиеся артефакты можно переиспользовать.

Поиск и ответы агента должны знать выпуск, по которому они работают. Идентификатор передаётся между компонентами в рамках запроса, чтобы страница и ответ не использовали разные поколения данных.

Откат опубликованного выпуска и исправление принятой истории — разные действия. Быстрое возвращение прежнего выпуска восстанавливает интерфейс, но ошибку в каноническом содержимом нужно исправить или отменить отдельным прослеживаемым изменением.

| Сбой | Требуемое поведение |
|---|---|
| Агент погиб при исследовании | Повтор с последнего сохранённого этапа |
| Старый исполнитель вернулся после передачи задания | Запоздавшая попытка не перезаписывает актуальную |
| Git обновился, подтверждение БД потеряно | Восстановление по намерению и истории |
| Сборка сайта завершилась ошибкой | Сохраняется предыдущий опубликованный выпуск |
| Индекс не готов | Новый выпуск ожидает готовности либо действует явно выбранная политика |
| Предложение изменилось после проверки | Перепроверка нового содержания |

Grokipedia рассматривалась как пример ИИ-энциклопедии с публичными предложениями правок и журналом. Её внутреннюю организацию агентов и механизм согласованности по публичным страницам в сессии установить не удалось. Оснований считать её открытым движком для самостоятельного размещения не приведено.

Для обмена структурированными основаниями обсуждались W3C PROV-O, SHACL и Web Annotation. Они помогают описывать происхождение, формальные ограничения и привязку к фрагменту, но не определяют истинность произвольного текста. Простой прототип может хранить эквивалентные записи в JSON.

## Первый эксперимент и критерии оценки

Предлагаемый объём: один сервис, его справочник параметров, настройка и диагностика; несколько параллельных исполнителей; устойчивые предложения; один координатор. Это ещё не принятое задание на реализацию.

Набор содержательных сценариев:

- одинаковое значение в разных единицах;
- разные версии продукта;
- изменение обязательности требования;
- действительно противоречащие источники;
- изменение прочитанного утверждения;
- новая запись в существенной выборке;
- совместное нарушение ограничения;
- сохранение обоснованного разногласия.

Набор сценариев восстановления: остановка после ответа модели, после обновления Git, до подтверждения БД и перед переключением выпуска. Каждый должен иметь путь восстановления без повторного применения принятой правки.

Оценивать следует пропущенные противоречия, необоснованно задержанные корректные правки, труд редактора, время принятия, стоимость одного проверенного опубликованного изменения, а также воспроизводимость оснований. Никакие испытания этого прототипа при архивировании сессии не выполняются.
