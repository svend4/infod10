## 1. Что реализовано

Прототип работает на Python и SQLite, использует стандартную библиотеку и запускается без установки зависимостей.

| Механизм | Что он делает |
|---|---|
| Параллельные исполнители | Несколько workers одновременно готовят документы, код и предложения утверждений |
| Очередь заданий | Сохраняет задания, зависимости и результаты |
| Аренды и номера попыток | Не позволяют запоздавшему исполнителю завершить уже переданное другому задание |
| Неизменяемые предложения | Сохраняют точный текст изменений и их контрольную сумму |
| Учёт прочитанных данных | Обнаруживает изменение сведений, которыми пользовался автор |
| Учёт результатов запросов | Обнаруживает, например, появление новой платформы в полном перечне |
| Проверка общих ограничений | Выявляет несовместимость правок разных записей |
| Отдельное принятие | Координатор повторно проверяет условия непосредственно перед записью |
| Согласованный выпуск | Формирует документы, Python-код, источники и поиск из одной ревизии |

**Исполнители демонстрации — программные агенты с заданными правилами. Внешние LLM пока не подключены.** Это позволяет отдельно изучать правильность координации.

Исходники находятся в каталоге [agentwiki](https://github.com/svend4/infod10/tree/d2c3df3b24a10bc6c54948a996eb644543ad7917/agentwiki).

### Пример смыслового конфликта

Исходное состояние:

```text
Тайм-аут: 30 секунд
Число попыток: 3
Общий бюджет: 120 секунд
```

Два агента независимо предложили:

- увеличить тайм-аут до 40 секунд: `40 × 3 = 120`;
- увеличить число попыток до 4: `30 × 4 = 120`.

Оба предложения по отдельности допустимы. Их объединение даёт:

```text
40 × 4 = 160 секунд > 120 секунд
```

Первая правка принята. Вторая заблокирована при повторной проверке общего ограничения.

Здесь нет обязательного конфликта строк: агенты меняют разные записи. Обычное текстовое слияние само по себе такую несовместимость не объясняет.

### Ещё три показанных случая

1. **Изменился состав запроса.** После добавления Windows старое предложение полного списка платформ было отклонено, хотя запись Linux оставалась прежней.
2. **Устарело основание документа.** Документ, подготовленный по тайм-ауту 30 секунд, не принят после изменения значения на 40.
3. **Вернулся старый исполнитель.** После передачи задания другому worker прежний номер попытки получил отказ `lease_lost`.

## 3. Как согласованы документы и код

Принятые структурированные утверждения используются в шаблонах обоих типов:

```text
Принятое значение
    ├── справочник и руководства
    └── Python-конфигурация
```

В результате документация и созданный код используют одинаковые параметры:

```python
TIMEOUT_SECONDS = 40
MAX_ATTEMPTS = 3
BUDGET_SECONDS = 120
```

**[Полученный Python-файл](https://github.com/svend4/infod10/blob/d2c3df3b24a10bc6c54948a996eb644543ad7917/examples/multi-agent/results/release/r9-a450bcf40a40dc20/code/client_config.py)** сохранён вместе с документами и манифестом выпуска.

Подстановка проверяемых параметров уменьшает расхождения между текстом и примером программы. Свободные абзацы, правильность алгоритмов и достоверность источников требуют дополнительных проверок. Предложенный код автоматически не исполняется.

## 4. Сколько агентов может работать

Нужно различать количество ролей, активных исполнителей, открытых предложений и операций принятия.

| Количество | Разумная организация работы |
|---:|---|
| 1 | Последовательная подготовка предложений с сохранением оснований |
| 4 | Несколько авторских заданий, проверка и координация |
| 8 | Авторы разных материалов и дополнительные проверяющие |
| 16 | Несколько тематических очередей |
| 32 | Ограниченный параллелизм с разделением областей знания |
| 100+ | Большой пул исполнителей, управляемый очередью и бюджетом |

Это **проектные сценарии**, а не измеренные пределы программы. Фактически выполнен сценарий с шестью потоками. Ограничение CLI в 32 workers задаёт допустимый размер пула примера.

Добавление агентов помогает, пока последовательные стадии и повторная работа не становятся главным ограничением. Например, при условных 90% распараллеливаемой работы закон Амдала даёт:

```text
4 исполнителя:   ускорение около 3,08
16 исполнителей: ускорение около 6,40
100 исполнителей: ускорение около 9,17
```

Это идеализированный расчёт без накладных расходов. Реальная система дополнительно тратит время на ревью, конфликты, источники и повторные вызовы моделей.

**[Полный теоретический анализ](https://github.com/svend4/infod10/blob/d2c3df3b24a10bc6c54948a996eb644543ad7917/docs/development/theory.md)** содержит формулы, расчёты очереди принятия и стоимости проверенного изменения.

## 5. Как запустить самостоятельно

Из корня репозитория:

```bash
python3 -m agentwiki demo \
  --workspace /tmp/agentwiki-my-run-01 \
  --workers 6

python3 -m agentwiki status \
  --workspace /tmp/agentwiki-my-run-01
```

Нужен новый пустой каталог. Программа сохраняет существующие данные.

Поиск по уже опубликованному примеру:

```bash
python3 -m agentwiki search \
  --release examples/multi-agent/results/release/r9-a450bcf40a40dc20 \
  --query "попытки бюджет"
```

В руководстве есть пример добавления собственного задания через Python API.

## 6. Поэтапное дальнейшее развитие

Подготовлена **[подробная дорожная карта](https://github.com/svend4/infod10/blob/d2c3df3b24a10bc6c54948a996eb644543ad7917/docs/development/roadmap.md)**. Наиболее перспективны следующие направления:

1. **Граф влияния изменений.** Вычислять, какие утверждения, документы, примеры кода и проверки затронуты конкретной правкой.
2. **Целевая перепроверка.** Повторять только необходимые проверки, измеряя пропущенные ошибки и объём сэкономленной работы.
3. **Пакеты с проверяемым основанием.** Передавать вместе с предложением снимок источника, цитату, зависимости, правила и результаты проверок.
4. **Корпус смысловых регрессий.** Собирать случаи с единицами измерения, версиями, отрицаниями, обязательностью требований и противоречивыми источниками.
5. **Разнообразное ревью моделей.** Сравнивать пользу разных моделей и исследовательских маршрутов при одинаковом бюджете.
6. **Адаптивный параллелизм.** Менять число активных агентов по очереди ревью, частоте конфликтов и стоимости принятого результата.

Новизну этих решений предстоит устанавливать сравнительными экспериментами. Мировое первенство не заявляется.

Сейчас каноническое рабочее состояние находится в SQLite; Git хранит код, документацию и снимки результатов. Систематические испытания отказов и нагрузки, реальные LLM, веб-портал и согласование транзакций Git с SQL остаются дальнейшими этапами. Архив беседы также продолжен: сохранено **49 сообщений до вашего поручения реализации включительно**.
