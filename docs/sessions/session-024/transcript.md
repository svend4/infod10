<a id="m0002"></a>
### m0002 · Ассистент · промежуточное сообщение

Для этого шага выбран постоянный запрет записи в исходной базе. Его метка поместится в существующую таблицу `meta`, поэтому формат прежних резервных копий сохранится.

Обнаружена важная гонка: сейчас публикация пишет файлы уже после завершения чтения SQLite. Чтобы она не завершалась после остановки источника, публикация и установка запрета будут использовать одну очередь блокировки записи.

<a id="m0003"></a>
### m0003 · Ассистент · промежуточное сообщение

Установка запрета будет проверять свежий план под блокировкой записи и сохранять метку вместе с одним событием. Точный повтор вернёт прежнюю квитанцию без повторного изменения базы.

Этот барьер действует для обновлённого Store и одной канонической базы. Старые версии приложения и прямой SQL его не соблюдают; это ограничение будет явно указано в документации.

### m0004 · Ассистент · промежуточное сообщение

Допустимы два исхода: публикация завершает файловые действия до установки запрета либо получает отказ после него. Фактический исход сохраню в отчёте.

## Завершён этап 21 — версия 0.21.0

Реализован постоянный запрет записи в источнике:
