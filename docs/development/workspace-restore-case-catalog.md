# Постраничный каталог сохранённых случаев восстановления

Статус: двадцать девятый этап локального прототипа. Отдельный частный каталог закрепляет явно выбранный состав case records и позволяет читать его ограниченными страницами. Исторические квитанции участников сохраняются в каталоге; текущая доступность их управляющих записей наблюдается отдельно.

**Обычный development-запуск успешно завершён 21 октября 2026 года с первой попытки.** Два каталога сохранили явный состав из трёх и четырёх случаев, потерянный create-ответ восстановлен точным replay, недоступный и заменённый пути получили отдельные наблюдения без потери исторических участников. Независимые публичная, частная и privacy-сверки завершены успешно; результаты приведены в разделе 13.

## 1. Зачем сохранять состав обхода

У нескольких процессов могут быть разные задачи: один фиксирует случаи отказа, другой выбирает новую попытку, третий собирает обзор для оператора. Если каждый заново перечисляет каталоги, состав и порядок работы меняются между страницами. Исчезнувшая запись может пропасть из обзора, а новая — попасть в середину уже начатого обхода.

Сохранённый каталог задаёт явную область: оператор передаёт упорядоченный список уже существующих case directories, а каталог фиксирует их исторические квитанции. Последующие страницы обходят этот состав. Появившиеся позднее случаи требуют нового каталога с новым явным входом.

Такой протокол позволяет повторить чтение страницы, восстановить потерянный ответ создания и распределить выбранные позиции между callers. Факт успешного обхода относится к перечисленным записям; полнота всех случаев в файловой системе требует отдельного источника учёта.

## 2. Состав фиксирован, наблюдения последовательны

Здесь различаются три основания:

| Основание | Что закреплено |
| --- | --- |
| Историческая квитанция каталога | Идентичность каталога, его операция, время и число выбранных случаев |
| Историческая квитанция участника | Безопасный 13-полевой case receipt, захваченный при создании |
| Текущее наблюдение участника | Доступность той же управляющей case record и читаемая link receipt на момент страницы |

Создание последовательно читает выбранные case records под их отдельными блокировками. Участники могли быть прочитаны в разное время. Зафиксированный состав не является общим снимком всех каталогов, исходных evidence или restore jobs.

При повторе страницы квитанции участников и их позиции сохраняются. Текущие метаданные могут отличаться: путь стал недоступен, управляющая запись заменена либо появилась допустимая link record.

## 3. Явный вход и ограниченный объём

В одном каталоге допускаются от 1 до 256 случаев. Вход является упорядоченным списком; порядок имеет значение для точного повтора операции. Повторяющиеся пути или case IDs вызывают отказ; автоматического удаления повторов нет.

Каталог и выбранные case directories располагаются отдельными соседями под одним частным parent. Список задаётся явно, без рекурсивного поиска, распознавания префиксов имён либо автоматического включения новых entries.

Страница запрашивает от 1 до 16 позиций. Предел относится к объёму одной операции; он не является измеренной ёмкостью по числу агентов. Весь каталог остаётся ограниченным даже при малом размере страницы.

Каждый запрос считывает и валидирует всю ограниченную запись каталога. Текущие управляющие файлы cases читаются только для выбранных позиций страницы. Поэтому page limit ограничивает число текущих наблюдений, а общий объём валидации также зависит от сохранённого числа участников.

Создание и чтение используют общий срок 60 секунд, включая ожидание блокировок. Истечение общего срока прекращает весь запрос с `workspace_restore_case_catalog_limit_exceeded`; оно не подменяется отдельным состоянием недоступного участника. Страницы читают только управляющие case/link records. Завершённые DB, архивы, старые evidence и текущий restore progress остаются за пределами такого обзора.

## 4. Частное хранение и неизменяемые привязки

Каталог сохраняется отдельно от case directories, исходных jobs и backup bundles. Он содержит частные пути и привязки выбранных управляющих записей. Права каталогов — 0700, частных файлов — 0600.

Неизменяемые case record и case lock закрепляются вместе с идентичностью case directory. Возможная link record наблюдается отдельно: допустимая ассоциация может появиться позже у той же case. При этом историческая квитанция участника каталога остаётся прежней.

Публичные ответы не раскрывают частные пути, полные управляющие записи, request digests, filesystem fingerprints и контрольные суммы. Их отсутствие в ответе не меняет требования к проверке частного основания.

Каталог содержит ровно два фиксированных control files:

| Файл | Ограничение |
| --- | --- |
| `.agentwiki-restore-case-catalog.json` | Каноническая частная запись, не более 2 MiB |
| `.agentwiki-restore-case-catalog.lock` | Постоянный пустой файл локальной блокировки |

Неизвестные entries не расширяют формат. Неполная либо неподтверждённая запись не разрешает перезаписать сохранённый состав.

## 5. Публичная квитанция каталога: 12 полей

| Поле | Значение |
| --- | --- |
| `rules_version` | `workspace-restore-case-catalog-1` |
| `catalog_id` | Локальный идентификатор `wrcat_` и 32 шестнадцатеричных символа |
| `operation_id` | ID точного запроса создания каталога |
| `created_at` | Фиксированное время исторической записи |
| `case_count` | Число явно выбранных участников, от 1 до 256 |
| `membership_frozen` | `true` |
| `order_frozen` | `true` |
| `inspection_only` | `true` |
| `domain_writes_allowed` | `false` |
| `original_files_modified` | `false` |
| `old_authority_activated` | `false` |
| `external_fencing_established` | `false` |

Время относится к созданию каталога. Оно не задаёт единый момент захвата всех case records. `membership_frozen` и `order_frozen` описывают состав и порядок этого каталога, без утверждения полноты всех случаев на машине.

## 6. Позиция и контекст cursor

Cursor связывает позицию с идентичностью конкретного каталога. Один числовой индекс без контекста каталога мог бы случайно продолжить другой набор случаев; поэтому идентичность проверяется вместе с позицией.

Cursor имеет ровно два поля: `catalog_id` и целочисленный `after_index`. Позиция описывает число уже пропущенных элементов фиксированного списка и допускает значения от 0 до `case_count`. Индексы самих участников начинаются с 1.

При размере страницы 2 для трёх участников первый запрос возвращает позиции 1 и 2, следующий с `after_index=2` — позицию 3. Значение `next_cursor` определяет возможность продолжения.

Cursor не закрепляет результат текущих наблюдений и не удостоверяет их свежесть. Повтор того же диапазона может сообщить другую доступность управляющей записи при той же исторической case receipt.

Изменение page limit меняет размер следующего диапазона, сохраняя контекст и порядок каталога. Новые случаи не добавляются в уже начатый обход.

Начальный API cursor равен `null`, что означает `after_index=0` текущего каталога. Явный cursor с чужим catalog ID либо индексом вне границ вызывает отказ. Индекс в конце списка разрешён и даёт пустую страницу с `next_cursor=null`.

CLI принимает `--catalog-id` и `--after-index` совместно. Отсутствие обеих опций начинает обход; только одна из них не задаёт допустимый cursor. Булевы значения не считаются целочисленными API-индексами или limit.

## 7. Страница: восемь полей

| Поле | Значение |
| --- | --- |
| `rules_version` | `workspace-restore-case-catalog-1` |
| `catalog` | Историческая 12-полевая квитанция каталога |
| `after_index` | Число пропущенных позиций перед этой страницей |
| `limit` | Запрошенный размер страницы, от 1 до 16 |
| `entries` | Следующие ограниченные позиции фиксированного списка |
| `next_cursor` | `{catalog_id, after_index}` при наличии оставшихся позиций, иначе `null` |
| `original_evidence_checked` | `false` |
| `live_jobs_checked` | `false` |

Каждая entry имеет ровно три поля:

| Поле | Значение |
| --- | --- |
| `index` | Устойчивая позиция участника, начиная с 1 |
| `case` | Захваченная историческая 13-полевая case receipt |
| `current_case` | Наблюдение управляющей записи с тремя полями `state`, `link`, `error_code` |

При доступном каталоге диапазон содержит `min(limit, case_count - after_index)` entries, включая позиции с текущими ошибками. Эти ошибки не сокращают список и не сдвигают следующие индексы. `next_cursor.after_index` совпадает с последним возвращённым индексом.

Публичные case/link вложения сохраняют прежние строгие схемы из [руководства по случаям](workspace-restore-cases.md). В частности, неизвестная исходная identity случая `plan_invalid` остаётся `null`; принадлежность участника каталогу не реконструирует её.

## 8. Текущее наблюдение управляющей записи

Историческая квитанция участника остаётся доступной из самого каталога. Для текущего case path предусмотрены ограниченные состояния:

| State | `link` | `error_code` | Наблюдение |
| --- | --- | --- | --- |
| `available` | Историческая 14-полевая квитанция либо `null` | `null` | Та же закреплённая case record доступна; её возможная link record читается в предусмотренном формате |
| `changed` | `null` | `workspace_restore_case_catalog_entry_changed` | Безопасно читаемые directory/file/lock pins отличаются от закреплённого основания |
| `unavailable` | `null` | `workspace_restore_case_catalog_entry_unavailable` | Путь отсутствует, небезопасен либо управляющие записи не проходят поддержанную проверку |

Ошибка одного участника сохраняется в его позиции. Остальные элементы страницы не исчезают из-за этой ошибки. Общая ошибка чтения самого каталога либо неверный cursor относятся ко всему запросу.

`available` относится к управляющей case record. Сохранность исходного job, его evidence, доступность связанной попытки и её текущий progress этим состоянием не устанавливаются.

Доступная замена закреплённого directory/file/lock обнаруживается до разбора изменённого case JSON. Непроверяемая форма, неподдержанные права, ошибка чтения либо malformed link дают ограниченное `unavailable`. Эти состояния сообщают исход наблюдения, без заявления об установленной причине изменения файлов.

Если доступная case содержит link, наружу передаётся прежняя историческая link receipt с её зафиксированным `attempt_status`. Для текущего состояния попытки caller отдельно вызывает существующую команду `workspace-restore-case show`.

Даже когда link содержит `prepared`, связанный job уже мог завершиться. Каталог не превращает сохранённый `attempt_status` в новое наблюдение restore job.

## 9. Повтор создания и восстановление ответа

Операция создания имеет собственный operation ID и точный упорядоченный вход. При повторе возвращается фиксированная историческая квитанция того же каталога. Другой operation ID, состав либо порядок для того же catalog directory вызывают `workspace_restore_case_catalog_conflict`. Для нового выбранного состава создаётся отдельный каталог.

Повтор использует сохранённые привязки и не требует заново считать текущее состояние каждого case. Благодаря этому потеря ответа создания отделяется от текущей недоступности одного из участников.

Такое восстановление ответа не является восстановлением удалённых case files. Сохранённая копия публичной квитанции также не предоставляет права ремонта исходного job или активации исторической DB.

Частичная запись самого каталога остаётся отдельным блокирующим состоянием. Поддержку прерываний её создания требуется обосновывать отдельным протоколом и выполненными сценариями.

## 10. Порядок блокировок и наблюдения между страницами

Создание сначала последовательно читает выбранные cases, затем резервирует отдельный catalog directory и под его блокировкой повторно захватывает участников. Оба набора закреплённых метаданных должны совпасть. Предварительные case-блокировки освобождены до резервирования каталога.

Страница удерживает локальную блокировку каталога. При чтении участника дополнительно берётся только одна case-блокировка, после чего она освобождается перед следующим участником. Порядок не требует совместного удержания блокировок всех случаев. Restore job locks для metadata-only обхода не нужны.

Метаданные участников наблюдаются последовательно. Поздний caller может получить link record, которой ещё не было в более ранней странице. Отсутствие общего SQL-снимка и общей файловой транзакции сохраняется явно.

Каталог не резервирует позиции за исполнителями и не отмечает их завершение. Два callers могут читать один диапазон. Для распределения работы с эксклюзивным владением нужны отдельные аренды, учёт результатов и правила повторной доставки.

Неизменяемое членство уменьшает неопределённость о составе работы; оно не заменяет планировщик.

## 11. Применение в многоагентном процессе

Один ограниченный поток может выглядеть так:

1. Координатор явно выбирает case directories и создаёт каталог.
2. Несколько читателей получают страницы того же каталога и сохраняют его ID вместе с позицией.
3. Для нужной позиции читатель отдельно запрашивает подробный case show.
4. Оператор принимает решение о новой попытке, сохранении свидетельств либо дальнейшей диагностике.
5. Появившиеся новые случаи попадают в отдельно созданный каталог.

Обзор и управляющее действие сохраняют разные operation IDs и основания. Каталог не создаёт restore jobs, не удаляет старые остатки и не подставляет параметры неизвестного исходного запроса.

Для технического портала аналогичный принцип полезен при обходе фиксированного списка документов, предложений либо редакторских пакетов: состав рассмотрения должен быть отделён от текущей доступности и состояния каждого объекта. Перенос этого принципа в предметную вики потребует собственного формата документов, зависимостей и семантических оснований; текущий каталог реализует только случаи локального восстановления.

Количество страниц, процессов и одинаковых квитанций не подтверждает независимость участников, качество текста или предельную производительность. Для этих выводов нужны отдельные измерения и независимая предметная оценка.

## 12. Команды и воспроизведение

Программный интерфейс отдельного модуля `agentwiki.workspace_restore_case_catalog`:

~~~python
create_catalog(catalog_directory, case_directories, operation_id=operation_id)
read_catalog_page(catalog_directory, limit=16, cursor=None)
~~~

`case_directories` передаётся явным упорядоченным списком. Например, три заранее созданных случая можно выбрать в порядке C → A → B:

~~~sh
python3 -m agentwiki workspace-restore-case-catalog create \
  --catalog /tmp/agentwiki-private/case-catalog \
  --case /tmp/agentwiki-private/case-c \
  --case /tmp/agentwiki-private/case-a \
  --case /tmp/agentwiki-private/case-b \
  --operation-id create-case-catalog-01
~~~

Начальная страница:

~~~sh
python3 -m agentwiki workspace-restore-case-catalog page \
  --catalog /tmp/agentwiki-private/case-catalog \
  --limit 2
~~~

Для следующей страницы caller использует оба значения из полученного `next_cursor`. Ниже `CATALOG_ID` обозначает возвращённый catalog ID:

~~~sh
python3 -m agentwiki workspace-restore-case-catalog page \
  --catalog /tmp/agentwiki-private/case-catalog \
  --limit 2 --catalog-id CATALOG_ID --after-index 2
~~~

Существующая подробная диагностика случая сохраняется:

~~~sh
python3 -m agentwiki workspace-restore-case show \
  --case /tmp/agentwiki-private/restore-case
~~~

Для обычного демонстратора из корня checkout укажите новый каталог запуска:

~~~sh
python3 -m agentwiki workspace-restore-case-catalog-demo \
  --workspace /tmp/agentwiki-restore-case-catalog-01 --workers 3
~~~

Python, стандартная библиотека и требования POSIX private permissions сохраняются; дополнительные зависимости для каталога не нужны. Составной сценарий заново выполняет основание предыдущего этапа. Размер worker pool относится к этому локальному основанию, без измерения числа LLM-агентов.

## 14. Границы и следующие задачи

Каталог охватывает явно заданный набор. Глобальное обнаружение всех случаев, автоматическое удаление, политика удержания и долговременный индекс не реализуются этим форматом.

Неизменяемые привязки помогают обнаружить поддержанные изменения файлов, но не устанавливают внешнее авторство, полноту истории либо защиту от владельца файлов. Доступная историческая квитанция не является новым полномочием.

Открытыми остаются прерывания записи каталога, аппаратные отказы, взаимное исключение обработчиков, политика хранения и измерение времени при разных долях недоступных участников. Отдельно остаётся оценка смыслового содержания документации и независимости редакторских решений.
