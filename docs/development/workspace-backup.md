# Резервная копия рабочей среды и всей истории происхождения

Статус: двадцать четвёртый этап локального прототипа, правила `workspace-backup-1`. Полный комплект сохраняет текущую SQLite-базу импортированной рабочей среды и все архивы её предков. Восстановленная база остаётся в постоянном карантине и используется для исторического чтения.

- [Предыдущий этап: цепочка повторных переносов](source-transfer-chain.md).
- [Исходный механизм снимка одной базы](store-backup.md).
- [Прикладной сценарий](../../examples/workspace-backup/README.md).
- [Фактический отчёт запуска](../../examples/workspace-backup/results/workspace-report.md).

## 1. Зачем нужен полный комплект

После повторного переноса история распределена между текущей рабочей базой и самостоятельными архивами прежних сред. Текущие документы могут сохранять зависимости от предложений из разных поколений. Резервная копия только `state.sqlite3` сохраняет импортированные описания зависимостей, но не включает внешние файлы с полной прежней историей.

Новый механизм сохраняет обе части в одном частном комплекте:

- согласованный снимок текущей базы, включая её собственные предложения, решения и квитанции;
- точные копии всех архивов предков и упорядоченную опись их происхождения;
- частные метаданные, достаточные для проверки комплекта после утраты прежних каталогов.

Исходная рабочая среда продолжает работу. Снимок отражает состояние на выбранной границе чтения SQLite; дальнейшие изменения источника не дописываются в уже созданную копию.

```mermaid
flowchart LR
    W["Действующая рабочая база"] -->|"согласованный SQLite backup"| Q["Карантинная копия базы"]
    A["Все архивы предков"] -->|"точное копирование байтов"| H["Архивы внутри комплекта"]
    Q --> B["Частный полный комплект"]
    H --> B
    B -->|"проверка и копирование"| R["Новый каталог для исторического чтения"]
```

## 2. Содержание и полномочия

Текущая база копируется целиком. В ней остаются grants, revocations, аренды, proposals, решения, операции, receipts и импортированный origin. Эти записи сохраняют историю исходной рабочей среды.

В копию добавляется постоянная quarantine table прежнего протокола `store-snapshot-1`. Обычный Store распознаёт её до настройки WAL и схемы, открывает базу для чтения и блокирует новые доменные записи и публикацию. Восстановление не продлевает срок допусков, не переоформляет аренды и не предоставляет права повторно выполнить историческую операцию как новое действие.

| Что сохраняется | Как используется после восстановления |
| --- | --- |
| Принятые документы, код и sources | Историческое чтение сохранённого состояния |
| Исходные dependency records и anchors | Объяснение происхождения и объявленных оснований |
| Полная текущая SQL-история | Чтение предложений, решений, аудитов и квитанций |
| Архивы прежних поколений | Проверка цепочки локального происхождения |
| Grants и leases в скопированных строках | Исторические сведения под запретом новых записей |
| Quarantine marker | Постоянная граница доступа к копии |

Текущий этап не содержит API активации восстановленной среды. Создание новой действующей среды требует собственного протокола прекращения прежних записей и выдачи новых полномочий.

## 3. Частный формат комплекта

### 3.1. Каталоги и файлы

Полная копия использует плоскую основную базу и отдельный подкаталог архивов:

~~~text
workspace-backup/
  .agentwiki-snapshot-intent.json
  state.sqlite3
  .agentwiki-snapshot-manifest.json
  archives/
    history-0001.sqlite3
    ...
    history.sqlite3
  .agentwiki-workspace-intent.json
  .agentwiki-workspace-manifest.json
~~~

Корень завершённого комплекта содержит шесть записей: пять файлов и каталог `archives`. Состав архива задаётся ограниченной описью; посторонние файлы не подменяют ожидаемые части.

Каталоги имеют права 0700, частные файлы — 0600. Требуются обычные файлы владельца; символические ссылки и неподдерживаемые файловые объекты отвергаются. Credentials хранятся отдельно и не копируются как самостоятельные credential-файлы в комплект. Их исторические хеши уже присутствуют в закрытых SQL-строках исходной базы.

Имена внутри `archives` сохраняют порядок от самого раннего предка к ближайшему. Последний архив называется `history.sqlite3`, старшие — `history-0001.sqlite3`, `history-0002.sqlite3` и далее. При одном архиве порядковые файлы отсутствуют.

### 3.2. Сохранение прежних форматов

Три файла snapshot сохраняют прежний частный формат снимка одной базы. Отдельные workspace intent и manifest связывают эту копию с полной архивной описью. Формат dependency record, публичного выпуска и квитанции `source-transfer-1` остаётся прежним.

Workspace intent имеет шесть полей: `schema_version`, `rules_version`, `kind`, `workspace_backup_id`, `created_at` и `workspace_id`. Workspace manifest добавляет к ним полный частный `snapshot` прежнего формата и список `archives`. Каждая архивная запись содержит `name`, `bytes`, `sha256` и безопасную `receipt`; частные файловые привязки не становятся публичным ответом.

Origin внутри скопированной базы также сохраняется без переписывания. Его первоначальные активные пути становятся историческими сведениями. При карантинном чтении они не требуют наличия прежних каталогов и не разрешают активировать копию по новому адресу.

В полном комплекте поддерживается происхождение импортированной среды с private origin schema 1 или schema 2. Для schema 1 ближайший архив и его квитанция задают одношаговое основание; schema 2 закрепляет полную архивную цепочку. Дополнительные возможности чтения не меняют старые сохранённые материалы.

### 3.3. Частные и публичные данные

Размеры файлов, SHA-256, полный manifest, schema fingerprint, origin, denylist и request digest остаются частными. Эти значения нужны для проверки согласованности собственного комплекта; они не являются внешней подписью или удостоверением администратора.

Публичный ответ содержит безопасные ID, счётчики, квитанции переносов и границы использования копии. Абсолютные служебные пути, контрольные суммы баз и credential hashes не включаются в CLI или публичный отчёт.

## 4. Источник и граница захвата

Создание полной копии принимает существующую активную импортированную базу. Источник должен иметь поддерживаемую схему, завершённый origin и доступный полный комплект его архивов. Карантинная или остановленная source fence база не используется как действующий источник нового backup.

Административный credential проверяется по актуальной исходной базе и текущему времени. Это подтверждает владение локальным административным допуском; личность человека и независимость участников так не устанавливаются.

Текущая база читается из одного закреплённого read-only снимка SQLite. В том же контексте устанавливаются ревизия, граница событий, таблицы, origin и данные для native backup. Полученная копия не собирается из нескольких независимо наблюдённых SQL-состояний.

Перед записью окончательного workspace manifest исходная база открывается отдельно для заключительной writer reservation `BEGIN IMMEDIATE`. Она проверяет актуальное разрешение завершить операцию; доменные SQL-строки при этом не меняются. Граница содержимого backup остаётся прежним закреплённым снимком.

Архивы предков являются самостоятельными неизменяемыми файлами. Они проходят полную проверку, копируются с точным совпадением байтов и проверяются в назначении. Такая файловая работа не превращается в общую транзакцию с SQLite источника.

## 5. Последовательность создания

1. Проверить платформу, пути, частные права и новый каталог назначения.
2. Открыть существующий источник для чтения и закрепить один SQL-снимок.
3. Проверить административный допуск, отсутствие quarantine/source fence и завершённое происхождение текущей среды.
4. Проверить весь набор архивов: размер, контрольную сумму, поддерживаемую схему, source fence, transfer binding, событие и непрерывность цепочки.
5. Создать новый каталог назначения и первым записать штатный snapshot intent.
6. Записать workspace intent и подготовить частный каталог `archives`.
7. Выполнить native SQLite backup текущего снимка, добавить quarantine marker только в копию и завершить её как самостоятельную базу `DELETE`.
8. Проверить скопированную базу, счётчики, целостность, внешние ключи и допустимый размер после добавления marker.
9. Скопировать архивы предков точно и подтвердить соответствие сохранённой описи.
10. Завершить штатный snapshot manifest и сверить полный комплект, включая связь origin с последним архивом.
11. Получить в источнике заключительную writer reservation, заново проверить отсутствие quarantine/source fence, текущий административный grant, захваченный origin и завершённый комплект происхождения.
12. Удерживая reservation, записать workspace manifest последним и синхронизировать завершение. Затем освободить reservation и вернуть безопасную сводку.

Штатный snapshot intent записывается первым, чтобы неполное назначение не могло выглядеть как место для новой активной базы. Добавление quarantine marker может увеличить число SQLite-страниц; предел размера проверяется по фактическому результату.

Native backup требуется текущей базе: простое копирование её main-файла при действующем WAL не гарантирует согласованного состояния. Для готовых архивов используется точное копирование байтов, чтобы сохранить уже закреплённые контрольные суммы.

### 5.1. Что означает заключительная writer reservation

Заключительная проверка использует свежую исходную базу и требует того же действующего административного grant, которым начато создание копии. Reservation удерживается до записи manifest и `fsync`. Кооперативные операции отзыва допуска и source fence, которым также нужен SQLite writer lock, сериализуются с этим завершением. Они не могут вклиниться между заключительной проверкой и записью файла завершения.

Между исходным захватом содержимого и заключительной reservation источник мог продолжить обычную работу. Поздние изменения не дописываются в сохранённый снимок и не превращают его историческую ревизию в текущую. Заключительная проверка разрешения завершить backup отделена от границы его содержимого.

SQLite и файловая система по-прежнему не образуют общую атомарную транзакцию. Заключительная reservation не устанавливает глобальное прекращение записей, не выбирает нового действующего писателя и не отменяет ранее выполненные внешние эффекты. После её освобождения исходная среда продолжает собственную работу.

## 6. Проверка полного комплекта

`inspect_bundle` требует завершённые штатные и workspace метаданные, точный поддерживаемый состав каталогов и весь заявленный набор архивов.

Проверка основной базы подтверждает:

- полный размер и контрольную сумму файла;
- поддерживаемую схему с quarantine table и точный marker;
- соответствие ревизии, границы событий и счётчиков таблиц manifest;
- самостоятельный режим `DELETE`, SQLite integrity и внешние ключи;
- корректный сохранённый origin и его связь с архивным происхождением.

Проверка архивов подтверждает полные контрольные суммы, source fence и квитанции соответствующих переносов, а также последовательность origin между поколениями. Anchors исходного импорта сопоставляются с принятым экспортом предыдущего архивного источника. Унаследованный denylist должен соответствовать совокупности прежних credentials.

При сравнении цепочки локальное имя архива не считается его содержательной идентичностью: прежний ближайший архив мог получить порядковое имя. Сравниваются квитанция, размер и контрольная сумма. Сами архивные байты сохраняются точно.

Проверка копии не открывает прежние активные пути, записанные в origin. Она использует текущую карантинную базу и локальные архивы полного комплекта. Прежние каталоги могут быть недоступны.

## 7. Восстановление для исторического чтения

Восстановление сначала полностью проверяет исходный bundle, затем создаёт новый частный каталог. Основная база и все архивы копируются с проверкой точных байтов. Quarantine marker и исторический origin сохраняются.

В новом каталоге создаются собственные intent и completion metadata операции восстановления. Связь с исходной копией сохраняется в предусмотренных идентификаторах; содержимое базы не получает новый активный административный допуск.

Идентификаторы полной копии, штатного snapshot и quarantine сохраняются. Метаданные новой файловой операции получают `kind=restore` и новую отметку её создания; сохранённый quarantine marker внутри SQLite остаётся прежним.

Повторная проверка восстановленного комплекта подтверждает сохранённый SQL-снимок и полную цепочку. Обычный Store открывает `state.sqlite3` для чтения; новые записи, публикация и попытки использовать копию как действующий источник остаются запрещёнными.

| Операция | Поведение |
| --- | --- |
| Чтение snapshot, задач, решений и receipts | Историческое наблюдение сохранённых записей |
| Проверка полного bundle | Основная база и все архивы проверяются совместно |
| Новая доменная запись или публикация | Блокируется карантином |
| Возобновление старой аренды или grant | Восстановление такого разрешения не создаёт |
| Восстановление поверх существующего каталога | Отклоняется |
| Автоматическая активация восстановленной среды | В текущем API отсутствует |

## 8. Полнота и частичные остатки

У комплекта две границы завершения. Штатный snapshot manifest завершает карантинную копию одной базы. Workspace manifest завершает полный набор вместе с архивами.

Если штатная копия уже готова, а workspace manifest или часть архивов отсутствует, обычный Store может читать эту карантинную базу. Это чтение само по себе не подтверждает полноту всей предшествующей истории. Полные `inspect` и `restore` требуют полного workspace завершения и всех заявленных файлов.

При отсутствующем штатном manifest, marker или основной базе обычный Store не должен инициализировать неполное назначение как активную среду. Сохранённый intent служит отдельным признаком незавершённой операции.

API создаёт новые каталоги и не переписывает чужие данные. Автоматического продолжения частичной полной копии, дописывания повреждённого архива, усыновления остатка или переназначения операции на другой путь этот этап не вводит.

Остатки следует сохранять для разбирательства. Их наличие, отсутствие workspace manifest и ошибка проверки не являются разрешением удалить quarantine или использовать старые credentials для новой работы.

## 9. Команды

Нужны Python 3.10+, стандартная библиотека и POSIX-права частных файлов. Все пути ниже обозначают локальные частные каталоги; credential уже должен находиться в отдельном файле с правами 0600.

~~~sh
python3 -m agentwiki workspace-backup create \
  --workspace /tmp/agentwiki-private/source \
  --destination /tmp/agentwiki-private/full-backup \
  --credential /tmp/agentwiki-private/admin.credential

python3 -m agentwiki workspace-backup inspect \
  --bundle /tmp/agentwiki-private/full-backup

python3 -m agentwiki workspace-backup restore \
  --bundle /tmp/agentwiki-private/full-backup \
  --destination /tmp/agentwiki-private/full-restore

python3 -m agentwiki status \
  --workspace /tmp/agentwiki-private/full-restore
~~~

`create` читает действующий источник и отдельный credential. `inspect` и `restore` работают с уже сохранённым частным bundle; чтение исторической копии не требует наличия прежнего источника.

Программный интерфейс находится в `agentwiki.workspace_backup`:

~~~python
create_backup(database_path, destination, credential=credential)
inspect_bundle(bundle_path)
restore_bundle(bundle_path, destination)
~~~

Вызовы возвращают безопасную сводку. Путь назначения и секрет не передаются как данные публичного отчёта.

Основные коды полного API:

| Код | Причина отказа |
| --- | --- |
| `workspace_backup_source_invalid` | Источник не является подходящей действующей импортированной средой |
| `workspace_backup_destination_exists` | Назначение уже существует; данные не заменяются |
| `workspace_backup_incomplete` | Нет необходимого завершения или заявленной части комплекта |
| `workspace_backup_manifest_invalid` | Метаданные, состав или связи происхождения не проходят проверку |
| `workspace_backup_checksum_mismatch` | Файл отличается от закреплённых байтов |
| `workspace_backup_limit_exceeded` | Превышен срок или поддерживаемый объём |
| `workspace_backup_private_path_required` | Путь или права не соответствуют частному формату |
| `workspace_backup_invalid_input` | Неподдерживаемый вход или расположение назначения |
| `workspace_backup_io_failed` | Обработка или ввод-вывод не завершились |

Отказы авторизации сохраняют коды `governance_*`; остановленный источник возвращает `store_source_fenced`. CLI отдельно использует `unknown_workspace_backup_command`, `workspace_backup_summary_invalid` и безопасный общий отказ `workspace_backup_command_failed`. Ранние отказы обычного Store по неполному snapshot сохраняют прежние коды карантина и не разрешают новую инициализацию.

## 10. Публичная сводка

Ответ включает фиксированный набор из 18 полей; дополнительные частные поля API не пересылаются CLI автоматически.

| Группа | Поля |
| --- | --- |
| Формат и операция | `rules_version`, `kind`, `workspace_backup_id`, `created_at` |
| Рабочая среда | `workspace_id`, `revision`, `event_high_water`, `event_count`, `table_counts` |
| История | `archive_count`, `receipts` |
| Техническая проверка | `integrity`, `foreign_keys` |
| Граница использования | `inspection_only=true`, `domain_writes_allowed=false`, `full_history_preserved=true`, `old_authority_activated=false`, `external_fencing_established=false` |

`receipts` сохраняет порядок архивов и прежние безопасные квитанции `source-transfer-1`. Текущее состояние копии описывают отдельные поля revision и event count; последняя квитанция переноса относится к исходному импортному основанию, которое могло предшествовать дальнейшей работе.

`full_history_preserved=true` относится к проверенному локальному комплекту и предусмотренной цепочке архивов. Это не утверждение о наличии всех внешних публикаций, файлов удалённых сервисов или неизвестных приложению действий.

## 11. Пределы и стоимость

| Ограничение | Значение |
| --- | --- |
| Основная SQLite-база | Не более 256 MiB после добавления карантина |
| Каждый архив | Не более 256 MiB |
| Число архивов | От 1 до 16 для импортированной среды |
| Совокупный размер архивов | Не более 1 GiB |
| Частный manifest | Не более 64 KiB |
| Intent | Ограниченный частный JSON, не более 4000 байт |
| Время полной операции | Общий срок 60 секунд |

Проверка и копирование требуют чтения основной базы и всей архивной цепочки. Время и необходимый объём растут с размером комплекта. Протокол не вводит дедупликацию архивов между разными backup и не передаёт только изменённые страницы.

Эти пределы ограничивают принимаемый ввод. Они не являются измерением пропускной способности, числа одновременно работающих агентов или гарантированного времени сохранения любого допустимого комплекта на произвольном носителе.

## 12. Совместимость и демонстрационный сценарий

Прежний `store-backup` продолжает проверять формат одной базы с точным составом из трёх файлов. Полный workspace bundle содержит дополнительные метаданные и `archives`, поэтому проверяется новым `workspace-backup`. Ослабление старой проверки состава каталогов для нового формата не требуется.

Обычный Store использует прежний quarantine marker основной базы. Восстановление не требует изменения dependency records или переписывания исторических путей origin.

Прикладной сценарий начинает с двух последовательно выполненных переносов. Затем сохраняет полную рабочую среду, сопоставляет снимок с последующей работой источника, восстанавливает копию и проверяет историческое чтение при недоступных прежних путях. Фактические ревизии, число файлов, исходы команд и границы выполненного сохраняются отдельно в [отчёте запуска](../../examples/workspace-backup/results/workspace-report.md).

~~~sh
python3 -m agentwiki workspace-backup-demo \
  --workspace /tmp/agentwiki-workspace-backup-01 --workers 3
~~~

Программируемые роли в этом примере не доказывают независимость людей или истинность содержания. Проверка архивной цепочки подтверждает согласованность сохранённых локальных оснований. Предметная полнота зависимостей, семантическая точность документации и польза рассмотрения требуют отдельной оценки.

## 13. Дальнейшая работа

Следующие инженерные задачи — ограниченное восстановление частичных комплектов, политика хранения и удаления проверенных архивов, наблюдаемость объёма и работа с внешним хранилищем. Продолжение операции должно распознавать её собственные файлы и сохранять запрет перезаписи неподтверждённых данных.

Для промышленного переключения также нужны внешний доверенный выбор действующего источника, маршрутизация, правила восстановления полномочий и согласование уже выполненных внешних эффектов. SQLite, Git и удалённая публикация не образуют одну транзакцию. Старые программы и прямой SQL владельца остаются за границей кооперативных проверок Store.
