# Перенос остановленного источника в новую рабочую среду

Статус: двадцать второй этап локального прототипа, правила `source-transfer-1`. Перенос создаёт отдельную рабочую базу с новым администратором и новыми полномочиями. Прежний источник сохраняет постоянную source fence, а карантинные снимки продолжают открываться для чтения.

Продолжение в версии 0.23.0: [цепочка повторных переносов](source-transfer-chain.md) сохраняет все предковые архивы в новом назначении. Описанное ниже ограничение одним переходом относится к первоначальному двадцать второму этапу; его сохранённые результаты остаются прежними.

- [Предыдущий этап: остановка исходной среды](source-fence.md).
- [Сверка и частные планы восстановления](recovery-reconciliation.md).
- [Прикладной сценарий](../../examples/source-transfer/README.md).
- [Фактический отчёт запуска](../../examples/source-transfer/results/transfer-report.md).

## 1. Решение и его назначение

После остановки источника его актуальные принятые материалы можно использовать как основание новой работы. Источник также содержит старые допуски, аренды, предложения, решения и идентификаторы операций. Перенос должен сохранить возможность объяснить историю и зависимости содержания, а действующие полномочия оформить заново.

Для этого создаются две базы назначения:

- Частный архив всей логической базы источника после закрепления переноса. Он сохраняет source fence и остаётся доступным для исторического чтения.
- Новая рабочая база с sources, текущими принятыми artifacts, импортной ревизией и закреплёнными зависимостями. В её активных таблицах отсутствуют прежние grants, leases, proposals, decisions и operations.

Изначально в новой рабочей базе есть только новый административный допуск. Остальные роли выдаются явно; задания и authenticated leases создаются заново.

Этот этап поддерживает один переход из исходного Store. Источник с уже сохранённым `__transfer_origin__` отклоняется до новой reservation: цепочка повторных переносов требует отдельного договора сохранения архивов предков и запретов старых credentials.

### 1.1. Почему нужен специальный импорт зависимостей

Обычный `Store.bootstrap()` создаёт начальную ревизию без предложения. Механизм `_dependencies()` при таком основании возвращает пустые read/query зависимости. Простой импорт текущих текстов потерял бы объявленные условия, на которых они были приняты, и ослабил бы последующие проверки публикации.

Перенос сохраняет исходные записи зависимостей с привязкой к каждому импортированному артефакту. Проверки `stale_accepted_read` и `stale_accepted_query` продолжают использовать эти основания. Наличие сохранённой зависимости подтверждает её происхождение внутри доверенной базы; достаточность выбранных зависимостей для смысла документа остаётся предметом рассмотрения.

### 1.2. Почему требуется единственное назначение

Один остановленный источник мог бы стать основанием нескольких активных копий. Поэтому источник закрепляет одно назначение: канонический абсолютный путь, новый workspace ID, operation ID и привязку нового административного секрета.

Обычный Store в источнике по-прежнему блокирует запись. Закрепление переноса выполняется отдельным узким методом управления, который добавляет зарезервированную запись `__source_transfer__` и одно событие. Source fence и её квитанция сохраняются.

## 2. Граница доверия

Протокол рассчитан на участников, использующих обновлённый Store и согласованные локальные пути SQLite. Владелец файлов, реализация приложения и часы остаются доверенными. Старые версии программы и прямой SQL способны обойти проверки приложения.

Source fence, transfer ID и workspace ID являются локальными сохранёнными фактами. Они не предоставляют внешний арбитраж, глобальную монотонность или распределённую гарантию единственного писателя. Проверка административного credential подтверждает владение локальным допуском, без удостоверения личности человека или независимости участников.

Источник должен быть доступен для проверки текущего административного допуска и существующей source fence. Старый карантинный snapshot не содержит поздних отзывов и выполненных операций и не заменяет этот вход.

## 3. Частные данные и публичный результат

### 3.1. Привязка в источнике

Зарезервированная source transfer запись содержит частную привязку точного запроса и безопасную квитанцию. Привязка включает существующий источник, его fence, назначение, нового администратора, хеш нового секрета и operation ID.

Request digest, хеши credentials и весь частный envelope не включаются в события, CLI, отчёты или Git. Публичное событие содержит только безопасную квитанцию переноса. Другой путь, operation ID или вход нового администратора не переоформляет существующую привязку.

### 3.2. Каталог назначения

Частный каталог назначения содержит:

| Файл | Назначение |
| --- | --- |
| `.agentwiki-transfer-intent.json` | Намерение конкретной операции, записанное первым |
| `state.sqlite3` | Новая рабочая база с импортным основанием и свежими полномочиями |
| `history.sqlite3` | Согласованный архив полной истории остановленного источника |
| `.agentwiki-transfer-manifest.json` | Завершение файловой части операции, записанное последним |
| `.agentwiki-transfer.lock` | Частная POSIX-блокировка материализации одного назначения |

Каталог имеет права 0700, частные файлы — 0600. Credentials хранятся отдельно в частных файлах. В manifest используются частные размеры, контрольные суммы и привязки; он не становится публичным отчётом.

Завершённый активный Store требует сохранения `history.sqlite3` в этом же каноническом каталоге. Утрата архива, нарушение частных прав или несоответствие закреплённого размера вызывают отказ обычного открытия; удалять архив после создания рабочей базы нельзя.

Новая рабочая база после начала работы изменяется. Контрольная сумма её начального файла относится к завершению импорта; она не является неизменной контрольной суммой будущих записей. Runtime проверяет структуру, идентичность и привязку пути завершённого переноса, сохраняя возможность обычной последующей работы.

### 3.3. Публичная квитанция

Безопасная квитанция описывает локальные идентификаторы операции и рабочей среды, исходную source fence, импортную ревизию, границу событий и количество перенесённых материалов. В ней нет частного envelope, абсолютных служебных путей, credential hashes, denylist или checksum базы.

| Группа квитанции | Поля |
| --- | --- |
| Формат | `schema_version`, `rules_version` |
| Идентификаторы | `transfer_id`, `workspace_id`, `operation_id`, `source_fence_id`, `source_epoch` |
| Основание | `created_at`, `source_revision`, `source_event_high_water_before`, `transfer_event_seq` |
| Материалы и новый principal | `artifact_count`, `source_count`, `new_administrator_id` |
| Границы | `dependencies_preserved=true`, `old_authority_transferred=false`, `external_fencing_established=false` |

Ответ операции также показывает режимы, активированные в новой базе при импорте, и признаки повторного вызова или продолжения собственной незавершённой попытки. Импортная ревизия в таком ответе относится к сохранённому факту переноса. Позднейшие принятия в рабочей базе имеют собственные ревизии.

Внешний report содержит `rules_version`, `receipt`, `destination`, `replayed`, `resumed` и три флага границ. В `destination` сохранены `workspace_id`, импортная `revision`, `artifact_count`, `source_count` и признаки включения governance, authorship, content и continuity при импорте. `transfer_status` возвращает тот же исторический report с `replayed=true` и `resumed=false`; текущее содержимое рабочей базы читается отдельно через Store.

## 4. Закрепление единственного назначения

Входы `transfer_source` — существующая база источника, каталог назначения, действующий credential исходного администратора, новый административный principal, новый credential и operation ID.

Основная последовательность:

1. Проверить пути, частные права, идентификаторы и существующий поддерживаемый источник. Карантинная копия не используется как действующий источник переноса.
2. Получить `BEGIN IMMEDIATE` в источнике и проверить его source fence.
3. Проверить по исходной базе и текущим часам административный допуск, которым оформлена source fence. Его grant ID должен совпадать с сохранённым в fence.
4. Проверить новый административный credential: он должен отличаться от всех credentials, когда-либо зарегистрированных в grants источника.
5. Проверить существующую transfer reservation. Точный исходный запрос может продолжаться; иной запрос конфликтует.
6. При первой операции атомарно записать постоянную привязку назначения и безопасное событие переноса.
7. Сохранить частный intent и подготовить назначение по этому же запросу.

Это специальная операция управления переходом. Она не снимает source fence и не разрешает обычные `Store.write=True`, публикацию, возврат старых аренд или новые доменные операции в источнике.

SQLite источника и файловая система назначения не образуют общую атомарную систему. После сохранения reservation может остаться частная незавершённая попытка. Она принадлежит одному запросу и одному назначению; перенос на другой путь автоматически не разрешается.

## 5. Архив исходной истории

Native SQLite backup захватывает источник после сохранения reservation. Поэтому архив включает прежнюю историю, source fence и запись переноса, а также старые grants, revocations, leases, proposals, decisions и receipts.

Архив завершается как отдельная база `DELETE`, без зависимости от внешнего WAL. Его встроенная source fence сохраняется, и обычный Store открывает его для чтения. Карантин прежних snapshot также продолжает действовать.

Согласованный SQLite backup учитывает подтверждённое логическое состояние источника. Произвольное копирование одного main-файла действующего WAL-источника не заменяет эту процедуру.

Исторические proposal IDs и решения новой импортной карты разрешаются в контексте архива происхождения. Они не обозначают новые действующие предложения или голоса рабочей базы.

### 5.1. Граница последующих backup новой базы

Существующий формат `store-backup` сохраняет одну SQLite-базу. Backup новой рабочей среды включает её текущее содержание, импортные dependency records и собственную новую SQL-историю. Внешний `history.sqlite3` со всей прежней историей источника в такой bundle не включается.

Восстановленная карантинная копия этой базы доступна для чтения в пределах сохранённого SQL-состояния. Полная история до переноса требует отдельного сохранения частного `history.sqlite3`. Сам перенос создаёт этот архив; последующие DB-only backup не следует объявлять полным архивом перехода.

## 6. Импорт принятого содержания и зависимостей

### 6.1. Импортная ревизия

Пусть текущая ревизия источника равна `R`. Новая база получает импортную ревизию `R` с актуальным принятым состоянием. Каждая импортированная строка artifacts закрепляется за этим импортным основанием.

Так сохраняется совместимость существующего выпуска schema 2: исходная `baseline_revision` в записи зависимости не превышает ревизию нового выпуска. Создание ревизии 1 с необработанными зависимостями ревизии 2 нарушило бы этот договор.

Архив источника содержит прежние промежуточные ревизии и предложения. Активная база содержит импортное основание и дальнейшие новые ревизии; её журнал не выдаётся за полный прежний runtime-журнал.

### 6.2. Карта импортного происхождения

В зарезервированном `__transfer_origin__` сохраняется ограниченная карта anchors:

| Часть anchor | Назначение |
| --- | --- |
| ID артефакта | Точная импортированная запись |
| Digest артефакта | Привязка к принятому содержимому |
| Dependency record | Исходные пять полей зависимости |

Сохраняются `proposal_id`, `baseline_revision`, `readset`, `queries` и `write_ids`. Формат записи выпуска не расширяется служебными полями происхождения. Данные о рабочей среде, архиве и импорте хранятся отдельно.

`Store._dependencies()` использует импортный record для неизменённого baseline-артефакта только при совпадении ID, digest и импортной ревизии. Нарушение привязки вызывает отказ; пустые read/query зависимости автоматически не подставляются.

После нового принятия артефакт имеет локальное предложение и новую ревизию. Для него используется обычный SQL-путь вычисления зависимостей после принятия. Остальные неизменённые импортированные артефакты сохраняют свои anchors.

### 6.3. Значение сохранённого provenance

Точные зависимости позволяют продолжить формальные проверки актуальности при публикации. Они не доказывают полноту предметной описи, истинность документации, независимость reviewers или поведение предлагаемой программы. Предложенный Python остаётся данными и автоматически не исполняется.

## 7. Свежие полномочия и режимы защиты

В новой базе переносятся конфигурации текущих правил governance, authorship, content и continuity в пределах режимов, включённых в источнике. Их активации оформляются заново новым администратором до завершения импорта.

Сначала действующим является только новый административный grant. Старые author/reviewer/coordinator grants, их leases, решения и operation IDs в активные таблицы назначения не копируются. Старые принятые receipts остаются историческими фактами в архиве.

Для продолжения работы новый администратор явно выдаёт необходимые роли. Авторы получают новые задания и authenticated leases; новые предложения проходят текущие формальные проверки, рассмотрение, content gate и новое принятие. Старые мнения не предоставляют кворум новому предложению.

Частный origin содержит denylist прежних credential hashes. Он используется для отклонения попытки зарегистрировать старый секрет как новый grant. Это запрещает повторное использование прежних секретов в предусмотренном пути выдачи полномочий; сам denylist не является действующим допуском.

Сроки новых grants и leases продолжают идти по часам. Сохранённый факт переноса не предоставляет бессрочного права на будущие операции.

## 8. Завершение и продолжение собственной попытки

В новой базе сохраняется постоянная READY-метка происхождения. Для обычной работы Store одновременно требует корректную метку, комплект завершения и совпадение канонического пути назначения.

Частный origin хранит transfer/workspace IDs, канонические source/destination/history paths, импортную ревизию, anchors, denylist прежних credential hashes, request digest, новый административный grant и `ready=true`. Публичный `snapshot_access` показывает лишь безопасное происхождение: локальные IDs, импортную ревизию, grant ID и флаги сохранения зависимостей и привязки пути.

Intent появляется до создания рабочей базы; manifest — после подготовки и проверки файлов. Наличие одной SQLite-базы без завершения не разрешает bootstrap или запись. Копия рабочего файла по другому пути также не становится вторым действующим назначением.

При повторе того же запроса протокол различает завершённый результат и принадлежащую ему незавершённую попытку. Завершённый результат возвращает прежний факт переноса. Продолжение собственной попытки сохраняет исходную reservation и не создаёт дополнительное событие источника. Несвязанные существующие файлы не перезаписываются.

Материализация и завершение одного назначения удерживают POSIX `flock` частного lock-файла. Параллельные повторы одного запроса не должны одновременно писать history, рабочую базу и manifest. Ожидание этой блокировки входит в общий срок операции; это локальная файловая координация, без внешней распределённой блокировки.

Поддерживаемое продолжение требует собственного канонического intent. Оно охватывает пустые SQLite-файлы, файл с полностью откатившейся пустой схемой, уже проверенный архив и готовую импортную базу без финального manifest. Непустой повреждённый или неподдерживаемый файл автоматически не заменяется.

Если процесс остановился между созданием каталога и сохранением intent, может остаться закреплённое в источнике назначение без достаточных файлов владения. Такой остаток блокируется; автоматического усыновления каталога или переноса reservation на другой путь нет. Его разбор требует отдельного действия оператора вне этого API. Протокол не заявляет восстановление после всех точек падения или отказов оборудования.

После начала обычной работы назначения точный повтор переноса не сбрасывает его очередь, grants, новые предложения или принятые ревизии. Ответ по-прежнему описывает исходный импорт, а текущее состояние читается обычными API рабочей базы.

Исторические базы с quarantine или source fence получают прежний приоритет режима чтения. Привязка активного назначения не должна запрещать осмотр согласованного исторического архива по его отдельному пути.

## 9. CLI и Python API

Python API:

~~~python
transfer_source(
    database_path,
    destination,
    credential=source_administrator_credential,
    new_administrator_id="recovery-administrator",
    new_credential=new_administrator_credential,
    operation_id="source-transfer-01",
)
transfer_status(destination)
~~~

Команда создания:

~~~sh
python3 -m agentwiki store-transfer create \
  --workspace /tmp/my-source/private/source \
  --destination /tmp/my-source/private/new-workspace \
  --credential /tmp/my-source/private/admin.credential \
  --new-administrator recovery-administrator \
  --new-credential /tmp/my-source/private/new-admin.credential \
  --operation-id source-transfer-01
~~~

Чтение результата:

~~~sh
python3 -m agentwiki store-transfer status \
  --workspace /tmp/my-source/private/new-workspace
~~~

Новый credential предварительно сохраняется в отдельный частный файл с правами 0600. CLI читает оба credentials из файлов и не печатает секреты. Публичный ответ проверяется точными allowlists; source/destination paths, частные manifest, denylist и request digests остаются внутри частной части протокола.

`create`, включая точный повтор, требует доступного источника и по-прежнему действующего исходного административного допуска. `status` читает готовое назначение и его частный архив; он не обращается к исходной базе и не выдаёт новых полномочий.

Команды не инициализируют источник обычным Store-конструктором. Завершение новой рабочей базы выполняется доверенным импортным путём до допуска обычных операций Store.

## 10. Ограничения и ошибки

Обход существующего источника сохраняет пределы предшествующих этапов: база до 256 MiB, строка до 4 MiB, до 100 000 строк с `sqlite_sequence` и общий срок отдельной операции 60 секунд. Типы и размеры проверяются до загрузки ограничиваемых тел.

| Ограничение метаданных | Значение |
| --- | ---: |
| Origin JSON в новой базе | До 1 MiB |
| Intent | До 4000 байт |
| Manifest и source reservation JSON | До 64 KiB каждый |
| Суммарные сериализованные dependency records при импорте | До 512 KiB |
| Artifact anchors | До 10 000 |
| Hashes прежних credentials в denylist | До 10 000 |
| Канонический служебный путь | До 4096 байт UTF-8 |

Превышение поддерживаемой структуры должно завершаться отказом, без снятия защиты или сокращения зависимостей. Runtime guard не накладывает на дальнейший рост активной базы начальный предел размера импорта. Он проверяет частный файл базы, неизменяемую идентичность завершения и наличие архива с закреплённым размером. Полная контрольная сумма истории не пересчитывается при каждой обычной транзакции Store.

Основные причины отказа: неподдерживаемый или неостановленный источник, недействующий исходный администратор, повторное использование прежнего credential, иной запрос существующей reservation, несвязанный каталог назначения, незавершённый или повреждённый комплект, несовпадение origin path или anchors, превышение срока либо объёма.

| Код API | Причина |
| --- | --- |
| `source_transfer_invalid_input` | Неподдерживаемый идентификатор или входной путь |
| `source_transfer_source_invalid` | Неподдерживаемый, неостановленный или уже импортированный источник |
| `source_transfer_credential_reused` | Новый административный secret уже использовался в исходных grants |
| `source_transfer_conflict` | Источник закреплён за другим точным запросом либо администратор не совпадает с допуском source fence |
| `source_transfer_destination_exists` | Существующее назначение не принадлежит этому intent либо содержит неподдерживаемые данные |
| `source_transfer_incomplete` | Нет необходимого файла завершённого назначения |
| `source_transfer_manifest_invalid` | Reservation, receipt или completion metadata не проходят проверку |
| `source_transfer_checksum_mismatch` | Частный архив истории расходится с сохранённой checksum |
| `source_transfer_limit_exceeded` | Превышен срок или поддерживаемый объём |
| `source_transfer_io_failed` | Обработка или ввод-вывод не завершились успешно |

Ранние проверки Store используют `store_transfer_incomplete` при отсутствии завершения и `store_transfer_invalid` при несовместимой метке, пути или структуре. Попытка выдать новый grant со старым секретом получает `governance_credential_conflict`. CLI дополнительно использует `unknown_source_transfer_command`, `source_transfer_summary_invalid` и безопасный общий отказ `source_transfer_command_failed`.

Эти ограничения относятся к одному локальному инструменту. Они не являются измерением производительности, гарантией восстановления после любого отказа оборудования или сравнением числа независимых агентов.

## 11. Прикладной сценарий

Демонстратор начинает с остановленного источника предыдущего этапа: принятый документ и код, история решений, аудиты, частные планы и сохраняющийся quarantine snapshot. Публичные материалы исходного сценария сохраняются без перезаписи.

Затем создаётся новая рабочая среда с новым администратором. Сопоставляются исходные принятые материалы и зависимости, читается частный архив, наблюдаются отсутствие старых действующих полномочий и точный повтор переноса. Другое назначение и повторное использование прежних credentials должны отклоняться.

Новые author/reviewer/coordinator grants, задания и leases позволяют подготовить и принять новое предложение в назначении. Источник остаётся остановленным; старый snapshot остаётся в карантине. Импортный выпуск должен сохранять совместимость загрузчика и прежние основания проверки публикации.

Фактические счётчики, время, результаты команд и границы выполненного находятся в [отчёте запуска](../../examples/source-transfer/results/transfer-report.md). Документация не выдаёт статический обзор за воспроизведение всех сбоев и расписаний.

Запуск с новым пустым каталогом:

~~~sh
python3 -m agentwiki source-transfer-demo --workspace /tmp/agentwiki-source-transfer-01 --workers 3
~~~

## 12. Дальнейшее развитие

Переход связывает один остановленный источник и одно локальное назначение через предусмотренный API. Для промышленного переключения потребуются внешний доверенный механизм поколений и маршрутизации, правила хранения архивов, доступ участников, наблюдаемость и согласование ранее выполненных внешних эффектов.

Git refs, файлы публикации, удалённые сервисы и SQLite не становятся одной транзакцией. Каждое внешнее действие требует собственного идентификатора, условного применения и процедуры восстановления результата. Отсутствие исходного источника также требует внешних доверенных сведений о поздних отзывах и уже выполненных операциях.
