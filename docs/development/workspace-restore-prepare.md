# Продолжение подготовки восстановления без исходного комплекта

Статус: двадцать седьмой этап локального прототипа. Команда `workspace-restore resume-prepare` продолжает только подготовку метаданных точного сохранённого задания. Она использует прежний план и не требует доступности исходного bundle.

**Обычный development-запуск успешно завершён 21 октября 2026 года.** Девять workers достигли фиксированных границ и завершились от SIGKILL. Шесть заданий продолжили подготовку без source, три остались блокирующими. Независимые сверки публичных результатов, частных артефактов и приватности публикации также завершены успешно. Основания и границы приведены в разделе 13.

## 1. Какой промежуток рассматривается

Прежний restore job закрепляет запрос до переноса основной DB и архивов. Подготовка тоже состоит из нескольких файловых действий: создание каталога задания, запись плана, создание назначения, установка первого snapshot intent и запись owner record.

Остановка между этими действиями отличается от остановки при копировании DB. После одних границ уже достаточно сведений для безопасного продолжения метаданных. После других остаётся неполная запись либо каталог без доказанной принадлежности.

Новый вызов делает это различие операционным: он продолжает только распознаваемую подготовку собственного задания. Неизвестный каталог, частичный plan или непроверяемый owner не превращаются в новую восстановительную операцию.

## 2. Identity должна пережить вызывающий процесс

Сохранённый план связывает job ID, operation ID, исходный manifest, назначение, будущий restore manifest и фиксированное время результата. Это долговечное описание одной операции. Новому caller не требуется придумывать новую identity после смерти прежнего процесса.

Наличие подходящих bytes ещё не доказывает, что каталог создало это задание. Поэтому owner record отдельно связывает план с устройством и inode назначения, созданного собственным exclusive mkdir. Похожие metadata, время либо имя каталога не заменяют это доказательство.

Метаданные перед данными обеспечивают следующие границы:

| Граница | Основание |
| --- | --- |
| Что именно требуется восстановить | Корректный неизменяемый план и закреплённый запрос |
| Какой каталог принадлежит операции | Собственный mkdir и точный постоянный owner record |
| Почему отсутствующая DB не должна инициализироваться как активная | Первый стандартный snapshot intent в назначении |
| Какие bytes принимаются позже | Проверки каждого файла по плану и проверка полного исторического комплекта |

Долговечность здесь относится к предусмотренным локальным файловым действиям и синхронизации. Этот этап не устанавливает сохранность при отказе питания, ядра, контроллера или носителя.

## 3. Новый API и обычная CLI

Программный интерфейс:

~~~python
resume_preparation(job_directory)
~~~

Обычная команда:

~~~sh
python3 -m agentwiki workspace-restore resume-prepare \
  --job /tmp/agentwiki-private/restore-job
~~~

Она принимает только уже выбранный каталог задания. Параметры исходного bundle, назначения и operation ID берутся из проверенного плана; переопределить их этим вызовом нельзя.

Ответ сохраняет прежние 15 публичных полей restore job. Новый вид status, публичный частный план либо отдельная диагностическая команда не добавляются. До переноса данных обычный результат остаётся `prepared`, `copied_file_count=0`, `completed=false`, `result=null`.

`prepared/0` может обозначать как корректный plan без ещё созданного target, так и полностью готовые подготовительные metadata. Новое диагностическое состояние не вводится. Фактическое продвижение подготовки устанавливается по проверенной файловой топологии, а не по изменению счётчика данных.

Схемы private plan/owner и правила `workspace-restore-job-1` сохраняются. Новый вызов имеет прежний срок 60 секунд; plan ограничен 256 KiB, owner — 8 KiB. Частные каталоги требуют 0700, файлы — 0600; job и target остаются соседями с общим частным родительским каталогом.

`prepare` при точном повторе и `status` остаются наблюдением сохранённого задания. Они не выполняют новое восстановление метаданных вместо `resume-prepare`.

## 4. Проверка до любого изменения

Вызов получает прежний flock задания, читает корректный план и выполняет обычную проверку status. Только после этого рассматривается продолжение подготовки.

Проверка сохраняет действующие ограничения: частные пути и права, состав задания, принадлежность назначения, стандартный intent, предусмотренные имена staging и точные уже установленные файлы.

| Наблюдённое состояние | Разрешённое поведение |
| --- | --- |
| Корректный plan, нет owner и нет target | Создать собственное новое назначение и подготовить метаданные |
| Корректный plan, точный owner и первый стандартный intent | Продолжить только разрешённые метаданные подготовки |
| Уже подтверждён хотя бы один файл данных | Вернуть тот же проверенный status без изменения файлов |
| Завершённый bundle | Вернуть тот же completed status без нового времени и записи |
| Partial plan, partial owner или target без точного owner | Отказать без усыновления или исправления неподтверждённого остатка |

Существующий target без owner не становится своим даже при подходящем первом intent. Owner при исчезнувшем либо заменённом target также не разрешает создать каталог заново.

## 5. Что означает «только метаданные»

Индексы подготовительных файлов следуют прежнему плану:

| Индекс | Файл назначения |
| ---: | --- |
| 0 | `.agentwiki-snapshot-intent.json` |
| 1 | `.agentwiki-workspace-intent.json` |
| 2 | `.agentwiki-snapshot-manifest.json` |

Продолжение может установить эти записи и подготовить каталог `archives/`. При собственном создании назначения owner record сохраняется прежним порядком: exclusive mkdir, первый стандартный intent, затем owner.

Файлы основной DB и архивов не копируются, не заменяются и не удаляются. Общий `.agentwiki-workspace-manifest.json` также не создаётся: он обозначает завершение полного комплекта после проверки данных.

Собственный staging с одной ссылкой для индексов 0–2 можно пересоздать. Доказанная пара staging/target этих метаданных допускает удаление только собственного промежуточного имени. Правила no-overwrite сохраняются: уже установленное несовпадающее содержимое не заменяется.

Data staging не входит в этот ремонт. Его наличие не является причиной очистить весь каталог задания либо заранее продолжить копирование DB.

## 6. Независимость от источника и граница чтения данных

Подготовительные JSON bodies уже определены неизменяемым планом. Поэтому `resume-prepare` не открывает исходный bundle и не требует его наличия по прежнему пути.

Это позволяет завершить metadata preparation после смерти прежнего caller, даже если источник временно недоступен. Полнота плана при этом обязательна: отсутствующие либо частичные параметры не восстанавливаются догадкой из неполного назначения.

Утверждение «только метаданные» относится к изменениям. Первоначальная обычная проверка status может читать и хешировать уже установленные data files, а для завершённого комплекта выполнять исторические SQL-проверки в режиме чтения. При `copied_file_count>0` вызов возвращает проверенный status без изменений.

Для пути `prepared/0` продолжение не читает содержимое data staging и не переносит его bytes. Подготовленный target всё ещё не содержит основной DB; последующему обычному step для копирования недостающих данных снова нужен полный проверенный source bundle.

## 7. Девять фиксированных development-случаев

Сценарий использует отдельные новые задания. Первые восемь границ относятся к подготовке; девятая использует прежнюю data boundary, чтобы показать точный предел нового ремонта.

| Случай | Сохранённое состояние | Наблюдённый исход `resume-prepare` | Worker returncode |
| --- | --- | --- | ---: |
| `plan_partial` | Непустой правильный префикс private plan; полного проверяемого запроса ещё нет | `workspace_restore_job_manifest_invalid`; остаток сохранён | `-9` |
| `plan_durable` | Полный план сохранён; target и owner отсутствуют | Новый собственный target подготовлен без source; `prepared/0` | `-9` |
| `intent_durable` | Первый стандартный intent установлен; owner ещё отсутствует | `workspace_restore_job_conflict`; назначение не усыновлено | `-9` |
| `owner_partial` | Первый intent есть; owner записан частично | `workspace_restore_job_manifest_invalid`; partial owner не достроен | `-9` |
| `owner_durable` | Полный owner закреплён; оставшиеся metadata ещё не подготовлены | Метаданные подготовлены без source; `prepared/0` | `-9` |
| `metadata_partial` | Частичный собственный staging workspace intent, индекс 1 | Metadata staging пересоздан без source; `prepared/0` | `-9` |
| `metadata_linked` | Точная пара staging/target workspace intent, индекс 1 | Собственный metadata alias удалён без source; `prepared/0` | `-9` |
| `preparation_ready` | Все подготовительные metadata готовы; данных ещё нет | Стабильный `prepared/0` без source | `-9` |
| `data_staging_preserved` | После готовой подготовки остался частичный DB staging, индекс 3 | `prepared/0` без source; data staging metadata сохранены | `-9` |

Наблюдены шесть положительных случаев и три блокирующих, как предусмотрено контрактом. Во всех девяти случаях подтверждены acknowledgement, живой worker перед сигналом и завершение от SIGKILL с returncode `-9`. Основания: [девять случаев](../../examples/workspace-restore-prepare/results/restore-prepare-cases.json) и [workers](../../examples/workspace-restore-prepare/results/restore-prepare-worker-outcomes.json).

В шести положительных случаях источник временно убран на время readonly prepare/status, `resume-prepare` и его повтора. После вызовов подтверждены metadata-ready, отсутствие основной DB, файлов архивных данных и общего manifest. Status остаётся `prepared/0`; полноту метаданных подтверждает отдельное наблюдение топологии.

Для девятого случая lstat-метаданные data staging до и после metadata resume совпали: устройство/inode, размер, права, UID, число ссылок и mtime/ctime остались прежними. Содержимое staging демонстратор не читал. Эти сведения подтверждают неизменность наблюдённых метаданных и identity; отдельная побайтная идентичность cache на их основании не заявляется.

Исходный путь возвращён в finally. Затем обычный step перенёс три файла данных каждого положительного случая — DB и два архива — и завершил прежний формат полного bundle. Три блокирующих остатка сохранились; prepare, status, step и resume-prepare отказали без ручного исправления.

## 8. Как создаётся прерывание

В production-коде остаётся частный no-op `_checkpoint`. Восемь новых фиксированных names: `plan_partial`, `plan_durable`, `intent_durable`, `owner_partial`, `owner_durable`, `metadata_partial`, `metadata_linked`, `preparation_ready`.

Для plan/owner partial boundary записывается правильный непустой префикс, затем выполняются flush и fsync. `metadata_partial` относится только к workspace intent с индексом 1. `metadata_linked` расположен после link и синхронизации каталога назначения, перед удалением промежуточного имени.

Доверенный development worker выбирает только предусмотренную границу. Для девятого случая он сопоставляет прежнюю `staging_partial` основной DB с публичным именем случая `data_staging_preserved`.

Его acknowledgement имеет ровно три поля:

| Поле | Значение |
| --- | --- |
| `rules_version` | `workspace-restore-prepare-1` |
| `boundary` | Один из девяти фиксированных случаев |
| `checkpoint_reached` | `true` |

После flush worker ожидает сигнал. Родитель проверяет точное acknowledgement и живой собственный child, посылает ему SIGKILL и ожидает reap. Обычные CLI вызываются уже после смерти worker и освобождения его flock операционной системой.

Ожидание acknowledgement ограничено 60 секундами и 4096 bytes; ожидание завершения child после kill — 15 секундами. Отдельный alarm worker на 90 секунд ограничивает его жизнь при исчезновении parent. Срабатывание alarm не считается успешным SIGKILL-случаем.

Public API/CLI и переменные среды не получают fault callbacks, произвольные пути для аварийной записи либо выбор исполняемого кода. Частный development hook не является форматом запроса агента.

## 9. Status наблюдает, resume-prepare изменяет

Неизменность status важна для разбора прерывания. Чтение не должно удалять partial staging, дописывать owner либо скрывать состояние, которое требуется наблюдать.

`resume-prepare` — явное действие над распознанным собственным заданием. Его область уже, чем у обычного step: он продолжает только подготовку и может работать без источника. Обычный step остаётся действием переноса данных и полного завершения.

Ошибку проверки нельзя трактовать как приглашение удалить остаток. В частности, повреждённый plan не сообщает достоверное назначение, а первый intent не доказывает, что операция успела сохранить свой owner.

## 10. Связь с несколькими агентами

Несколько callers могут обращаться к одной операции последовательно или конкурировать за её flock. Число процессов не меняет job ID, operation ID, фиксированный timestamp либо число логически установленных файлов.

После смерти worker новый caller получает блокировку и использует долговечное основание. Он не наследует полномочия прежнего процесса из самого факта продолжения; принадлежность определяется проверенными локальными файлами задания.

Отдельная команда подготовки позволяет агенту восстановления закончить инфраструктурную часть, не требуя source и не принимая новый документ или программную правку. Это локальный файловый протокол. Его результат не устанавливает истинность содержания, независимость LLM, распределённый consensus или ёмкость системы по числу агентов.

## 11. Карантин и неподдерживаемые ранние окна

Первый стандартный intent должен предшествовать остальным файлам назначения. До установки DB он запрещает инициализировать её как новую активную базу; установленная затем DB уже содержит постоянный quarantine marker.

Окно после target mkdir, но до первого intent остаётся неподдерживаемым. В этом состоянии ещё нет snapshot-barrier. Development-сценарий не открывает там Store и не выдаёт существование пустого каталога за гарантированно защищённое восстановление.

Каталог задания до достаточного plan, частичные control records, неизвестные имена, заменённое назначение и target без owner остаются блокирующими. У данного этапа нет обещания универсального crash repair либо принятия старых неполных одношаговых restores.

Готовый результат сохраняет прежние шесть записей bundle; plan, owner, lock и staging остаются снаружи. Исторические grants/leases не активируются, действующая среда и её поздние отзывы сохраняют собственное текущее состояние.

## 12. Воспроизведение

Из корня существующего checkout нужен новый workspace:

~~~sh
python3 -m agentwiki workspace-restore-prepare-demo \
  --workspace /tmp/agentwiki-restore-prepare-01 --workers 3
~~~

Продолжение сохранённого задания выполняется обычными командами:

~~~sh
python3 -m agentwiki workspace-restore status \
  --job /tmp/agentwiki-private/restore-job

python3 -m agentwiki workspace-restore resume-prepare \
  --job /tmp/agentwiki-private/restore-job

python3 -m agentwiki workspace-restore step \
  --job /tmp/agentwiki-private/restore-job --limit 16
~~~

Нужны Python 3.10+, POSIX private permissions, flock, hard links и сигналы процессов. После закрепления корректного плана источник снова требуется обычному step для переноса недостающих данных; новый metadata-only вызов использует plan и target.

После запуска выполнены отдельные независимые сверки:

- Публичная сверка выполнила 480 сравнений содержимого, схем, идентичности, топологии, маркеров и ссылок и сопоставила все 269 экспортированных файлов с сохранёнными копиями. Все 749 сравнений прошли без расхождений. Изменяемое верхнее `governance.observed_at` исключается из сравнения Store-наблюдений; адресованные основания, timestamps и expired-признаки сохраняются.
- Частная проверка root обнаружила 16 файлов плана: 15 корректных и один намеренно неполный. Проверены 13 завершённых комплектов с 39 файлами данных и три блокирующих задания. Для проверяемых записей сверены канонические метаданные, привязка запроса, owner/назначение, публичная identity и точный состав файлов.
- Для завершённых комплектов подтверждены закреплённые bytes, отсутствие staging, одна ссылка у файлов, тип/UID и точные права 0700/0600, SQLite integrity/foreign keys, постоянный quarantine и полный origin. Все шесть новых результатов сохраняют R4/36 и оба архива; действующая среда остаётся R5/59.
- Частичный owner совпал с первой половиной ожидаемой канонической записи. Частичный plan проверен только как ограниченный частный объект с неполной некорректной формой: полная identity его запроса остаётся недоступной. Этот остаток не использовался как основание для усыновления или восстановления параметров.
- Отдельная проверка полных адресованных пакетов и связей прежних этапов также завершилась успешно. Это проверка сохранности свидетельств и их связей, без утверждения смысловой истинности содержания.
- Privacy-сверка root подтвердила сохранность 2057 прежних материалов и всех 269 экспортированных копий, корректность JSON/Python и отсутствие проверенных значений credentials, private fingerprints и полных/частичных control records в публичных кандидатах. Проверки безопасной формы status/summary и раздельных PID процессов также прошли.

Для чтения SQL при privacy-сверке использован `immutable=1` с условием отсутствующего либо пустого WAL/journal. Уже существующие sidecars старого fenced-источника сохранили наблюдённые metadata; удаления, checkpoint и ремонта этих файлов не выполнялись. Этот read-only разбор не расширяет гарантии самого протокола восстановления.

Частные планы, request digests, owner records, inode, SQL-отпечатки и контрольные суммы не публикуются. Независимые сверки дополняют наблюдения девяти фиксированных точек; полная identity намеренно неполного plan остаётся недоступной и после успешного аудита.

## 14. Ограничения и продолжение

Сценарий рассматривает выбранные локальные точки и фиксированный исторический комплект. Он не перебирает все инструкции, конкурентные расписания, максимальный набор из 17 файлов данных или произвольную подмену файлов владельцем.

Дополнительные flush/fsync правильных префиксов plan, owner и workspace intent меняют объём I/O. Runtime cost и throughput не измерены; дополнительная наблюдаемая граница не описывается как бесплатная.

Следующее расширение должно отдельно определить, какие новые durable facts достаточны для продолжения и какие остатки обязаны остаться блокирующими. Ремонт метаданных не должен превращаться в неявную активацию исторической DB либо в усыновление неизвестного назначения.
