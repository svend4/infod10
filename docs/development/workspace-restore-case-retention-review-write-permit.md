# Локальный допуск к конкретному действию записи review

Статус: тридцать шестой этап локального прототипа. Отдельный permit связывает владение частным credential с одним уже закреплённым действием записи. Его область относится к новому защищённому пути вызова.

- [Действие одной фазы](workspace-restore-case-retention-review-write-action.md).
- [Локальные аренды позиций](workspace-restore-case-retention-review-write-leases.md).
- [Исходная поэтапная запись review](workspace-restore-case-retention-review-write.md).
- [Локальная governance-политика Store](governance.md).
- [Дорожная карта](roadmap.md).

## 1. Какой пробел закрывается

Action предыдущего этапа проверяет точные index, worker, lease ID, поколение и текущую фазу. Worker при этом остаётся строкой запроса. Caller, имеющий доступ к управляющим файлам, может повторить эти публичные идентификаторы; само совпадение не подтверждает владение отдельным секретом.

Permit вводит отдельный локальный допуск для защищённого вызова конкретного action. Проверка credential должна предшествовать возврату защищённого результата, включая уже сохранённый исторический ответ. Это связывает использование данного интерфейса с владением выданным секретом.

Прежние прямые write/action API сохраняют свою область. Получение permit не превращает все существующие пути доступа в обязательную проверку допуска. Владелец файловой системы и процесса остаётся доверенным оператором.

## 2. Разные основания действия

| Основание | Что оно устанавливает |
| --- | --- |
| Каталог write jobs | Явный состав, порядок и исторические descriptors |
| Lease | Последнюю локальную попытку назначения позиции одного ledger |
| Action | Одну исходную и целевую фазу выбранного write intent |
| Permit | Область локального допуска к определённому защищённому вызову |
| Bearer credential | Владение секретом соответствующего допуска в момент проверки |
| Review и его план | Историческое мнение по точному сохранённому основанию |

Эти основания не заменяют друг друга. Действующий credential не обновляет срок lease и не переносит старый action на другое поколение. Допуск к управляющей записи review не даёт права принять предметное изменение, архивировать либо удалить данные.

## 3. Что означает локальная аутентификация

Bearer-модель проверяет, что caller предъявил секрет конкретного локального допуска. Секрет может быть скопирован или передан другому процессу; владение им не устанавливает имя человека, организацию, независимость модели либо автора документа.

Issuer задаёт локальный `principal` для permit. Он обозначает держателя выданного допуска в этом протоколе. Имя worker исходной аренды и actor исторического review остаются отдельными самозаявленными метками. Связь credential с principal и точным action не превращает эти строки во внешне подтверждённую личность.

Выдача локального допуска опирается на доверие к оператору среды. В этом прототипе нет внешнего identity provider, SSO либо доказательства, что разные credentials принадлежат разным людям. Совпадение или различие меток не является предметной экспертизой.

## 4. Точная область permit

Область допуска сохраняет identity уже подготовленного action, его исходную lease и выбранную фазу. Изменение job, claim, поколения либо параметров action требует собственного явного основания. Исторический permit автоматически не распространяется на новое назначение.

Issue может закрепить как prepared, так и уже recorded action. Во втором случае он предоставляет право сегодняшнего обращения к защищённому интерфейсу. Он не удостоверяет, что ранее сохранённую фазу выполнил держатель этого credential или что прежний эффект прошёл такую же проверку.

Частные pins связывают допуск с проверенными controls. Они служат внутренней проверке поддержанного локального протокола. Контрольная сумма не является внешней подписью, удостоверением оператора либо доказательством полноты истории против владельца с прямым доступом к файлам.

## 5. Секреты и публичные наблюдения

Один bearer credential позволяет выполнить защищённый вызов и отозвать собственный permit. Отдельной административной роли этого уровня нет; issuer — доверенный владелец частной файловой среды. Право отзыва чужих permits из владения одним credential не следует.

Credential хранится в отдельном обычном owner-файле `*.credential` с правами 0600 и одной ссылкой, внутри частного родительского каталога 0700. CLI требует прямого соседства этого файла с каталогом permit и отклоняет символьные aliases пути. Секрет не передаётся как буквальное значение аргумента shell, не попадает в stdout, публичные отчёты либо Git. Его хеш также остаётся частным.

Публичная квитанция может назвать identity допуска и его точный предмет, сохраняя явную границу между исторической записью и текущим разрешением вызова. Само наличие такой квитанции не позволяет восстановить credential.

Файл credential и управляющие записи permit не образуют общей транзакции с action либо lease SQLite. Неудача регистрации не должна выдавать частично подготовленный остаток за действующий допуск или давать право перезаписать ранее созданный файл.

## 6. Отзыв и момент допуска

Отзыв сохраняется отдельно от неизменяемой выдачи. Поддержанный API не удаляет этот факт ради повторного включения прежнего permit. Новый самостоятельный допуск имеет собственную identity; он не меняет прежнюю запись отзыва. Другой permit на тот же action проверяется отдельно и не восстанавливает прежний отозванный credential.

Self-revoke требует тот же bearer credential. Точный повтор сохранённого запроса отзыва с тем же operation ID возвращает прежнюю запись после проверки секрета. Другой operation ID конфликтует с уже сохранённым отзывом. Такая историческая квитанция не разрешает выполнить action по отозванному permit.

Точный повтор issue читает собственные controls и возвращает фиксированную квитанцию выдачи, в том числе после отзыва. Он не удаляет marker, не создаёт новый permit ID и не делает прежний допуск действующим.

Проверка permit и отзыв сериализуются собственной локальной блокировкой. Защищённый execute удерживает её на протяжении допущенной операции и сохранения результата. Поэтому другой соблюдающий протокол caller не может вклинить отзыв между проверкой и локальным эффектом.

Если execute уже получил допуск, ожидающий отзыв не отменяет начавшийся файловый шаг. После завершения критической области отзыв блокирует последующие защищённые вызовы. Он не стирает уже сохранённый action result, не отменяет исторический review и не отзывает уже доставленный ответ.

## 7. Исторический результат и защищённый replay

У action имеется собственный исторический результат. Прежний own-only reader может читать его по прежним правилам. Новый защищённый интерфейс отдельно проверяет действующий credential и состояние permit перед выдачей ответа.

Поэтому точный replay через защищённый путь не становится бессрочным разрешением чтения. Отозванный permit должен отказать даже тогда, когда файловый шаг давно завершён и сохранённый action result существует. Новый вызов не создаёт повторный шаг ради восстановления ответа.

Эти правила различают содержание истории и право конкретного обращения к интерфейсу. Отказ защищённого replay не утверждает, что прежний эффект не произошёл. Успешный replay возвращает исторический action result, сохраняя его прежние фазу и время; он не выдаёт новый lease.

Защищённый ответ стабилен: в него не добавляется новое время проверки permit. Поэтому потерянный ответ можно восстановить целиком точно, пока permit действует. При этом каждый новый вызов снова проверяет секрет и отзыв перед чтением сохранённого action result. Булевы признаки проверки относятся к текущему вызову; они не образуют отдельный постоянный журнал аутентификации и не удостоверяют первоначальный файловый эффект.

У permit нет собственного TTL. Для нового исполнения pending action продолжает действовать прежняя проверка его исходной lease. Если action result уже сохранён, активный permit может разрешать его защищённый replay и после освобождения либо истечения этой lease. Такое чтение не возвращает старую аренду в действующее состояние.

Собственный show permit читает metadata без credential. Его active означает отсутствие сохранённого отзыва в наблюдаемой записи. Это не подтверждает владение секретом, текущую lease либо готовность pending action к выполнению.

## 8. Несколько обработчиков

Разные процессы могут предъявлять один credential; это несколько callers одного допуска, а не несколько удостоверенных участников. Отдельные credentials также не доказывают независимость людей либо моделей.

Блокировка permit добавляет собственную критическую область к action, ledger, job и review locks. Её удержание на протяжении файловой фазы позволяет сериализовать отзыв с допущенным выполнением, но увеличивает ожидание других обращений к тому же permit.

Назначения разных jobs в одном ledger по-прежнему могут ожидать общей ledger lock. Объём списка позиций и число созданных permits не являются измерением числа одновременно полезных LLM или пропускной способности редакционного портала.

Для практического масштабирования нужны отдельные измерения времени допуска, ожидания locks, длительности файлового шага, доли повторов и отказов после отзыва. Их следует связывать с полезным предметным результатом при сопоставимом бюджете источников, времени и токенов.

## 9. Содержание документации и права вызова

Permit относится к выполнению управляющего action записи review retention plan. Он не переоценивает сам план и не подтверждает, что actor внимательно прочёл текст. Проверка credential не является `revalidate_review` и не устраняет устаревшее предметное основание.

Для технической вики нужны отдельные источники, полнота предметной описи, связи между затронутыми разделами и политика принятия. Изменение параметра в коде и изменение его описания могут требовать совместного содержательного рассмотрения даже при корректных отдельных permits.

Согласие нескольких программных участников не заменяет независимого оценивания смысла. Локальная аутентификация владения допуском добавляет проверяемую границу интерфейса; истинность и полезность документации требуют собственных оснований.

## 10. Границы сохранности

Общей SQL/filesystem транзакции не появляется. Потеря ответа, сохранённый результат, файловый эффект и состояние отзыва остаются отдельными фактами, которые должны проверяться по своему протоколу.

Неполный bootstrap, частичная управляющая запись и изменённые pins не дают права автоматически усыновить остаток или восстановить недостающую случайную identity. Поддержанный обычный запуск не доказывает обработку всех расписаний прерывания, отказов хранения либо потери питания.

Прямой доступ владельца к controls, старый action execute, write step и независимые копии остаются вне новой проверки. Поэтому локальный permit не является внешним fencing и не устанавливает обязательную политику всей среды.

## 11. API и команды

Программный интерфейс находится в `agentwiki.workspace_restore_case_retention_review_write_permit`:

~~~python
issue_review_write_permit(permit, action, operation_id=operation_id,
                         principal=principal, credential=credential)
inspect_review_write_permit(permit)
revoke_review_write_permit(permit, operation_id=operation_id,
                          credential=credential)
execute_review_write_permit(permit, credential=credential)
~~~

Выдача нового permit по уже подготовленному action:

~~~sh
python3 -m agentwiki workspace-restore-case-retention-review-write-permit issue \
  --permit /tmp/agentwiki-private/permit-fill \
  --action /tmp/agentwiki-private/action-fill \
  --principal local-executor-a --operation-id permit-fill-01 \
  --credential-out /tmp/agentwiki-private/permit-fill.credential
~~~

Родительский каталог должен существовать и быть частным. Новый credential-файл создаётся эксклюзивно и сохраняется до регистрации permit. Если подготовленный секрет уже существует, точный повтор использует `--prepared-credential` вместо `--credential-out`, сохраняя тот же operation ID, principal и action.

Собственное наблюдение и защищённое выполнение:

~~~sh
python3 -m agentwiki workspace-restore-case-retention-review-write-permit show \
  --permit /tmp/agentwiki-private/permit-fill
python3 -m agentwiki workspace-restore-case-retention-review-write-permit execute \
  --permit /tmp/agentwiki-private/permit-fill \
  --credential-file /tmp/agentwiki-private/permit-fill.credential
~~~

Отзыв этого permit тем же credential:

~~~sh
python3 -m agentwiki workspace-restore-case-retention-review-write-permit revoke \
  --permit /tmp/agentwiki-private/permit-fill \
  --operation-id revoke-permit-fill-01 \
  --credential-file /tmp/agentwiki-private/permit-fill.credential
~~~

Operation ID относится к явно выбранному каталогу permit. Глобального реестра уникальности operation ID либо автоматического обнаружения других permits нет. Тот же principal может иметь отдельные допуски; отзыв одного не устанавливает глобальный запрет этого имени.

## 12. Частные управляющие записи

Каталог permit содержит неизменяемый grant, собственный пустой lock и после отзыва отдельный неизменяемый marker. Сохранённые пути, credential hash, pins и digests используются внутри частного протокола; публичная квитанция их не экспортирует.

| Файл | Назначение |
| --- | --- |
| `.agentwiki-restore-case-retention-review-write-permit.json` | Grant13 и точный исторический action |
| `.agentwiki-restore-case-retention-review-write-permit.lock` | Пустой owner-lock для выдачи, чтения, execute и отзыва |
| `.agentwiki-restore-case-retention-review-write-permit.revoked.json` | Revocation7, присутствует только после отзыва |

Точный набор полей grant13: `schema_version`, `rules_version`, `permit_id`, `operation_id`, `created_at`, `permit_path`, `parent`, `permit_directory`, `principal`, `credential_hash`, `action_anchor`, `action`, `request_digest`.

`schema_version=1`, а `rules_version=workspace-restore-case-retention-review-write-permit-1`. `permit_id` имеет форму `wrrwpm_` и 32 шестнадцатеричных символа. `action` — точный прежний public action22, включая исходную lease и пару фаз. Время grant не может предшествовать времени создания action.

`action_anchor4` содержит `action_path`, `action_directory`, `action_intent`, `action_lock`. Полные pins intent и пустого lock проверяются до разбора live action. Новая запись результата action может появиться после выдачи permit; результат не подменяет закреплённый intent и не меняет его предмет.

Точный набор полей revocation7: `schema_version`, `rules_version`, `permit_id`, `operation_id`, `revoked_at`, `grant_digest`, `request_digest`. Marker связан с конкретной выдачей; его время не может предшествовать `created_at` grant. Повтор операции сохраняет прежнее время отзыва.

Записи сохраняются эксклюзивно с fsync. Наличие неполной либо неподдержанной записи останавливает протокол: она не считается отсутствующей и не перезаписывается. Полный канонический digest проверяет целостность поддержанного формата; внешней подписи владельца он не создаёт.

## 13. Публичные ответы

Числа ниже обозначают количество полей на соответствующем верхнем уровне. Вложенный `action` сохраняет прежнюю схему action22, а `action_result` — прежнюю recorded-обёртку18.

| Ответ | Собственные поля сверх общих 16 flags |
| --- | --- |
| Grant22, результат issue | `rules_version`, `permit_id`, `operation_id`, `created_at`, `principal`, `action` |
| Show20, результат show или revoke | `rules_version`, `permit`, `state`, `revocation` |
| Execute22 | `rules_version`, `permit`, `action_result`, `credential_verified`, `revocation_checked`, `historical_effect_authenticated` |

`permit` — grant22. `state` принимает `active` либо `revoked`. При active поле `revocation=null`; при revoked оно содержит revocation5: `rules_version`, `permit_id`, `operation_id`, `revoked_at`, `reason=holder_revoked`. У revocation5 нет дополнительных flags.

Общие flags сохраняют прежние 14: `advisory_only=true`, `inspection_only=true`, `domain_writes_allowed=false`, `original_files_modified=false`, `archival_authorized=false`, `deletion_authorized=false`, `actor_authenticated=false`, `old_authority_activated=false`, `external_fencing_established=false`, `coordination_only=true`, `job_steps_enforced=false`, `same_ledger_only=true`, `worker_authenticated=false`, `lease_required_for_new_execution=true`. Permit добавляет `local_capability_only=true` и `external_identity_verified=false`.

Execute22 требует `credential_verified=true`, `revocation_checked=true`, `historical_effect_authenticated=false`. Вложенный `action_result.action` должен точно совпасть с `permit.action`, а состояние старой обёртки — быть `recorded`. Текущий допуск к выдаче исторической обёртки не меняет её старые flags и не удостоверяет прежнего actor либо worker.

Верхний ответ не содержит нового checked-at. Повтор возвращает тот же полный объект после новой проверки credential и отсутствия marker. Это свойство формата ответа; отдельной durable квитанции каждой успешной аутентификации здесь нет.

## 14. Порядок допуска и пределы

~~~mermaid
flowchart TD
    A[Permit lock] --> B[Own grant и marker]
    B --> C[Bearer совпадает и permit не отозван]
    C --> D[Action lock и captured pins]
    D --> E{Есть saved action result?}
    E -->|Да| F[Историческая recorded-обёртка]
    E -->|Нет| G[Ledger lock и история исходной lease]
    G --> H[Job lock, review lock, точная PRE или POST]
    H --> I[Свежая проверка срока и одна фаза или наблюдение]
    I --> J[Сохранение result и fsync]
    J --> F
    F --> K[Стабильный protected ответ]
~~~

Отрицательная проверка credential или отзыва останавливает путь до обращения к action/result. При новом результате порядок locks — permit → action → ledger → job → review. Они удерживаются до формирования и валидации защищённой обёртки; saved replay требует только permit и action locks. Read-only SQL закрывается до файлового эффекта, пока ledger lock продолжает защищать локальную критическую область. Все вложенные действия получают тот же deadline.

Для операции установлен общий кооперативный предел 60 секунд; ожидание нескольких locks не начинает новый полный интервал на каждом уровне. Это не принудительное прерывание произвольного системного вызова либо откат уже сохранённого эффекта. Grant, revocation и публичный ответ ограничены каждый 64 КиБ. Вложенные action, ledger, catalog и write сохраняют собственные прежние пределы.

Предел каталога до 256 позиций, размер SQLite history и число permit directories описывают разные ресурсы. Новый слой не вводит общего численного предела callers, реестра всех credentials либо гарантии масштабирования. Несколько permit на один action имеют разные locks, затем сходятся на прежней action lock; отзыв одного не отменяет остальные.

## 15. Следующие предметные задачи

Для перехода от локальных управляющих шагов к порталу документации потребуется отдельно определить единицу содержательного изменения, источники, read/query-зависимости и политику рассмотрения. Permit можно привязать к явно выбранному действию, но полномочия публикации и актуальность предметного основания должны проверяться в собственном месте принятия.

Практическое развитие стоит разделить на наблюдаемые этапы: сначала измерить очереди и locks без внешних LLM; затем расширить проверку повторов на разные окна потери транспортного ответа и прерывания; после этого добавить транспорт с явной границей секретов и только затем исследовать независимость и качество предметных reviewers. Число процессов следует сопровождать числом принятых полезных изменений, долей отклонённых устаревших оснований и стоимостью проверки.

Разделение выдачи и отзыва по системным пользователям, внешний identity provider, обязательный единый интерфейс для всех writers, внешнее fencing и заверенный журнал потребуют отдельных решений о доверии. Текущие локальные labels, locks и hashes не дают этих свойств автоматически.
