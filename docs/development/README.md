# Работающая модель многоагентной разработки

Пользователь поручил перейти от обсуждения к подробному анализу и реализации. Здесь сохранён первый исполняемый этап: локальная координация нескольких авторов документов и программного кода. Исторический [проект архитектуры](../knowledge/multi-agent-wiki.md) остаётся источником идей; текущие гарантии определяются кодом и границами ниже.

[Журнал выполненных работ](activity.md) фиксирует последовательность, команды, исправления и фактические результаты.

**Второй реализованный этап:** [анализ влияния](impact-analysis.md), команды impact/graph/compare, зависимости принятых артефактов и запрет экспорта при устаревшем основании. [Выполненный пример](../../examples/impact-analysis/results/report.md) показывает изменения трёх файлов и повторное ревью списка платформ. Прежний отчёт первого этапа ниже сохраняется без изменений; новые выпуски имеют schema 2 и dependencies.json.

**Третий реализованный этап:** [корпус смысловых изменений](semantic-corpus.md), 24 авторских случая, команды corpus list/show/analyze и review-pair. [Четыре выполненных разбора](../../examples/semantic-review/results/report.md) показывают точное преобразование единиц, изменение типа утверждения, разные версии и отсутствие цитаты. Это отдельный инструмент редактора, без автоматического принятия и измерений точности.

**Четвёртый реализованный этап:** [редакторские решения](editorial-decisions.md), неизменяемые пакеты, история решений, проверка актуальности, повторы и экспорт. [Выполненный пример](../../examples/editorial-review/results/report.md) сохраняет согласие программных проверяющих, разногласие и устаревание решений после изменения текста. Согласие не даёт права принятия в Store; решения человека в примере отсутствуют.

**Пятый реализованный этап:** [досье конкретного предложения](proposal-dossiers.md) связывает runtime proposal, точную правку существующего шаблона документа или кода и редакторский пакет. Повторная оценка показывает смену зависимостей, формальной review и последних редакторских решений. Это материал для человека: снимки двух баз последовательны, общей транзакции нет, `Store.accept` сохраняет прежнюю политику. [Практический сценарий](../../examples/proposal-dossiers/results/report.md) сохраняется отдельно от прежних результатов.

**Шестой реализованный этап:** [составное предложение и полное рассмотрение](composed-review.md) объединяют точные предложения документа и кода через `Store.compose`. Набор `review-set` связывает все записи одного proposal с редакторскими пакетами, используя один runtime-контекст и один снимок журнала. Происхождение компонентов фиксируется, исходные одобрения не переносятся; готовность материала к рассмотрению человеком не предоставляет права принятия. [Отдельный пример](../../examples/composed-review/results/report.md) сохраняет фактические результаты этого этапа.

## 2. Быстрый запуск

Нужны Python 3.10+ и SQLite из стандартной библиотеки. Установка пакетов, ключи API и сервер не требуются. Запускайте из корня существующего checkout:

~~~sh
python3 -m agentwiki demo --workspace /tmp/agentwiki-my-run-01 --workers 6
python3 -m agentwiki status --workspace /tmp/agentwiki-my-run-01
~~~

Укажите новый пустой каталог. Программа сохраняет существующие данные. Повторный demo с готовым отчётом читает его; для нового выполнения задайте другой workspace.

После демонстрации путь выпуска указан в report.json. В сохранённом примере это r9-a450bcf40a40dc20:

~~~sh
python3 -m agentwiki search --release examples/multi-agent/results/release/r9-a450bcf40a40dc20 --query timeout
python3 -m agentwiki export --workspace /tmp/agentwiki-my-run-01 --output /tmp/agentwiki-my-export-01
~~~

Экспорт создаёт отдельный каталог выпуска. Команда не публикует сайт и не меняет удалённый Git. Python-файлы из предложений сохраняются и проверяются синтаксическим разбором, но не исполняются.

## 3. Устройство

~~~mermaid
flowchart TD
    S[Неизменяемые источники] --> K[Снимок утверждений и шаблонов]
    T[Задания и зависимости] --> A[Пул авторов с арендой]
    K --> A
    A --> P[Предложения с read set и query digests]
    P --> R[Проверяющий: digest и правила]
    R --> C[Координатор: повторная проверка и SQL commit]
    C --> K
    K --> E[Экспорт одного снимка]
    E --> D[Документы]
    E --> B[Код]
    E --> I[Индекс и manifest]
~~~

Параллельны подготовка предложений и исполнение заданий. Запись в SQLite сериализуется. Полная копия снимка при каждой принятой правке делает прототип прозрачным для изучения; это расход O(N) на ревизию и O(N × R) на историю без учёта размеров текста. Такая модель хранения намеренно не рассчитана на большую энциклопедию.

### Почему в runtime каноничен SQLite

Ранняя архитектура предлагала Git как каноническую версию, а SQL как управляющую базу. Для этого нужен отдельный протокол согласования двух хранилищ. Первый реализованный этап держит и знания, и принятие в одной SQL-транзакции. Git хранит исходники, документы и экспортированные снимки. Прототип не выполняет Git CAS, не создаёт PR и не заявляет атомарность SQL + Git.

Такой выбор позволяет показать конфликтную семантику без скрытого окна между двумя системами. Будущее согласование Git и SQL описано в [дорожной карте](roadmap.md).

## 4. Какие агенты что делают

| Роль | Разрешённый результат в API | Право принятия |
|---|---|---|
| analyst | Структурированные claims | Через проверку и координатора |
| doc_author | Шаблоны docs/*.md | Через проверку и координатора |
| code_author | Шаблоны code/*.py | Через проверку и координатора |
| integrator | Составление непересекающихся предложений документов и кода | Новая проверка и координатор |
| reviewer | Отчёт о конкретном digest | Не заменяет принятие |
| coordinator | Проверяет одобрение, актуальность и инварианты | Одна SQL-транзакция |
| exporter | Строит файлы и индекс из принятого снимка | Не меняет знания |

Сейчас reviewer и coordinator — функции локального приложения. Это разделение операций и записей, а не отдельные модели или защита от пользователя с доступом к файлу SQLite. Авторы не могут через submit изменить типы артефактов вне своей роли; отдельной сетевой аутентификации нет. Неравенство имён автора и проверяющего не доказывает независимость людей или моделей.

Источники добавляет локальный управляющий код; заменить содержимое существующего source_id нельзя. Бюджет api.budget_seconds защищён от агентных изменений после bootstrap. Политика timeout × attempts ≤ budget зафиксирована в коде.

## 5. Пошаговый практический результат

1. Создана вымышленная спецификация с вариантами timeout 30/40 секунд, attempts 3/4 и бюджетом 120 секунд.
2. На ревизии 1 сформированы шесть независимых заданий для документов, кода и сведений о платформе.
3. Шесть потоков получили аренды, отправили предложения и выполнили формальную проверку.
4. Принята Windows. Старый список платформ отклонён с query_changed, хотя Linux не менялся.
5. Четыре независимых предложения той же исходной ревизии приняты. Изменение общего head само по себе не запрещает правку.
6. Полный список платформ пересоздан по свежему снимку и принят.
7. Два предложения отдельно соответствовали правилу: 40 × 3 = 120 и 30 × 4 = 120. После принятия timeout 40 правка attempts 4 отклонена с invariant_violation: 160 > 120.
8. Подготовленный ранее документ, читавший timeout 30, отклонён с stale_read.
9. Задание с истёкшей арендой передано новому worker. Старый token получил lease_lost. Новый результат принят.
10. Повторное принятие того же предложения вернуло прежнюю ревизию.
11. Из ревизии 9 получены пять Markdown-документов, один Python-файл, знания, источники и индекс. Рендер документа и кода использует timeout 40, attempts 3, budget 120.

Итог: 11 предложений, 8 принятых, 3 заблокированных принятия, 1 отклонённая запоздавшая отправка и 1 повтор принятия без новой ревизии. В [JSON-отчёте](../../examples/multi-agent/results/report.json) сохранены результаты и события. В нём абсолютный workspace относится к фактическому историческому запуску; файлы для чтения находятся рядом с отчётом.

## 6. Как добавить собственное задание

Минимальный пример использует базу уже выполненной демонстрации. Он создаёт новый документ с явной зависимостью на timeout. Используйте уникальный task_id и свободный путь артефакта:

~~~python
from agentwiki.store import Store

store = Store('/tmp/agentwiki-my-run-01/state.sqlite3')
snapshot = store.snapshot()
target = 'docs/custom-guide.md'
claim = 'api.timeout_seconds'
proposal = {
    'readset': {
        target: snapshot['digests'].get(target),
        claim: snapshot['digests'][claim],
    },
    'queries': {},
    'writes': [{
        'id': target,
        'kind': 'document',
        'template': '# Настройка\n\nTimeout: {{api.timeout_seconds}} секунд.\n',
        'bindings': [claim],
    }],
    'rationale': 'Добавить руководство из принятого значения timeout.',
}
store.enqueue('custom-guide-01', 'doc_author', {'proposal': proposal})
task = store.claim_task('author-custom', roles=['doc_author'])
if task is not None:
    # В общей очереди worker обрабатывает фактически выданное задание.
    submitted = store.submit(task['task_id'], 'author-custom', task['token'],
                             task['payload']['proposal'])
    review = store.review(submitted['proposal_id'], reviewer='editor-custom')
    if review['approved']:
        result = store.accept(submitted['proposal_id'])
        print(result)
~~~

Новые файлы включаются в readset со значением null: это проверка, что путь ещё свободен. Для изменения существующего файла нужен его текущий digest. Каждая binding тоже обязана быть в readset. Берите все зависимости из одного snapshot; отдельные чтения могут относиться к разным ревизиям.

Полный перечень требует query digest из snapshot['queries']['platforms:api-v1']. Запросы ограничены зарегистрированными областями api:v1 и platforms:api-v1. Произвольный SQL от автора не принимается. Digest отражает состав и содержимое результата; если всё вернулось к прежнему содержимому, digest совпадает, история промежуточных изменений не отслеживается этим условием.

Зависимости заданий depends_on означают «предыдущая задача сохранила предложение», а не «её предложение принято». Потребитель принятого знания должен получить новый snapshot после решения координатора. Не используйте task.done как редакционное одобрение.

Для долгой работы вызывайте heartbeat с тем же token до истечения аренды. Сроки используют часы одного хоста; распределённые аренды и модель скачков времени здесь не решены. Исправление предложения создавайте новым заданием; сохранённый payload не редактируется.

## 7. Что значит семантика в этом MVP

Проверяются конкретные формальные отношения: прочитанное значение, состав выборки, зависимость шаблона, единицы бюджетного правила и совместное ограничение. Синтаксис Python разбирается без исполнения. Источник фиксируется текстом и SHA-256; цитата должна присутствовать буквально.

Это полезная часть смыслового контроля, но не доказательство истинности свободного текста. Нельзя надёжно определить этим кодом, что цитата поддерживает произвольный вывод, что источник независим или что алгоритм программы верен. Сведения демонстрации вымышлены, а логический вывод из цитаты автоматически не проверяется.

Шаблоны являются принятыми правилами отображения: их значения пересчитываются при новом экспорте. Изменение claim поэтому меняет отображаемые документы и константы без отдельного одобрения каждой полученной строки. Это допустимо для явно связанных параметров; перенос на свободные рекомендации требует анализа влияния и отдельного ревью.

Сохранённые код и Markdown могут содержать произвольный авторский текст. Приложение их не запускает и не показывает как доверенный HTML. SQLite, файловые права и процесс считаются доверенными. Проверка manifest обнаруживает несовпадение с сохранёнными хешами, но без подписи не удостоверяет происхождение.

## 8. Сколько агентов запускать

Практический старт — 4–8 авторских заданий и последовательное принятие. Выполненный сценарий использовал 6 потоков. Предел CLI 32 — ограничение примера, не измеренная ёмкость. Сто и тысячи агентов требуют измерения доли конфликтов, задержки ревью, стоимости моделей и пропускной способности координатора.

Подробные формулы, сценарии 1/4/8/16/32/100 и ограничения моделей производительности: [теоретический анализ](theory.md). Исследовательские направления и критерии перехода: [пошаговая дорожная карта](roadmap.md).

Явный граф влияния реализован во втором этапе, иллюстративный корпус и парный анализ — в третьем, журнал решений — в четвёртом. Пятый связывает рассмотрение с точным proposal без предоставления полномочий принятия. Шестой сохраняет происхождение составного предложения и рассматривает все его файлы по общим наблюдённым основаниям. Далее нужны проверенные роли участников, общая редакционная политика, проверка качества на отдельных материалах, измерение полезности целевой перепроверки и адаптивное ограничение параллелизма. Мировое первенство и выигрыш в качестве ещё не установлены.
