# Журнал редакторских решений и актуальность основания

Четвёртый этап добавляет долговременную историю рассмотрения смысловых изменений. Он продолжает [сравнение структурированных утверждений](semantic-corpus.md).
Пара утверждений объясняет, что предложено изменить; журнал сохраняет, кто и на каком основании высказался.
Повторное рассмотрение относится к точному пакету, а изменившееся основание требует нового решения.

Это локальный инструмент на Python и SQLite, без вызовов внешних LLM. Описанные роли задаются строковыми идентификаторами; аутентификация и независимость рецензентов не реализованы.
Авторский корпус остаётся иллюстративным материалом ИИ-агентов, без экспертного эталона.

## 1. Зачем нужен отдельный журнал

Одного итогового слова «одобрено» недостаточно для совместной работы над документацией и кодом. Нужно восстановить исходную пару, снимки источников, объяснение инструмента и мотивировку редактора.
Также важно отличить новое решение от повторной доставки прежней операции.
При обновлении источника прежнее мнение сохраняет историческую ценность, но требует новой проверки.

Пример: автор меняет измеренное время ответа на гарантированный верхний предел. Первый рецензент считает цитату достаточной; второй указывает, что измерение не доказывает гарантию.
Их ответы должны оставаться доступными одновременно вместе с точными основаниями.
Поздняя правка первого ответа добавляет новую запись, а не стирает прежнее разногласие.

## 2. Три разных объекта

| Объект | Содержание | Изменяемость через API |
|---|---|---|
| Пакет | Пара before/after, sources, анализ, правила, политика, автор | После создания неизменяем |
| Решение | Рецензент, тип участника, вердикт, мотивировка, ссылка на пакет | Новая запись при каждом изменении мнения |
| Оценка | Сопоставление пакета с текущим входом и сводка последних мнений | Вычисляется по явно переданному текущему входу |

События журнала дополнительно фиксируют порядок записей и контрольные суммы. Рабочий файл называется `editorial.sqlite3`; он хранится отдельно от основного runtime.
Новый журнал не принимает proposals в [Store](../../agentwiki/store.py).
Его результат не вызывает публикацию, генерацию Python-кода или выполнение предложенного кода.

## 3. Неизменяемый пакет рассмотрения

Пакет замораживает входные данные и результат анализа в момент создания. Вход содержит только `before`, `after` и `sources`, как у команды `review-pair`.
Авторские аннотации корпуса в сравнение утверждений не передаются.
Для каждого источника сохраняются полный локальный текст и его SHA-256.

В пакет также входят идентификатор автора, версия правил и действующая политика. Digest входа отличается от digest анализа: это позволяет отдельно объяснить изменение данных и правил.
Общий digest пакета связывает эти компоненты в одну проверяемую запись.
Изменение одной цитаты, идентификатора автора или результата анализа требует нового пакета.

~~~text
pair + sources → semantic analysis
        + rules version + policy + proposer
        → immutable packet → packet digest
~~~

Снимок источника позволяет повторно увидеть прочитанный фрагмент без обращения к сети. Буквальное наличие цитаты не устанавливает её логическую достаточность или истинность.
Корректная контрольная сумма подтверждает совпадение байтов относительно сохранённого значения.

## 4. Роли, идентификаторы и доверие

Автор готовит изменение и указывает `proposer_id`. Рецензент записывает мнение под собственным `reviewer_id`.
Тип участника обозначается как `agent` или `human` и сообщается самим вызывающим процессом.
Журнал не проверяет паспорт, принадлежность учётной записи или происхождение ответа модели.
Объявленный тип закрепляется за идентификатором в журнале и не меняется следующей записью.

Совпадение идентификаторов автора и рецензента запрещено. Это ограничение интерфейса уменьшает случайное саморецензирование в кооперативном процессе.
Оно не мешает одному человеку или процессу объявить несколько разных идентификаторов.
Поэтому число записей и число идентификаторов не означают число независимых экспертов.

В демонстрации все участники имеют тип `agent`. Не следует превращать заданную программой реплику в «решение человека» сменой подписи.
Даже запись с типом `human` остаётся самозаявлением без внешней аутентификации.
Реальная система доступа и проверка полномочий относятся к следующему этапу.

## 5. Вердикт и мотивировка

Поддерживаются `approve`, `request_changes` и `abstain`. Одобрение означает мнение конкретного рецензента о конкретном пакете.
Запрос изменений должен сохранять объяснение того, что автору следует пересмотреть.
Воздержание сохраняет участие и недостаточность собственного вывода.

Мотивировка обязательна для каждого вердикта. Она не превращается в структурированное доказательство только потому, что хранится в БД.
Осмысленность аргумента, независимость основания и достаточность компетенции требуют рассмотрения.
Запись не исполняется как инструкция для координатора или исходный программный код.

## 6. Условная запись и история пересмотра

При отправке решения вызывающая сторона передаёт ожидаемый digest пакета. Журнал сопоставляет его с сохранённым пакетом перед добавлением записи.
Так одобрение нельзя случайно приложить к содержанию с другим digest.
Эта проверка относится к неизменяемому пакету, а не к удалённому Git ref.

Для первого решения рецензента ожидаемая предыдущая запись отсутствует. При смене мнения передаётся идентификатор именно последнего решения этого рецензента.
Если другой процесс уже добавил новую запись, прежнее ожидание больше не совпадает.
Отправитель должен прочитать историю и решить, как продолжать, вместо молчаливого затирания.

~~~text
reviewer-A: decision-1 approve
          → decision-2 request_changes, supersedes=decision-1
reviewer-B: decision-3 approve
~~~

Старые записи остаются в истории; для сводки используется последнее мнение каждого рецензента.
Проверка ожиданий и добавление записи выполняются в одной локальной транзакции SQLite.
Это ограничивает гонку двух записей, но не образует распределённую транзакцию с GitHub.

## 7. Повторная доставка операции

Каждая команда записи получает `operation_id`. Повтор той же операции с тем же содержанием возвращает сохранённый результат.
Вторая доставка не добавляет ещё один голос и не увеличивает историю новым решением.
Повторное использование идентификатора с другим содержанием должно завершаться конфликтом.

В содержимое операции входят пакет, его ожидаемый digest, рецензент, тип, вердикт и мотивировка.
Ожидаемая предыдущая запись тоже существенна для различения операций.
Новый вердикт или новая мотивировка требуют нового `operation_id`.
Это протокол повторов кооперативного клиента, а не криптографическая подпись автора.

## 8. Актуальность основания

Команда оценки всегда получает явно указанный текущий вход. Самого сохранённого пакета недостаточно, чтобы утверждать актуальность относительно внешнего мира.
Текущий вход должен отражать данные, которые координатор действительно собирается рассматривать.
Если вызывающая сторона передала старую копию, журнал не узнает о скрытом внешнем изменении.

Проверяются digest входа, действующая политика, версия правил и повторно вычисленный анализ.
Так можно различить изменившуюся пару и изменившееся объяснение при прежних входных данных.
Обновление правил не переносит автоматически старое одобрение на новый результат анализа.
Изменение политики также требует повторного рассмотрения соответствующего пакета.

~~~text
saved input ≠ current input        → stale_input
saved rules ≠ current rules        → stale_rules
saved policy ≠ current policy      → stale_policy
saved analysis ≠ current analysis  → stale_analysis
~~~

Причины сохраняются явно, а не сворачиваются в безымянный общий балл доверия.
Старые решения остаются видимы как решения по прежнему основанию.
Чтобы рассмотреть изменённый материал, создают новый пакет и добавляют новые решения.
Оценка не изменяет старый пакет и не переписывает прошлые мотивировки.
CLI требует `--current-input`; Python API без него возвращает `input_not_checked` и `is_current=None`.
Отсутствие проверки не описывается как актуальное основание.

## 9. Сводка мнений и разногласия

Актуальность основания и распределение мнений — отдельные измерения.
В истории могут быть согласующиеся ответы, относящиеся к уже устаревшему входу.
Их согласие остаётся фактом истории; действующего одобрения нового входа из него не следует.

Сводка использует последние решения рецензентов, сохраняя полную историю отдельно.
`agent_agreement` требует минимум двух одобрений агентов и отсутствия запросов изменений.
`disagreement` сохраняет существенное расхождение одобрений и запросов изменений.
`changes_requested` показывает, что действующие ответы требуют переработки.
Воздержания учитываются явно и не превращаются в одобрение.
Отсутствие решений обозначается `awaiting_reviews`, только воздержания — `abstained`.
`review_recorded` сохраняет прочие сочетания, не объявляя машинное согласие.

Большинство голосов не устанавливает истину.
Три агента, использующие один ошибочный источник, могут согласиться по одной и той же причине.
История возражения полезна даже при одном несогласном участнике.
Разрешение предметного спора требует основания и полномочного редакционного процесса.

Во всех исходах сохраняются `auto_accept=false` и `requires_human_review=true`.
Ни согласие, ни пометка `human` не создают автоматического пути в `Store.accept`.
Журнал подготавливает материалы для решения, сохраняя ограничение текущего прототипа.

## 10. Экспорт и проверяемое происхождение

Экспорт сохраняет самостоятельный JSON-снимок журнала.
В нём должны оставаться пакеты с исходными данными, все решения и события.
Получателю не нужно угадывать, к какой версии текста относилась краткая сводка.
Снимок можно хранить рядом с документами, кодом и результатами обсуждения в Git.

События связаны предыдущей контрольной суммой и содержимым текущей записи.
Такая цепочка помогает заметить несогласованное изменение относительно известных контрольных сумм.
Владелец файла может пересчитать всю цепочку; подпись и внешний доверенный якорь отсутствуют.
Поэтому экспорт не называется защищённым от подмены аудитом или доказательством авторства.

Самостоятельный снимок не синхронизирует две базы и не выполняет удалённый Git CAS.
Публикация файла в Git — отдельное действие после локального сохранения.
Для будущего общего процесса нужны восстановление намерений, проверка ref и политика доступа.

## 11. Практический порядок работы

1. Получить или подготовить JSON с `before`, `after` и `sources`.
2. Создать пакет с явным идентификатором автора и сохранить выданные ID и digest.
3. Передать неизменяемый пакет другим участникам на рассмотрение.
4. Записать мотивированные решения с отдельными идентификаторами операций.
5. Перед выпуском оценить пакет относительно явно переданного текущего входа.
6. При изменении основания создать новый пакет; прежние решения оставить в истории.
7. Экспортировать журнал для совместного рассмотрения и фиксации происхождения.

Команды выполняются из корня репозитория. Для собственного запуска выберите новые пути:

~~~sh
python3 -m agentwiki corpus show --case kind-measurement-to-guarantee --pair > /tmp/editorial-my-pair.json
python3 -m agentwiki editorial create --db /tmp/editorial-my.sqlite3 --input /tmp/editorial-my-pair.json --proposer-id author-1 --proposer-kind agent
~~~

Скопируйте выданные идентификатор и digest пакета в переменные `PACKET_ID` и `PACKET_DIGEST` оболочки.
Затем можно записать первое решение другого участника и получить оценку:

~~~sh
python3 -m agentwiki editorial show --db /tmp/editorial-my.sqlite3 --packet "$PACKET_ID"
python3 -m agentwiki editorial record --db /tmp/editorial-my.sqlite3 --packet "$PACKET_ID" --packet-digest "$PACKET_DIGEST" --reviewer-id reviewer-1 --actor-kind agent --verdict request_changes --rationale "Измерение не подтверждает заявленную гарантию" --operation-id review-1
python3 -m agentwiki editorial assess --db /tmp/editorial-my.sqlite3 --packet "$PACKET_ID" --current-input /tmp/editorial-my-pair.json
python3 -m agentwiki editorial history --db /tmp/editorial-my.sqlite3 --packet "$PACKET_ID"
python3 -m agentwiki editorial export --db /tmp/editorial-my.sqlite3 --output /tmp/editorial-my-snapshot.json
~~~

Для пересмотра передайте новое `--operation-id` и `--supersedes` с ID последнего своего решения.
Экспорт требует отсутствующий выходной файл и сохраняет существующий снимок.
Самостоятельный демонстрационный сценарий запускается в новом пустом каталоге:

~~~sh
python3 -m agentwiki editorial-demo --workspace /tmp/editorial-my-run
~~~

Сценарий использует только участников `agent`; его результаты не являются экспертной оценкой корпуса.
Обычный запуск демонстрации не заменяет систематическую проверку отказов и нагрузки.

## 12. Выполненный пример

В [отчёте запуска](../../examples/editorial-review/results/report.md) сохранён сценарий с тремя рецензентскими ID типа `agent`.
Два задания отправляют одобрения через пул потоков; третий участник затем добавляет возражение и пересматривает своё мнение.
В [самостоятельном JSON-снимке](../../examples/editorial-review/results/journal.json) находятся 2 пакета, 4 решения исходного пакета и 10 событий.

| Действие | Наблюдаемый результат |
|---|---|
| Два одобрения, затем возражение | `agent_agreement` → `disagreement` |
| Пересмотр возражения с актуальным предшественником | Новая запись, `agent_agreement` |
| Повтор той же операции | Количество решений осталось 4 |
| Ссылка на уже устаревшего предшественника | `decision_conflict`, запись не добавлена |
| Добавление текста в исходную пару | `stale_input`, `current_basis_decisions=[]` |
| Новый пакет по изменённому входу | `awaiting_reviews`, решений 0 |

У старого пакета сохраняется исторический `review_state=agent_agreement` одновременно с `freshness=stale_input`.
Это раздельные измерения: голоса не перенесены на новый вход. Решение человека не записывалось, автоматического принятия нет.

## 13. Следующие направления развития

Первое направление — связать пакет рассмотрения с точным proposal основного runtime. Для этого потребуется общая политика принятия, срок действия решения и проверка основания в транзакции.
Простое копирование поля `approved` между базами создаст окно устаревания.

Второе направление — явные полномочия и происхождение участников.
Аутентификация позволит отличать заявленный тип от проверенной учётной записи.
Независимость исследований всё равно потребует данных об источниках, маршрутах и моделях.

Третье направление — оценка пользы журнала на отдельно размеченных задачах.
Следует измерять необоснованные одобрения, пропущенные возражения и труд редактора.
Факт сохранения истории сам по себе не измеряет качество семантического решения.
Результаты этого этапа нужно сопоставлять с [дорожной картой](roadmap.md), сохраняя различие реализации и исследовательской гипотезы.
