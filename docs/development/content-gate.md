# Обязательное рассмотрение объявленного содержания

Четырнадцатый этап связывает [межфайловые обязательства](cross-file-obligations.md), [опись обещаний](promise-coverage.md), [полномочия проверяющих](governance.md) и [происхождение предложений](authorship.md) с новым принятием в SQLite. В отдельно включаемом режиме недостаточно предъявить положительный внешний отчёт: действующий пакет содержания вычисляет сам Store из состояния своей транзакции. Решение проверяющего закрепляет digest этого пакета.

Предмет проверки остаётся узким: явно выбранное поле помеченного JSON-блока документа, литеральная константа Python и объявленное отношение между ними. Совпадение этих значений не устанавливает истинность свободного текста, выполнение программы или полноту документации. [Прикладной пример](../../examples/content-gate/README.md) и [отчёт выполнения](../../examples/content-gate/results/report.md) сохраняют фактический сценарий отдельно от прежних запусков.

## 1. Какой разрыв закрывается

До этого этапа аналитические инструменты могли обнаружить противоречие документа и конфигурации, а runtime отдельно проверял актуальность предложения, авторство и кворум. Положительное решение governance не было обязано ссылаться на результат предметного сравнения. Координатор мог удовлетворить прежнюю политику, даже когда отдельный совещательный отчёт показывал `mismatch`.

Теперь оператор может явно включить правило: новое принятие требует пригодного пакета содержания по действующей политике, а учитываемые решения должны закреплять именно его. Расхождение значений, неразрешимый селектор, неверная связь обещания или устаревшее основание остаются препятствиями независимо от числа одобрений.

| Вопрос | Механизм |
| --- | --- |
| Кто подготовил предложение и его компоненты? | Authorship и исходные grants конкретных попыток |
| Кто вправе высказать учитываемое мнение? | Governance, область grant и исключение contributors |
| Какие поля и обещания обязательны для этой работы? | Административная политика содержания |
| Каковы значения и отношения на текущем основании? | Пакет, вычисленный внутри транзакции Store |
| К какому предмету относится мнение? | Точный digest пакета в решении |
| Можно ли принять правку сейчас? | Совместная проверка runtime, авторства, содержания и кворума |

Это развитие локального прототипа. Сравнение с чужими продуктами, измерение уникальности решения и утверждение о готовности промышленного портала в этом этапе не выполнялись.

## 2. Режим включается отдельно

Content gate односторонне включается администратором только после governance и authorship. Существующая база без активации продолжает прежний процесс. Автоматической активации по наличию Markdown, прежнего отчёта или новой версии программы нет.

Оператор передаёт строгую непустую политику и ожидаемое текущее поколение governance. Активация в одной write-транзакции:

1. Проверяет административный credential и ожидаемое поколение.
2. Проверяет форму и связи политики содержания.
3. Сохраняет её первое поколение.
4. Повышает поколение governance, сохраняя существующую политику полномочий.
5. Сохраняет событие активации.

При последовательном включении governance, authorship и content gate поколения governance меняются `1 → 2 → 3`; первое поколение содержания равно `1`. Если оператор уже обновлял политику, действующее число будет другим. Нужен явный номер из состояния базы.

Это два отдельных счётчика. В результате активации и обновления `policy_generation` обозначает действующее поколение governance, а `content_policy_generation` — поколение содержания. В `current_policy.generation` статуса содержания находится номер его собственной политики. В пакетах оба поколения имеют явные имена `governance_policy_generation` и `content_policy_generation`.

Повышение поколения исключает перенос прежних голосов на новые условия. Принятые до активации предложения сохраняют исторический статус; доказательства рассмотрения содержания задним числом не создаются. API выключения режима нет.

## 3. Политика задаёт конечный комплект

Верхний уровень политики содержит ровно четыре поля:

~~~json
{
  "schema_version": 1,
  "artifact_ids": ["code/client_config.py", "docs/reference.md"],
  "spec": {
    "schema_version": 1,
    "obligations": [
      {
        "id": "maximum-attempts",
        "description": "Объявленное число попыток равно документированному.",
        "scope": {"api": "v1"},
        "relation": "equals",
        "value_type": "integer",
        "document": {
          "artifact_id": "docs/reference.md",
          "fence_id": "retry-policy",
          "path": ["max_attempts"]
        },
        "code": {
          "artifact_id": "code/client_config.py",
          "symbol": "MAX_ATTEMPTS"
        }
      }
    ]
  },
  "inventory": {
    "schema_version": 1,
    "promises": [
      {
        "id": "attempt-limit-promise",
        "description": "Число попыток включено в обязательное рассмотрение.",
        "anchor": {
          "artifact_id": "docs/reference.md",
          "quote": "Максимальное число попыток — 3."
        },
        "requirement": {
          "scope": {"api": "v1"},
          "relation": "equals",
          "value_type": "integer",
          "document": {
            "artifact_id": "docs/reference.md",
            "fence_id": "retry-policy",
            "path": ["max_attempts"]
          },
          "code": {
            "artifact_id": "code/client_config.py",
            "symbol": "MAX_ATTEMPTS"
          }
        },
        "obligation_ids": ["maximum-attempts"]
      }
    ]
  }
}
~~~

Это самостоятельный пример формы, а не результат выполненного запуска. Документ соответствующего предложения должен содержать точную цитату и однозначный помеченный блок:

````markdown
Максимальное число попыток — 3.

```json agentwiki:retry-policy
{"max_attempts": 3}
```
````

Файл конфигурации должен принадлежать поддержанной литеральной грамматике, например:

~~~python
MAX_ATTEMPTS = 3
~~~

Политика использует прежние схемы спецификации `obligations` и описи `coverage`. Требование обещания должно точно совпадать с указанным обязательством: оба селектора, scope, тип и отношение. Множество `artifact_ids` должно точно равняться объединению всех документальных и программных сторон обязательств. Каждое правило должно иметь точную привязку хотя бы к одному обещанию. Пустая опись или удобное совпавшее правило без такой связи не создают пригодную политику.

При вычислении пакета у каждого обещания заново проверяются однозначная точная цитата, разрешимое поле документа и связи с обязательствами. Наличие строки цитаты не доказывает, что её смысл правильно переведён в структурированное требование. Например, «три повтора после первой попытки» и «три попытки всего» требуют различного предметного определения.

### 3.1. Равенство комплекта и записей

Множество `write_id` предложения должно **точно совпадать** с `artifact_ids` политики. Дополнительная запись не остаётся за пределами обязательного процесса. Предложение с частью комплекта также не проходит.

Это намеренно простой способ сделать границу проверки наблюдаемой. Если меняется только документ, действующая политика пары требует включить и файл кода, при необходимости с неизменённым телом. Такая запись всё равно участвует в предложении и его основаниях. Это может увеличить число конфликтов, объём рассмотрения и ширину требуемых grants.

В текущем варианте нет маршрутизации к нескольким политикам по разделам портала, необязательных файлов или автоматического расширения комплекта по графу влияния. Для большой базы знаний требуется отдельная модель выбора политики и проверки её полного покрытия. Уменьшать комплект ради удобства без явного административного изменения нельзя.

## 4. Ограниченный язык содержания

Проверка переиспользует чистые ограниченные экстракторы прежних аналитических модулей. Она не импортирует предложенный код и не исполняет его. Не вызываются внешняя модель, поиск или редакторский журнал.

| Часть | Поддержанное основание |
| --- | --- |
| Документ | Однозначный fenced JSON с меткой `json agentwiki:<id>` и путь по ключам объектов |
| Конфигурация | Литеральные объявления верхнего уровня в ограниченном AST Python |
| Типы | `string`, `boolean`, `integer`, `string_set` |
| Отношения | `equals`; для `string_set` также `code_subset_of_document` |
| Цитата | Единственное точное вхождение в отображённом документе |
| Подстановки | Значения из того же захваченного кандидата Store |

Для `code_subset_of_document` направление фиксировано: код ⊆ документ. `true` не считается целым `1`; не выполняются неявные преобразования строк в числа. Динамический вызов, импорт, мутация или неподдержанное выражение дают `unresolved`, а не предполагаемое значение. Первая удобная константа не выбирается с игнорированием дальнейшей мутации модуля.

`match` означает выполнение заявленного отношения над извлечёнными значениями. `mismatch` означает нарушение этого отношения. `unresolved` означает недостаточность основания для определённого сравнения. Для нового принятия последние два результата препятствуют пригодности пакета.

Сама проза может противоречить извлечённому полю иначе, чем предусмотрено цитатой и правилом. Область scope является заявленными метками, а не доказанными условиями исполнения. Единицы, причинность, модальность, исключения и фактологическая истинность не выводятся автоматически.

## 5. Один пакет из одного состояния SQL

Store вычисляет пакет содержания во время `content_status`, записи governance-решения, наблюдения допустимости и нового принятия. Вход берётся из текущего SQL-снимка: предложение и его записи, ожидаемые и фактические read/query основания, текущие артефакты и используемые при отображении зависимости.

Для принятия вычисление находится внутри той же `BEGIN IMMEDIATE`, что и остальные условия и запись новой ревизии. Другой writer этой базы не может незаметно изменить основание между содержательной проверкой и сохранением принятия. Это свойство относится к одной SQLite-базе и доверенной реализации Store.

~~~mermaid
flowchart TD
    P[Предложение и точный digest] --> S[Один снимок Store]
    B[Read/query основания и зависимости] --> S
    C[Текущая политика содержания] --> S
    G[Текущее поколение governance] --> S
    S --> X[Чистое извлечение полей и цитат]
    X --> K[Детерминированный пакет]
    K --> D[Решение с точным digest пакета]
    K --> A[Повторное вычисление при принятии]
    D --> A
    A --> R[Проверки runtime, авторства и кворума]
    R --> F[Свежая авторизация и квитанция]
~~~

Не загружается внешний `review-set` с вымышленными положительными решениями. Не используется сохранённый отчёт `EditorialJournal` как источник разрешения. Старые `dossier`, `review-set`, `obligations` и `coverage` сохраняют собственные совещательные форматы и границы. Их исторические поля `atomic_capture=false` и `live_state_checked=false` не переписываются для вида.

Внешний текст, URL, файл checkout или выпущенный Git-экспорт не включается в транзакцию автоматически. Если для проверки нужны внешние данные, их сначала необходимо ввести в управляемое основание по отдельному процессу с источником и версией.

## 6. Что закрепляет digest

Пакет schema 1 с правилами `content-gate-1`, `obligations-1` и `coverage-1` связывает:

- ID и digest конкретного предложения.
- Предлагаемые записи через proposal digest и контрольные суммы выбранных тел и фрагментов.
- Ожидаемые и наблюдаемые read sets и scoped queries.
- Использованные для отображения зависимости и их значения.
- Спецификацию и опись через digest политики; извлечённые поля, цитаты и результаты отношений сохраняются в пакете.
- Поколение и digest политики содержания.
- Поколение и digest политики governance.
- Версии применённых правил.

Пакет получает `packet_id` вида `cgp_<digest>` и отдельный `packet_digest`. Полные тела политик сохраняются в истории `content_policies`; их поколения и digests входят в пакет. Он не дублирует весь payload предложения и всю политику. Для разбора предмета используются закреплённые записи истории и извлечённые фрагменты. Несовместимая замена версий используемых экстракторов даёт `content_rules_unsupported`; прежние пакеты нельзя молча переинтерпретировать новыми правилами.

Часы, глобальный счётчик revision, текущий статус предложения, история голосов и факт выполнения формальной review не входят в предмет пакета. Иначе само появление первого решения или формальной review изменяло бы digest и делало невозможным накопление согласованных мнений.

Изменение посторонней записи само по себе не означает новый пакет. Изменение затронутого основания, отображаемого значения, наблюдаемого результата query или поколения политики означает новый предмет. Поэтому повторное вычисление в неизменном состоянии воспроизводит digest, а изменённое основание не наследует прежнее одобрение.

Успешный `content status` является публичным наблюдением. Он не сохраняет голос, не резервирует состояние для будущего принятия и не блокирует последующие изменения. Перед записью решения Store пересчитывает пакет и сравнивает переданный digest. Между status и decide допустим отказ из-за изменившихся условий.

`content status --proposal …` всегда вычисляет текущий пакет. После принятия его ожидаемые и фактические основания могут расходиться из-за собственных записей принятой правки; такой текущий пакет не заменяет исторический. Команда `content show --packet …` читает сохранённое полное тело по точному ID, проверяя его внутренний адрес, схему, границы и исторические связи предложения и политик без пересчёта по живому состоянию. Для аудита квитанции нужен именно закреплённый исторический пакет. Его историческое `eligible=true` не является разрешением сегодняшнего принятия.

## 7. Решение закрепляет предмет рассмотрения

При активном режиме `governance_decide` требует `expected_content_packet_digest`. CLI передаёт его через `--content-packet-digest`. Совпадения proposal digest и поколения политики недостаточно: должны совпасть также текущие предметные основания.

Решение активного режима сохраняется как schema 2 вместе со ссылкой на неизменяемый пакет. Полное тело пакета сохраняется в SQLite при записи решения. Несколько решений могут ссылаться на один и тот же предмет; это не превращает повторное вычисление в независимую проверку.

В schema 2 верхний `content_packet_digest` закрепляет запрос reviewer. Вложенный `content_packet` содержит `packet_id`, `packet_digest`, `content_policy_generation` и `content_policy_digest`. Эти поля сверяются совместно. Receipt schema 3 использует такую же вложенную ссылку; полный пакет и политики читаются из соответствующих исторических записей. Digest предложения, политики и пакета относятся к разным объектам и не взаимозаменяемы.

| Verdict | Условие содержания |
| --- | --- |
| `approve` | Переданный digest совпадает с текущим пакетом, пакет пригоден |
| `request_changes` | Digest совпадает; можно закрепить замечание к заблокированному пакету |
| `abstain` | Digest совпадает; можно зафиксировать воздержание по заблокированному пакету |

Такая запись означает, что обладатель reviewer credential явно подтвердил идентификатор предмета своего решения. Она не доказывает, что человек прочёл пакет, понял документ, проверил источник или независимо от другого участника пришёл к выводу. Автоматизированный процесс с тем же credential обладает теми же локальными полномочиями.

Текущая роль, область grant, principal, CAS последнего мнения и operation ID сохраняют прежний смысл. Все contributors корневой композиции исключаются из любого governance-verdict по всему комплекту. Новый допуск с тем же principal это ограничение не обходит.

## 8. Пригодность пакета и кворум различаются

Пригодный пакет может ещё не иметь ни одного одобрения. Одобрений также может быть достаточно по числу, но они могут относиться к старому пакету, старому поколению или отозванным grants.

Наблюдение governance учитывает содержание и пригодность последних мнений. Для нового принятия требуются одновременно:

1. Прежние проверки формы, digest, read/query оснований и инвариантов Store.
2. Действительное происхождение и допустимое разделение участников.
3. Пригодный пакет содержания по действующей политике.
4. Последние действующие решения каждого нужного reviewer principal по каждой записи, закрепляющие этот пакет.
5. Требуемый политикой кворум, отсутствие действующих блокирующих решений и допустимый coordinator.
6. Формальная review по прежним требованиям runtime и свежая заключительная авторизация.

Одобрение исходного компонента не становится одобрением композиции. Правильный пакет компонента также не освобождает интегратора от проверки конечного комплекта: у корневого предложения свои digest, основания и пакет.

`observe` остаётся наблюдением условий, а не новым принятием. Результат до последующего вызова может устареть. Полное действие с записью выполняет `Store.accept`.

## 9. Порядок финальной проверки

Содержательная проверка может занять время: нужно захватить зависимости, разобрать тексты и AST, проверить цитаты, происхождение и историю мнений. Проверка срока grant до этой работы не удостоверяет полномочия в конце.

Перед новым принятием Store вновь вычисляет и сверяет пакет в текущей транзакции. После этого фиксируется свежий `authorization_time` и повторно проверяются coordinator и выбранные одобрения. Если выбранный grant истёк к этому моменту, попытка завершается отказом; другой голос автоматически не подставляется.

Успешное новое принятие сохраняет governance receipt schema 3. Квитанция закрепляет использованный пакет содержания вместе с политиками, авторством, coordinator, выбранными решениями и новой ревизией. Старые receipt schema 1 и 2 сохраняют свои исторические форматы. Это локальная история решения, без внешнего заверения SQLite или доказательства истинности статьи.

Действительность grants относится к записанному моменту авторизации внутри транзакции. Обещания, что они будут действовать ещё какое-либо время после него или после `COMMIT`, нет. Ход часов и владелец SQLite остаются частью доверенной среды.

## 10. Обновление политики и исторические повторы

Изменение политики содержания требует администратора и ожидаемого текущего поколения governance. В одной транзакции создаются следующее поколение содержания и следующее поколение governance. Прежние решения не действуют в новом поколении, даже если числовой результат отношений случайно совпал.

Администратор способен сузить опись, убрать часть требований или заменить более сильное отношение более слабым. Проверка формы не устанавливает, что такая политика достаточна. Изменение видно в истории и требует свежих решений, но специального внешнего утверждения ослабления в этом этапе нет. [Анализ изменения требования](requirement-delta.md) помогает рассматривать такие изменения отдельно; автоматической связи с управлением политикой сейчас нет.

| Повтор | Поведение |
| --- | --- |
| Точный повтор уже записанного решения с тем же operation ID | После текущей авторизации исходного reviewer grant и исключения contributors возвращает прежнее решение и его исторический пакет; не требует совпадения с сегодняшним пакетом |
| Новое мнение с новым operation ID | Требует текущего пакета и CAS последнего мнения; прежнее решение остаётся в истории |
| Повтор уже выполненного `accept` | После текущей авторизации coordinator и проверки ожидаемого поколения возвращает исторический факт |

Историческое принятие не получает новую квитанцию или пакет задним числом. Его read set не оценивается как новая правка после того, как собственные записи уже изменили базу. Историческое решение, возвращённое replay, также не становится действующим одобрением сегодняшнего пакета. Для нового действия нужен новый явно закреплённый предмет.

Для точного повтора решения, записанного до включения content gate, digest содержания остаётся отсутствующим. Это разрешённое чтение старого результата после текущей авторизации; schema и пакет задним числом не добавляются. Для повтора решения активного режима передаётся его прежний digest, в том числе после обновления политики. Новая операция в активном режиме всегда требует явного digest текущего пакета.

## 11. Команды

Команды работают с существующим workspace. Перед включением нужны governance, authorship, подходящие задания и административный credential в частном обычном файле с правами `0600`. Для решений и координации используются отдельные подходящие grants. Секрет передаётся через путь к файлу; его значение, хеш и SQLite не публикуются. Политика, scope, описания и цитаты являются публичными данными: секреты в них помещать нельзя. CLI сохраняет произвольные метаданные политики, чтобы её digest оставался воспроизводимым; автоматическое редактирование известных credential не заменяет выбор корректного публичного входа.

В примере ниже governance имеет поколение 2 до включения content gate. Переменные proposal, digest, artifact и пакета обозначают точные значения из своих результатов; это не готовый сценарий с универсальными ID.

~~~sh
python3 -m agentwiki content enable \
  --workspace "$CONTENT_WORKSPACE" \
  --credential /tmp/agentwiki-content-private/admin.credential \
  --policy "$CONTENT_POLICY_JSON" \
  --expected-policy-generation 2

python3 -m agentwiki content status \
  --workspace "$CONTENT_WORKSPACE" \
  --proposal "$CONTENT_PROPOSAL_ID"

python3 -m agentwiki governance review \
  --workspace "$CONTENT_WORKSPACE" \
  --credential /tmp/agentwiki-content-private/reviewer-a.credential \
  --proposal "$CONTENT_PROPOSAL_ID"

python3 -m agentwiki governance decide \
  --workspace "$CONTENT_WORKSPACE" \
  --credential /tmp/agentwiki-content-private/reviewer-a.credential \
  --proposal "$CONTENT_PROPOSAL_ID" \
  --artifact "$CONTENT_ARTIFACT_ID" \
  --verdict approve --rationale "Рассмотрен указанный пакет объявленных полей." \
  --expected-proposal-digest "$CONTENT_PROPOSAL_DIGEST" \
  --content-packet-digest "$CONTENT_PACKET_DIGEST" \
  --expected-policy-generation 3 \
  --operation content-review-a-01

python3 -m agentwiki governance observe \
  --workspace "$CONTENT_WORKSPACE" \
  --credential /tmp/agentwiki-content-private/coordinator.credential \
  --proposal "$CONTENT_PROPOSAL_ID" \
  --expected-policy-generation 3

python3 -m agentwiki governance accept \
  --workspace "$CONTENT_WORKSPACE" \
  --credential /tmp/agentwiki-content-private/coordinator.credential \
  --proposal "$CONTENT_PROPOSAL_ID" \
  --expected-policy-generation 3

python3 -m agentwiki content show \
  --workspace "$CONTENT_WORKSPACE" \
  --packet "$CONTENT_STORED_PACKET_ID"
~~~

Один вызов `decide` относится к одной записи и одному reviewer. Необходимые остальные мнения следуют из политики кворума; их не создаёт показанный вызов автоматически. При замене собственного последнего мнения передаётся `--previous-decision` с его точным ID. После `request_changes` новое `approve` также является явной заменой с CAS.

Обновление политики в исходном примере:

~~~sh
python3 -m agentwiki content policy \
  --workspace "$CONTENT_WORKSPACE" \
  --credential /tmp/agentwiki-content-private/admin.credential \
  --policy "$CONTENT_NEXT_POLICY_JSON" \
  --expected-policy-generation 3
~~~

После успешного изменения действуют новые поколения; для нового решения нужно получить новый статус, digest и номера. Повторная отправка прежних чисел не является переносом одобрения.

Прикладной сценарий запускается в новом пустом каталоге:

~~~sh
python3 -m agentwiki content-demo \
  --workspace /tmp/agentwiki-content-my-run-01 --workers 3
~~~

Фактические этапы и результаты опубликованного запуска перечислены в [отчёте](../../examples/content-gate/results/report.md): семь авторских заданий, шесть композиций, 16 этапов и 16 решений. Восемь ожидаемых отказов API и восемь заблокированных принятий сохранились отдельно. Один кандидат принят на ревизии 2 с квитанцией schema 3; основной журнал содержит 99 событий. Восемь [дополнительных CLI-команд](../../examples/content-gate/README.md) прочитали исторический пакет до и после обновления политики, сохранили его тело и прежнюю квитанцию. После CLI поколения содержания/governance равны 3/5, событий 101, ревизия осталась 2. Это обычный продуктовый сценарий с сохранёнными исходами, без измерения производительности или качества энциклопедии.

### 11.1. Как разбирать отказы

| Код или причина | Что проверить |
| --- | --- |
| `content_prerequisites_required` | Governance и authorship должны быть включены раньше содержания |
| `invalid_content_policy` | Строгую форму, непустые списки, точный комплект сторон и все соответствия обещаний |
| `content_packet_required` | У новой активной операции должен быть явный digest пакета |
| `content_packet_changed` | Получить текущий пакет и рассмотреть изменение оснований; не подменять ID без нового рассмотрения |
| `content_packet_blocked` | Посмотреть конкретные причины пакета; дополнительный голос не исправляет значение |
| `content_proposal_write_set` | Записи предложения должны точно покрывать административный комплект |
| `content_stale_read`, `content_query_changed` | Обновить предложение и его основания через авторский процесс |
| `content_relation_mismatch`, `content_relation_unresolved` | Сравнить извлечённые значения либо устранить неоднозначную или неподдержанную конструкцию |
| `content_promise_unresolved`, `content_promise_mismatch` | Проверить цитату, поле и закреплённые отношения обещания |
| `content_dependency_untracked` | Использованная при отображении зависимость должна входить в readset предложения |
| `content_packet_too_large` | Размер канонического пакета превысил разрешённую границу |

Причины пакета и ошибка команды имеют разные уровни. Например, непригодный пакет доступен для рассмотрения и закрепления `request_changes`, а попытка `approve` по нему получает `content_packet_blocked`. Ошибка авторизации или устаревшее поколение политики проверяются также по прежнему контракту governance.

## 12. Сколько агентов может участвовать

Процесс подготовки допускает несколько авторских задач и несколько рассматривающих процессов. Разделение ролей действует по стабильным principal, а не по числу потоков, окон модели или вызовов API.

Для примера с двумя авторами, одним интегратором, двумя внешними по отношению к авторству reviewer и отдельным coordinator потребуется не менее шести подходящих principal, если политика требует два одобрения и отдельную координацию. Вложенная интеграция добавляет участников происхождения и может уменьшать доступный круг проверяющих. Это арифметика выбранных ролей; число реально необходимых участников зависит от политики и состава предложения.

Можно запустить больше рабочих процессов, чем существует одновременно пригодных задач. Это не увеличит объём независимой работы или круг независимых проверяющих. Несколько процессов с одним credential используют общий допуск; несколько разных principal также не доказывают разных людей, моделей или независимость их суждений.

SQLite сериализует writers. Чтение, подготовка предложений и размышление внешнего агента могут идти параллельно; фиксация аренды, решения или принятия проходит через транзакции. Увеличение размера пула само по себе не даёт измеренного ускорения. При широких комплектах и общих read/query основаниях могут чаще возникать конфликты и необходимость пересборки.

## 13. Почему это полезно для портала документации

У параллельных авторов есть несколько разных видов расхождений: столкновение записей, устаревшее основание, несовместимые значения, пропущенное обещание и несогласие предметных проверяющих. Один механизм хранения версий не разрешает все эти случаи. Новый этап добавляет проверяемую связь между частью содержательного договора и разрешением нового принятия.

Для технического портала это применимо к узким конфигурационным контрактам: документированным перечням, значениям и отношениям с явными объявлениями. Администратор выбирает обязательную опись, авторы готовят материалы, интегратор объединяет их, проверяющие закрепляют один предмет, а Store предотвращает принятие известного текущего нарушения выбранных правил.

Для вики или энциклопедии общий вопрос сложнее. Там нужно подтверждать источники, контекст утверждения, дату, исключения, степень уверенности, предметные возражения и допустимость цитирования. Нынешний формат требует пары документа и литерального файла кода и не моделирует эти отношения. Он не является готовым контуром модерации Википедии или автоматически создаваемой LLM-вики.

Сходный принцип точного пакета и актуального решения можно развить для других предметов, но потребуются новые схемы, правила и основания. Например, связь утверждения с цитатой источника должна отдельно описать, что проверяется: совпадение фрагмента, подтверждение факта, выводимость из нескольких фрагментов или редакторское заключение. Эти свойства нельзя назвать одним `match` без определения процедуры.

## 14. Границы доверия и масштаба

| Ограничение | Следствие |
| --- | --- |
| До 16 артефактов в комплекте, 16 обязательств и 16 обещаний | Это конечная локальная область; пределы не измеряют ёмкость портала |
| До 1 МБ канонической политики и 4 МБ пакета | Превышение границы даёт отказ, а не частично положительное рассмотрение |
| В `status` до 100 метаданных сохранённых пакетов и отдельный полный счётчик | Это ограничение выдачи; исторический пакет запрашивается по точному ID через `show` |
| Прежние ограничения JSON, AST, глубины и размера текста | Неподдержанное или чрезмерное основание не должно превращаться в положительный результат |
| Опись задаёт администратор | Наличие всех существенных обещаний в ней не установлено |
| Цитата и поле сопоставлены декларативно | Правильность смыслового перевода требует предметного рассмотрения |
| Проверяются литеральные объявления | Поведение произвольной программы не доказано |
| Credential является локальным bearer-допуском | Личность и независимость экспертов не удостоверены |
| Владелец SQLite и часы доверенные | Прямое изменение базы или часов выходит за гарантии API |
| Внешние системы не входят в SQL-транзакцию | Git, источники и уведомления требуют отдельного протокола согласования |
| Хеши без внешнего заверения | Внутренняя согласованность не доказывает полноту истории и авторство человека |

Прошедший пакет не разрешает автоматическое исполнение предложенного кода или публикацию в отдельный внешний портал. Для этих действий нужны свои явно определённые условия и права.

## 15. Следующие шаги

1. **Управление полнотой политики.** Назначить предметного владельца описи, описать причины изменения и процесс внешнего рассмотрения удаления или ослабления требования. Сохранять сравнение поколений и связь с [разбором изменения требования](requirement-delta.md).
2. **Предметное рассмотрение.** Разделить формальную проверку, проверку перевода прозы в поля, проверку источников и вывод о поведении программы. Для каждого вида задать вход, квалификацию участников и способ разрешения возражений.
3. **Внешняя идентификация.** Связать principal с удостоверенной учётной записью и управлением секретами. Явно определить, что считать независимостью людей, организаций или моделей; различие ID недостаточно.
4. **Пакеты для документальных источников.** Ввести версии и сохранённые фрагменты источников, даты применимости и конкретные типы связей утверждений. Проверку доступности URL хранить отдельно от доказательства содержания.
5. **Маршрутизация по разделам.** [Пятнадцатый этап](content-routing.md) реализует каталог schema 2 и транзитивное замыкание пересечений комплектов. Отказ при непокрытой записи сохраняется; одно удачное правило не освобождает соседний раздел. Далее оценить размеры связных компонентов и необходимость более узкого договора проверки; полезность такого перехода требует предметных оснований.
6. **Работа с конфликтами.** Дать участникам понятное объяснение изменённого основания, новый пакет и явный запрос свежего рассмотрения. Не переносить голоса на изменившийся предмет молча.
7. **Долговечная публикация.** Определить протокол SQL → Git → портал, повторяемые операции и восстановление после частичного отказа. Текущая квитанция подтверждает принятие в базе, а не завершение всех внешних записей.
8. **Оценка на реальных материалах.** Собрать независимо размеченные случаи с явно установленными правилами, определить ошибки и стоимость работы. Измерять задержки, конфликты и очередь при конкретном пуле; не выдавать лимиты формата или количество workers за экспериментальную производительность.

Общий план развития находится в [roadmap](roadmap.md). Следующая предметная возможность должна сохранять уже разделённые свойства: происхождение, разрешения, актуальность основания, содержание выбранного договора и исторический факт решения.
