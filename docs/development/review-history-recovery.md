# Восстановление ответа и обнаружение аудитов истории

Восемнадцатый этап добавляет два способа чтения сохранённых результатов [пошагового аудита](review-history-audit.md): восстановление ответа по известному `operation_id` и постраничный каталог начатых аудитов. Первый нужен после потери ответа `start` или `advance`; второй помогает найти аудит, когда клиент не сохранил его ID.

Оба интерфейса совещательные. Они не создают новый голос, checkpoint или разрешение принятия. `Store.accept` не читает строки аудита, предел continuity остаётся 64 перехода, а действующее возражение не исчезает после восстановления или обнаружения исторического результата.

Слово «восстановление» здесь означает получение результата уже подтверждённой SQLite-транзакции после потери ответа клиентом. Исправление повреждённой базы, резервное копирование и восстановление после потери хранилища в этот этап не входят.

Практические материалы: [пример и команды](../../examples/review-history-recovery/README.md), [отчёт выполнения](../../examples/review-history-recovery/results/report.md). Конкретные ID, количества и исходы запуска берутся из отчёта; описание ниже задаёт договор интерфейса.

## 1. Две разные неопределённости клиента

После успешного `start` приложение сохраняет заголовок, начальный checkpoint, голову, карту операции и событие запуска в одной транзакции. Ответ клиенту передаётся позднее. Клиент может потерять этот ответ, хотя состояние уже сохранено.

Для `advance` ситуация похожа: checkpoint и новая CAS-голова уже существуют, но клиент продолжает помнить только прежнюю позицию. Отправка новой операции с прежней ожидаемой головой закономерно получит конфликт.

Обычный точный replay этапа v0.17 решает эту проблему, когда клиент сохранил весь исходный запрос. Но у него могут остаться только имя операции и административный credential. Самостоятельно восстанавливать прежние поколение политики, digest цели, predecessor и limit из текущего живого состояния нельзя: они могли измениться.

Есть и другая задача: человек открывает рабочую область и не знает ни audit ID, ни operation ID. Здесь нужен обозримый каталог уже начатых аудитов, а не угадывание параметров старой операции.

| Что сохранилось у клиента | Подходящий интерфейс |
| --- | --- |
| Весь исходный запрос `start` или `advance` | Прежний точный replay с тем же operation ID |
| Только исходный operation ID и действующий исходный административный допуск | `history-audit recover` |
| Audit ID | `history-audit show` |
| Ни одного ID аудита | `history-audit list`, затем `show` нужного ID |
| Потеряна сама база или повреждены исходные строки | Эти интерфейсы не заменяют отдельный процесс восстановления хранилища |

## 2. Решение ADR

**Контекст.** Исторический результат должен оставаться связанным с первоначальным запросом. Нельзя подменять потерянную цель нынешним пакетом или повторно продвигать голову только ради повторной выдачи ответа.

**Решение для recover.** Загрузить ограниченную карту уже завершённой операции, восстановить исходный запрос из неизменяемых объектов, сверить его digest и воспользоваться прежним механизмом replay. Требовать текущий исходный административный grant. Не записывать новый результат и не создавать событие восстановления.

**Решение для каталога.** Использовать существующие события `review_history_audit_started` с устойчивым порядком `events.seq`. При первом чтении закрепить верхнюю границу состава, затем возвращать ограниченные страницы. Проверять заголовок, начальную точку и текущую голову каждого обрабатываемого аудита. Ошибку отдельной записи возвращать отдельно, продолжая курсор за ней.

**Последствия.** Повтор выдачи не меняет историю. Каталог не требует полной загрузки всех событий в память. Цена — явные ограничения: доверенная SQLite, непроверяемая внешняя полнота журнала и головы, наблюдаемые отдельно на каждой странице.

**Формат хранения.** Форматы заголовка аудита и checkpoint этапа v0.17 сохраняются. Новая схема добавляет индекс `events(type,seq)`; отдельного формата «восстановленного аудита» и миграции прежних audit ID нет.

## 3. Как работает recover

Вызов принимает только `operation_id` и credential. Клиент не передаёт новый target, поколение политики, predecessor или limit.

В одной транзакции чтения выполняется следующая последовательность:

1. Проверить текущую административную авторизацию.
2. Найти карту завершённой операции по точному operation ID.
3. Проверить размеры и типы метаданных, допустимое действие `start` или `advance`, формат grant ID, digest и адреса объектов.
4. Проверить совпадение текущего административного grant с grant исходной операции.
5. Загрузить и проверить неизменяемые заголовок, адресованный checkpoint и их исходные и целевые основания.
6. Восстановить исходный запрос из этих объектов и сравнить его digest с картой операции.
7. Повторно проверить карту через существующий механизм idempotency и вызвать прежний `_replay`.
8. После последнего наблюдения заново проверить текущую административную авторизацию и вернуть envelope replay без дальнейшего пересчёта результата.

Такой порядок использует зафиксированные исторические данные. Текущий пакет proposal и нынешняя CAS-голова не заменяют параметры исходной операции.

### 3.1. Откуда берутся параметры

| Исходное действие | Восстанавливаемое поле | Источник |
| --- | --- | --- |
| `start` | `decision_id` | Исходное решение в заголовке |
| `start` | `expected_policy_generation` | Закреплённое целевое поколение governance |
| `start` | `expected_target_packet_digest` | Digest закреплённого целевого пакета |
| `advance` | `audit_id` | Проверенный заголовок |
| `advance` | `expected_checkpoint_id` | `previous_checkpoint_id` сохранённого результата шага |
| `advance` | `limit` | `requested_limit` этого checkpoint |
| Оба | `administrator_grant_id` | Текущий авторизованный grant, совпавший с исходным |

Сохранённый digest запроса нужен для проверки связи этих полей с уже записанной операцией. Недостаточно найти checkpoint с похожим состоянием или взять нынешний limit по умолчанию.

### 3.2. Что возвращается

`recover` возвращает прежний envelope v0.17 напрямую:

- `audit` — тот же неизменяемый заголовок.
- `checkpoint` — результат именно восстанавливаемой операции.
- `replayed=true`.
- `current_checkpoint_id` — текущая голова этого аудита в транзакции чтения.
- Прежние поля ограничений и совещательные признаки.

Голова могла продвинуться после исходной операции. Поэтому `checkpoint.checkpoint_id` и `current_checkpoint_id` могут различаться. Это нормальный исторический результат, а не восстановление головы назад. Весь JSON-ответ не обязан совпадать побайтно с первым ответом: текущие метаданные обращения изменяются.

~~~mermaid
flowchart LR
    O[Сохранённый operation ID] --> A[Текущий исходный admin grant]
    A --> M[Ограниченная карта операции]
    M --> I[Неизменяемые заголовок и checkpoint]
    I --> D[Восстановленный запрос и сверка digest]
    D --> R[Прежний replay]
    R --> F[Свежая проверка полномочий]
    F --> E[Исторический checkpoint и текущая голова]
~~~

### 3.3. Нет новой записи

Восстановление не вызывает новый `start` или `advance`, не добавляет operation map, checkpoint или событие и не меняет голову. Успешный результат сообщает о сохранённом факте. Он не утверждает, что операция была выполнена второй раз.

Обычные вызовы Store работают с транзакцией чтения. Создание индекса относится к инициализации схемы; оно не является событием восстановления пользовательской операции.

## 4. Полномочия и ошибки recover

Привязка к исходному grant ID сохраняется. Действующий новый допуск того же principal не становится исходным допуском старой операции. Отзыв или истечение исходного допуска нельзя обойти знанием operation ID.

| Ситуация | Результат |
| --- | --- |
| Не найден operation ID в выбранной базе | `audit_operation_not_found` |
| Некорректный входной operation ID | `audit_invalid_input` |
| Действующий административный grant отличается от исходного | `audit_idempotency_conflict` |
| Нарушены метаданные, адреса, действие, индекс checkpoint, ссылки или digest запроса | `audit_record_invalid` |
| Credential не даёт текущих административных полномочий | Ошибка действующей авторизации governance |
| Сохранённый результат согласован и исходный grant действует | Исторический replay с текущей головой |

Неизвестный operation ID не создаёт операцию автоматически. Он означает отсутствие такой записанной операции в выбранном хранилище. Клиент сначала сверяет рабочую область и собственный журнал запросов; новый запрос является самостоятельным действием.

Локальный bearer credential подтверждает владение допуском. Он не удостоверяет личность человека, независимость модели или внимательное рассмотрение документа. Публичные `show` и `list` позволяют читать доступный исторический материал, но не заменяют авторизацию `recover`, `start` или `advance`.

## 5. Каталог начинается с событий запуска

Каталог использует только события типа `review_history_audit_started`. Их `seq` берётся из существующего `INTEGER PRIMARY KEY AUTOINCREMENT` таблицы `events`. Между такими событиями могут находиться другие события, поэтому номера каталога не обязаны идти подряд.

Индекс `(type,seq)` позволяет выбрать нужный диапазон по типу и номеру. В каталоге нет фильтра по proposal; proposal ID возвращается в каждой успешно проверенной записи.

Первый вызов по умолчанию имеет параметры:

~~~text
after_seq=0
snapshot_max_seq=None
limit=10
~~~

Приложение считывает `MAX(seq)` именно среди событий запуска аудита и сохраняет это число как `snapshot_max_seq` ответа. При отсутствии таких событий граница равна нулю. Общий максимум всех событий Store не используется как граница состава каталога.

### 5.1. Правила продолжения

- `limit` — целое число от 1 до 20.
- `after_seq` и переданная граница — неотрицательные целые числа.
- При `after_seq > 0` граница `snapshot_max_seq` обязательна.
- Должно выполняться `0 <= after_seq <= snapshot_max_seq`.
- Переданная граница не может быть выше текущего максимума событий запуска.
- Для продолжения используются оба поля возвращённого `next_cursor` без замены границы новым текущим максимумом.

Вход, нарушающий этот договор, получает `audit_invalid_input`. Клиент может начать новый просмотр с нуля, чтобы увидеть более поздние аудиты. У старого просмотра остаётся прежняя граница.

### 5.2. Ограниченное чтение страницы

Для диапазона `after_seq < seq <= snapshot_max_seq` читаются не более `limit + 1` строк метаданных: seq, тип и размер payload. Последняя возможная строка нужна только для определения `has_more`.

Payload загружается не более чем для `limit` обрабатываемых событий. Каждое тело ограничено 4 000 байтами и должно иметь каноническую форму события запуска. Затем проверяются адреса аудита и начального checkpoint, заголовок с закреплёнными основаниями и текущая голова.

Бюджет страницы относится к событиям, а не ко всем SQL-чтениям: для каждой записи дополнительно выполняются ограниченные проверки объектов v0.17. Каталог не проходит всю сырую историю переходов и не доказывает её завершённость.

### 5.3. Ошибка записи не останавливает курсор

Повреждённый payload, неверная ссылка или недоступный проверяемый объект дают запись в `errors`. Она содержит `event_seq` и фиксированный код `audit_record_invalid`; `audit_id` добавляется только если удалось получить адрес допустимого формата. Сырой payload и произвольное сообщение исключения в такую запись не переносятся.

Курсор продвигается за последнее обработанное событие, включая ошибочное. Иначе одна повреждённая запись могла бы навсегда удерживать клиента на одной странице.

Нужно различать ошибку отдельной записи и отказ всей страницы. Например, отсутствие нужного индекса или некорректные общие параметры не превращаются в обычную пустую страницу.

## 6. Состав ответа каталога

| Поле | Значение |
| --- | --- |
| `rules_version` | Версия правил `review-history-recovery-1` |
| `after_seq`, `snapshot_max_seq`, `limit` | Применённые параметры страницы |
| `scanned_count` | Число обработанных событий, без строки lookahead |
| `returned_count` | Число успешных элементов `entries` |
| `entries` | Проверенные записи с кратким состоянием головы |
| `errors` | Ошибки отдельных обработанных событий |
| `has_more` | Найдена следующая строка метаданных в закреплённом диапазоне |
| `next_cursor` | Следующие `after_seq` и `snapshot_max_seq` либо `null` |
| `heads_observed_at` | Локальная временная отметка наблюдения страницы в epoch |

Для обычной обработанной страницы `scanned_count = returned_count + len(errors)`. Пустой `entries` при ненулевом `errors` не означает отсутствие аудитов. Продолжение определяется `next_cursor`, а не числом успешных элементов.

Успешный элемент содержит:

- `event_seq`, `audit_id` и `proposal_id`.
- `source_decision_id` и полный четырёхполевой pin `target_packet`.
- Исходное и целевое поколения governance.
- `start_operation_id` и `initial_checkpoint_id`.
- `observed_head`: `checkpoint_id`, индекс, состояние, накопленное число успешно пройденных переходов и четырёхполевой `cursor`.

Ответ и успешные элементы сохраняют `advisory_only=true`, `acceptance_authority=false`, `authority_evaluated=false`. Это признаки исторического объяснения, а не результаты проверки нынешнего права принять proposal.

## 7. Что именно замораживает snapshot

Граница фиксирует состав допустимых событий запуска. Если после первой страницы появился ещё один аудит с большим seq, он не попадёт в продолжение старого просмотра.

При этом голова уже существовавшего аудита может измениться. Каждая страница читается в собственной SQL-транзакции; повтор первой страницы с той же границей может показать тот же audit ID с более поздним `observed_head`.

| Объект | Поведение между страницами |
| --- | --- |
| Верхняя граница seq | Сохраняется в курсоре |
| Более поздний запуск аудита | Исключён из прежнего диапазона |
| Заголовок уже включённого аудита | Имеет прежний неизменяемый предмет |
| Текущая голова включённого аудита | Наблюдается заново при чтении страницы |
| Live grant, quorum и candidate | Каталог не устанавливает их действительность |

`heads_observed_at` помогает описать время наблюдения страницы. Это локальные часы, а не внешняя временная аттестация и не единый момент снимка всего многостраничного каталога.

Курсор — закладка чтения, не ACL, credential или подпись. Передача его другому локальному читателю не передаёт административный допуск. Сам интерфейс не добавляет сетевой сервер или многопользовательскую систему разграничения доступа.

## 8. Практика: восстановить потерянный ответ

Команды выполняются из корня checkout против существующей рабочей области с `state.sqlite3`. В демонстрационных примерах это обычно каталог `private/`. Credential хранится отдельным закрытым POSIX-файлом; его содержимое не передаётся в аргументе CLI.

### Шаг 1. Сохранить operation ID до отправки

Клиент заранее назначает уникальный ID и записывает его в собственный журнал. Например, `audit-start-001` и `audit-advance-001` — разные операции. Сам ID не является секретом и не доказывает полномочия.

### Шаг 2. Получить существующий результат

~~~bash
python3 -m agentwiki history-audit recover \
  --workspace /tmp/my-agentwiki/private \
  --credential /tmp/my-agentwiki/private/admin.credential \
  --operation audit-start-001

python3 -m agentwiki history-audit recover \
  --workspace /tmp/my-agentwiki/private \
  --credential /tmp/my-agentwiki/private/admin.credential \
  --operation audit-advance-001
~~~

Для start восстанавливается начальная точка. Для advance — результат выбранного шага. В обоих случаях ответ содержит нынешнюю голову отдельно от восстановленного checkpoint.

### Шаг 3. Проверить текущую позицию перед новым шагом

~~~bash
python3 -m agentwiki history-audit show \
  --workspace /tmp/my-agentwiki/private \
  --audit AUDIT_ID
~~~

Если состояние `pending`, новый `advance` использует текущую голову как `--expected-checkpoint` и новый operation ID. Если аудит терминальный, recover не открывает его заново. Для точного повторного чтения старого результата используется прежний operation ID.

Нынешние `governance observe` и `governance accept` остаются отдельным действующим процессом. Историческое восстановление не предоставляет нового разрешения записи.

## 9. Практика: найти аудит и продолжить страницы

Первая страница:

~~~bash
python3 -m agentwiki history-audit list \
  --workspace /tmp/my-agentwiki/private \
  --limit 2
~~~

Из ответа берутся оба поля `next_cursor`. Если он не `null`, следующая команда использует именно эти значения:

~~~bash
python3 -m agentwiki history-audit list \
  --workspace /tmp/my-agentwiki/private \
  --after-seq NEXT_AFTER_SEQ \
  --snapshot-max-seq SNAPSHOT_MAX_SEQ \
  --limit 2
~~~

Чтение продолжается до `next_cursor=null`, включая страницы, где есть ошибки. Размер следующей страницы можно изменить в пределах 1–20, сохранив возвращённые курсор и границу.

Для обновлённого состава начинается новый просмотр с нуля. Для подробностей выбранного элемента используется `show --audit AUDIT_ID`; для административного восстановления известной операции — `recover --operation OPERATION_ID` с исходным действующим допуском.

Публичный каталог не фильтрует данные по principal или proposal. Клиент выбирает нужный proposal из возвращённых полей; курсор не даёт гарантии изоляции чужих записей.

## 10. Store API и исходники

| Store API | Смысл |
| --- | --- |
| `continuity_audit_recover(operation_id, *, credential)` | Восстановить точный сохранённый replay исходной операции |
| `continuity_audit_catalogue(*, after_seq=0, snapshot_max_seq=None, limit=10)` | Прочитать ограниченную публичную страницу запусков |

Ядро располагается в [review_history_recovery.py](../../agentwiki/review_history_recovery.py), публичные обёртки — в [Store](../../agentwiki/store.py), команды — в [review_history_audit_cli.py](../../agentwiki/review_history_audit_cli.py). Базовая логика проверки заголовков, checkpoint и replay остаётся в [review_history_audit.py](../../agentwiki/review_history_audit.py).

## 11. Воспроизводимый сценарий и граница демонстрации

Новый обычный сценарий запускается на пустом пути:

~~~bash
python3 -m agentwiki history-recovery-demo \
  --workspace /tmp/agentwiki-history-recovery-example-01 \
  --workers 3
~~~

Демонстрация моделирует потерю ответа так: отдельный CLI-процесс завершает операцию, а вызывающий процесс отбрасывает stdout. Затем результат извлекается по заранее сохранённому operation ID. Это конкретная модель потери ответа; она не означает испытание сетевого отказа, аварийного завершения процесса или восстановления повреждённого файла SQLite.

Предусмотрены восстановление start и advance, просмотр исходного состава из трёх аудитов и более поздний четвёртый запуск, исключённый из старого диапазона. Повтор страницы показывает, как у того же audit ID может измениться голова при прежнем составе каталога. Эти числа задают устройство сценария, а результаты исполнения и реальные счётчики должны подтверждаться [отчётом](../../examples/review-history-recovery/results/report.md).

Редакционный путь отдельно показывает явное возражение C, последующую свежую замену мнения на `abstain` и обычное принятие с квитанцией schema 4. Восстановление и каталог не превращают старое возражение в одобрение и не заменяют свежие проверки.

`--workers 3` задаёт локальный пул программируемых workers. Это не три независимые LLM, не три человека и не измеренная ёмкость промышленного портала. Предлагаемый код сохраняется как данные. Истинность документации и качество внешней экспертизы таким сценарием не устанавливаются.

Публичный отчёт отделяется от частных SQLite и credential-файлов. Исторические запуски сохраняются отдельно. Человекочитаемое время приводится в Europe/Berlin, технические шкалы UTC/epoch указываются явно.

## 12. Стоимость, доверие и полнота

Для recover число адресованных объектов ограничено: карта одной операции, заголовок, checkpoint, его необходимый предшественник и закреплённые основания. Он не пересчитывает весь пройденный префикс сырых переходов. Размеры объектов и правила проверки наследуются от v0.17; восстановленный запрос ограничен 4 000 байтами.

Для страницы каталога обрабатывается не более 20 событий и одна дополнительная строка метаданных. Полный просмотр `A` событий требует порядка `O(A)` обработок записей, плюс работа индексированных запросов и проверка ограниченных объектов каждой записи. Это не обещание конкретной задержки или пропускной способности.

При первом открытии существующей базы создание нового индекса `(type,seq)` обрабатывает её события. Для большой базы эта начальная работа может быть существенной; она выполняется отдельно от чтения страниц. Предел в 20 обрабатываемых событий страницы относится к работе с уже подготовленным индексом и не ограничивает стоимость его построения.

Каталог основан на записанных событиях запуска. Он не находит аудит, если доверенный владелец базы удалил его событие, не доказывает отсутствие пропущенных событий и не предоставляет внешнего доказательства полноты. При повреждении связанных записей интерфейс показывает обнаруженную ошибку, но не ремонтирует её.

Хеши проверяют внутренние связи сохранённых байтов. Владелец SQL остаётся доверенным и может изменить исходные строки и digests. `AUTOINCREMENT` задаёт порядок нормальных вставок, но не создаёт внешне заверенный журнал. Общей транзакции между SQLite, Git и отчётом нет.

Сохранённый target не означает действующий grant reviewer, текущую голову мнения, кворум или истинность текста. Повторная выдача одного результата не является независимой проверкой. Известные барьеры политики, неопределённая длинная история и действующие veto продолжают оцениваться обычным governance независимо от каталога.

## 13. Следующие шаги

1. Добавить в клиент явное сохранение operation ID до отправки и раздельное отображение восстановленного checkpoint и нынешней головы.
2. Сохранять оба поля курсора страницы вместе с локальным контекстом просмотра; отдельно предлагать начало нового состава.
3. Показывать ошибки отдельных событий рядом со счётчиками, не скрывая их за пустым списком успешных элементов.
4. Разработать самостоятельный процесс резервного копирования, проверки целостности и восстановления базы, если он требуется эксплуатации. Не приписывать его гарантий recover.
5. Для сетевого портала определить аутентификацию, политику чтения и границы доступа отдельно от локального публичного каталога.
6. Если нужен внешне проверяемый журнал, определить источник доверенного обязательства, полноту диапазонов, версии проверяющего и политику восстановления. Хеши нынешних локальных записей этот договор не заменяют.
