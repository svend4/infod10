# Составное предложение документа и кода

Шестой этап развивает [досье отдельного предложения](proposal-dossiers.md): несколько авторов могут подготовить разные файлы, интегратор объединяет их в одно новое предложение, а редактор получает материал по всем его записям из общих наблюдённых оснований. [Практический пример](../../examples/composed-review/results/report.md) сохраняется отдельно от прежних запусков.

Реализация состоит из двух операций: `Store.compose` создаёт составное предложение в runtime, `review-set` формирует вспомогательный набор рассмотрения. Составление не принимает знания; набор рассмотрения не даёт разрешения на принятие. Внешние LLM, подтверждённые роли и обязательная редакционная политика пока не подключены.

## 1. Какой разрыв найден

Автор документа и автор кода могут независимо изменить связанные файлы. Досье пятого этапа связывает одну запись предложения с одним редакторским пакетом. Если предложение изменяет несколько файлов, остальные `writes` остаются непокрытыми. Простое объединение отдельных досье не решает проблему: они могли получить разные runtime-снимки, разные состояния журнала и разные последние решения.

Для страницы API и клиентского примера важно ответить на четыре вопроса:

1. Какие точные предложения авторов вошли в общую правку?
2. Совместимы ли их прочитанные основания и пересекаются ли записи?
3. Представлен ли каждый изменяемый файл соответствующим редакторским пакетом?
4. Сохранились ли основания и последние решения при повторном рассмотрении?

Эти вопросы касаются происхождения и актуальности. Совместное наличие документа и кода ещё не устанавливает, что их свободный текст и поведение согласованы по смыслу. Для такого вывода нужны содержательное рассмотрение и отдельные основания.

## 2. Контур работы

~~~mermaid
flowchart TD
    S[Один принятый снимок] --> D[Автор документа]
    S --> C[Автор кода]
    D --> PD[Неизменяемое предложение документа]
    C --> PC[Неизменяемое предложение кода]
    PD --> I[Интегратор: точные ID и digests]
    PC --> I
    I --> P[Новое составное предложение]
    P --> F[Новая формальная review]
    P --> R[Один runtime-контекст]
    J[Один снимок редакторского журнала] --> V[Рассмотрение всех writes]
    R --> V
    B[Явные связи: файл, пакет, текущая пара] --> V
    V --> H[Материал для человека]
    H --> N[Обновление оснований или отдельное решение]
~~~

Два снимка относятся к двум базам: runtime читается один раз, затем журнал читается один раз. Общей транзакции между ними нет. Во время и после наблюдения решения могут измениться. Поэтому результат сохраняет наблюдённые данные и предоставляет повторную оценку; он не служит транзакционным условием `Store.accept`.

## 3. Составление в Store

### 3.1. Задание интегратора

Роль `integrator` ограничена составлением предложений документов и кода. Имя роли — локальное правило API; оно не удостоверяет личность и не выдаёт внешних полномочий. Интегратор работает через задачу, аренду и fencing token, как остальные авторы.

Неизменяемый payload задания заранее фиксирует компоненты и пояснение:

~~~json
{
  "components": [
    {"proposal_id": "PROPOSAL_DOCUMENT", "digest": "SHA256_DOCUMENT"},
    {"proposal_id": "PROPOSAL_CODE", "digest": "SHA256_CODE"}
  ],
  "rationale": "Совместно рассмотреть справочник и пример клиента."
}
~~~

Значения в примере — обозначения, их нужно заменить фактическими ID и SHA-256. Передача одного ID без digest не фиксирует заявленное содержание компонента. Изменить состав сохранённого задания задним числом нельзя: для другого состава требуется новое задание.

### 3.2. Транзакционные условия

`Store.compose(task_id, worker, token)` использует только уже сохранённый payload задания. В одной транзакции записи операция проверяет действующую попытку, указанные компоненты, их digests, статус `proposed`, фактические read sets, scoped queries и текущие инварианты. Составление отклоняет повторяющиеся записи файлов и несовместимые ожидания по общим чтениям или запросам. Затем проверяются форма и глобальные инварианты объединённой правки. Компонент с устаревшим основанием не становится актуальным от включения в общую правку.

Операция принимает от 1 до 32 разных компонентов и ограничена 100 записями и объёмом составляемых данных до 1 МБ. Эти пределы защищают ограниченный локальный интерфейс; они не являются измеренной ёмкостью по числу агентов. Предложения claims не входят в допустимые компоненты интегратора. Повторяющийся `write_id` отклоняется даже при одинаковом содержимом.

Результат — новый proposal с собственными ID и digest. Его обычный payload содержит объединённые `readset`, `queries`, `writes` и строковое `rationale`. Внутри `rationale` канонический JSON фиксирует `text` и точный перечень `components`: `proposal_id`, `digest` и отсортированные `write_ids` каждого источника. Таким образом, digest нового proposal фиксирует и отображение исходных предложений на файлы. Отдельная таблица `proposal_components` сохраняет эти связи.

Исходные предложения остаются `proposed`. Их прежние formal reviews не переносятся на новый digest. Для составного предложения требуется собственная `Store.review`, а принятие по-прежнему выполняется отдельным `Store.accept` с повторной проверкой оснований и инвариантов. Отсутствие пересечения путей не доказывает выполнение общих ограничений или согласованность содержания.

### 3.3. Повтор завершённого задания

Повтор того же успешно завершённого задания возвращает его сохранённый результат. Проверка этого повтора предшествует проверке текущей свежести компонентов: позднейшее изменение знаний не должно создавать вторую копию уже сохранённого результата или лишать исполнителя возможности узнать результат прежней операции.

Это возвращение исторического результата. Его допустимость для нового принятия определяют текущая review и транзакционная проверка `accept`. Новое выполнение с другим составом или пояснением требует нового задания.

## 4. Общий runtime-контекст

`Store.proposal_context` захватывает предложение, фактические основания, формальную review и связанные данные в одной транзакции чтения. Для составных предложений контекст schema 2 дополнительно содержит зафиксированные компоненты. Связи сверяются с перечнем, включённым в `rationale` составного proposal.

Компоненты перечислены в исходном порядке, с позицией от 1. Контекст содержит ссылки, digests и `write_ids`, но не полные payloads исходных предложений. Поэтому экспортированный набор сам по себе не позволяет полностью пересчитать хеши каждого исходного proposal. Проверка оригиналов выполняется внутри Store; экспорт сохраняет наблюдённые ссылки без удостоверения их внешнего авторства.

Ранее сохранённые досье с runtime-контекстом schema 1 продолжают загружаться. Они остаются историческими снимками без нового поля компонентов; их содержание не переписывается ради новой схемы. Обновление формата не переносит старые одобрения на составное предложение.

Общая ревизия нужна для описания наблюдения. Её изменение само по себе не означает, что все материалы устарели: значение имеют конкретные чтения, существенные запросы, зафиксированное происхождение компонентов и последние рассматриваемые решения. Позднейший статус исходного предложения не входит в экспортируемую связь и отдельно не перечитывается при оценке набора; актуальность объединённой правки проверяется по её собственным основаниям.

## 5. Полное покрытие записей

Вход `review-set` — список явных связей:

~~~json
[
  {
    "artifact_id": "docs/reference.md",
    "packet_id": "PACKET_DOCUMENT",
    "pair": {"before": {}, "after": {}, "sources": {}}
  },
  {
    "artifact_id": "code/client_config.py",
    "packet_id": "PACKET_CODE",
    "pair": {"before": {}, "after": {}, "sources": {}}
  }
]
~~~

Пустые объекты здесь обозначают места полных значений [формата смысловой пары](semantic-corpus.md); это схема расположения полей, а не исполняемый пример. Сохранённый сценарий содержит полные входы.

Каждый `artifact_id` должен относиться к записи выбранного предложения. Неизвестный или повторно указанный артефакт считается ошибкой входа. Пропущенная запись остаётся видимым блокирующим препятствием. Таким образом, неполное рассмотрение нельзя представить как полное посредством молчаливого исключения неудобного файла.

Текущая реализация связывает правки существующих документов и кода. Для каждого файла `before.text` должен буквально совпасть с текущим шаблоном, а `after.text` — с предлагаемым. Новые файлы, claims и иные формы содержательного покрытия требуют отдельного протокола и сейчас не получают готового основания по умолчанию. Список ограничен 100 связями; пустой список сохраняет явное отсутствие покрытия.

Один пакет разрешается явно указать для нескольких записей, если входы проходят проверки. Такое повторное использование остаётся видимым; оно не создаёт дополнительных независимых рассмотрений или голосов. Число покрытых файлов и число разных пакетов нужно интерпретировать отдельно.

## 6. Что сохраняется один раз

Набор содержит общий runtime-контекст и общий экспорт редакторского журнала. Для каждого файла сохраняются его связь, текущая пара, проверка шаблонов, редакторская оценка и объясняющие причины. Общие снимки не дублируются внутри отдельных независимых досье.

Вложенная запись каждого файла сохраняет частичное покрытие, унаследованное от механизма досье: сама по себе она не представляет остальные файлы предложения. Поэтому локальное `uncovered_writes` не следует считать итогом для всего набора. Полноту определяет общее `observation.coverage`, готовность всего материала — общее `observation.state`, а действующее состояние отдельного файла — `observation.entry_summaries`. Поле `entry_coverage_scope` явно фиксирует это различие. Например, замечание по коду блокирует общий набор и сводку кода, сохраняя документ текущим при отсутствии других препятствий.

Это устраняет смешение наблюдений при формировании одного набора. Оно также уменьшает повторное сохранение общих данных. Полный журнал всё ещё захватывается целиком, а часть проверок структуры повторяется для каждого файла. Итоговый JSON ограничен 25 МБ; набор не является выборочным промышленным индексом или распределённым согласованным снимком.

Структурированные поля пары вводятся явно. Они не извлекаются из Markdown или Python и не считаются подтверждёнными совпадением `text`. Например, равенство 30 секунд и 30000 миллисекунд относится к указанным значениям. Оно не доказывает корректность алгоритма клиента, полноту инструкции или отсутствие противоречия между двумя файлами.

Сохранённый JSON получает собственные идентификатор и digest. Существующий файл результата не перезаписывается. Контрольная сумма помогает проверить соответствие сохранённых данных; без доверенного внешнего заверения она не доказывает авторство или полноту истории.

## 7. Повторная оценка

При `review-set recheck` явно передаются текущие связи с парами. Runtime снова захватывается один раз, журнал — один раз. Сравнение объясняет изменение общих оснований и состояние каждого файла.

Состав связей `artifact_id → packet_id` должен остаться тем же. Пара может измениться, и тогда объясняется устаревание; переназначение пакета или добавление другого файла требует создания нового набора. Такой порядок сохраняет предмет прежнего рассмотрения.

| Изменение | Ожидаемая интерпретация |
|---|---|
| Изменился прочитанный claim или существенная выборка | Основание предложения больше не то же самое |
| Изменился зафиксированный перечень компонентов | Сохранённое происхождение больше не совпадает |
| Изменилась последняя формальная review | Формальное основание набора изменилось |
| Появилось новое последнее решение по выбранному пакету | Обновилась редакторская позиция по соответствующему файлу |
| Изменились текущая пара, правила или политика | Прежняя оценка относится к прежнему входу или процедуре |
| Принята посторонняя правка вне объявленных зависимостей | Одна только новая revision не делает набор устаревшим |
| Изменился посторонний пакет | Его решения не переносятся на рассматриваемые файлы |

Итоговые состояния `current_for_human_review`, `needs_refresh` и `blocked` описывают вспомогательный материал. Первое означает согласованность наблюдённых оснований для передачи человеку; человеческое заключение этим не создаётся. Нерешённое возражение или непокрытая запись не исчезают при объединении файлов. Отсутствие человеческого решения остаётся явным и не выдаётся за состоявшееся ревью.

Во всех результатах сохраняются `requires_human_review=true` и `auto_accept=false`. Повторная оценка не добавляет решений, не принимает предложения и не исполняет предлагаемый код.

Общие причины изменения включают `proposal_changed`, `runtime_basis_changed`, `formal_review_head_changed`, `components_changed`, `proposal_status_changed`, смену правил и `artifact_review_changed`. В `per_artifact_changes` видны изменение пакета, последних решений, привязки шаблонов, редакторской оценки и текущего входа. Флаг `journal_snapshot_changed` отдельно показывает изменение захваченного журнала; посторонняя запись может изменить его без устаревания выбранных оснований.

## 8. Команды

Самостоятельный прикладной сценарий запускается из корня checkout в новом пустом каталоге:

~~~sh
python3 -m agentwiki review-set-demo \
  --workspace /tmp/agentwiki-review-set-my-run-01 \
  --workers 3
~~~

Для своих существующих runtime и журнала используйте сохранённый JSON связей:

~~~sh
python3 -m agentwiki compose \
  --workspace "$RUNTIME_WORKSPACE" \
  --task "$INTEGRATOR_TASK_ID" \
  --worker "$INTEGRATOR_WORKER" \
  --token "$LEASE_TOKEN"

python3 -m agentwiki review-set create \
  --workspace "$RUNTIME_WORKSPACE" \
  --journal "$EDITORIAL_DB" \
  --proposal "$COMPOSED_PROPOSAL_ID" \
  --bindings "$BINDINGS_JSON" \
  --output /tmp/agentwiki-review-set-my-record-01.json

python3 -m agentwiki review-set recheck \
  --workspace "$RUNTIME_WORKSPACE" \
  --journal "$EDITORIAL_DB" \
  --input /tmp/agentwiki-review-set-my-record-01.json \
  --bindings "$CURRENT_BINDINGS_JSON"
~~~

ID, пути и переменные должны соответствовать реальным ранее сохранённым данным. Для `compose` задача должна быть заранее создана через Python API и выдана указанному worker с действующей арендой. Команды не создают учётных записей и не меняют полномочия. Рабочие SQLite-файлы остаются отдельно от Git; в репозиторий помещаются экспортированные результаты и документация.

Python API модуля `agentwiki.review_set` предоставляет `create_review_set`, `recheck_review_set`, `load_review_set`, `save_review_set` и `load_bindings`. Загрузка проверяет сохранённую структуру и контрольные суммы, сохраняя исторический результат; она не пересчитывает старое смысловое решение по новым правилам. Для нового наблюдения предназначен явный `recheck`.

Типичные причины отказа составления: `component_digest_mismatch`, `component_not_proposed`, `stale_component`, `composition_write_conflict` и `lease_lost`. Ошибка формы связей возвращается как `invalid_review_set`; допустимый, но неполный набор сохраняется со статусом `blocked` и причиной `uncovered_writes`. Различие между ошибкой входа и содержательным препятствием позволяет сохранить неполное рассмотрение, не выдавая его за готовое.

## 9. Применение к порталу документации

Для технического портала единицей работы может стать связанная правка: страница API, пример клиента, руководство миграции и список ограничений. Авторы получают разные файлы, интегратор формирует одно предложение, редактор видит покрытие всех файлов и их общее происхождение. Это помогает восстановить, что именно обсуждалось и какие мнения относятся к текущим данным.

Для энциклопедии потребуются более сложные единицы: утверждение, раздел, статья, взаимные ссылки и источники с разными областями действия. Сведение статьи к одной паре значений скрывает существенную часть содержания. Текущий механизм даёт форму для сохранения основания, но не модель истинности произвольной статьи.

Если `A` авторов производят независимые компоненты, интегратор может собрать не более `32` за одну операцию текущего интерфейса. Это ограничение размера предложения, а не максимальное число работающих авторов. Несколько задач и тематических очередей могут обслуживать больше участников; фактическая полезность зависит от конфликтов, темпа принятия и доступного времени редакторов.

Цена набора зависит от числа файлов, объёма runtime-контекста, всего захваченного журнала и размеров пар. Один общий захват устраняет повтор одного и того же чтения для каждого файла, но не отменяет канонизацию, хеширование и пофайловое рассмотрение. Измеренного ускорения относительно независимых досье пока нет. Увеличение размера пула не доказывает рост полезного потока.

### 9.1. Почему полной описи файлов недостаточно

Рассмотрим проектный пример: руководство обещает повторять только безопасные операции, а клиент добавляет повтор для любой операции. Два файла могут иметь все пакеты, точные digests и актуальные решения. Такое покрытие само по себе не обнаружит противоречие: правило безопасности нужно выразить и связать с обоими артефактами. Этот пример объясняет ограничение; выполненная демонстрация не анализировала такое поведение программы.

Следующее содержательное направление — межфайловые обязательства. У каждого обязательства можно сохранять явное условие, связанные фрагменты документа и кода, область применимости и основание проверки. Тогда комплект сможет показывать отдельно покрытие файлов и рассмотрение общих обязательств. Для свободного текста извлечение таких связей останется предположением автора или модели, которое требует проверки.

Исследовательский вопрос: помогает ли такое отображение находить противоречия между файлами при том же времени редактора? Нужны отдельно размеченные случаи, учёт пропущенных ошибок и ложных замечаний. Эта возможность пока предложена, а не реализована.

## 10. Выполненный сценарий

Обычный запуск `review-set-demo` выполнен в `/tmp/infod10-composed-development-01` с пулом 3. Два программных автора подготовили правки существующих `docs/reference.md` и `code/client_config.py`. Программный интегратор создал один новый proposal из двух исходных. Отдельные формальные операции рассмотрели компоненты и затем композицию; два редакторских ID записали по решению для каждого пакета.

| Шаг | Состояние общего набора | Что произошло с файлами |
|---|---|---|
| Есть formal reviews компонентов, но отсутствует review композиции | `blocked`, `unapproved` | Прежние одобрения не перенесены |
| Композиция проверена, указан только пакет документа | `blocked`, `uncovered_writes` | Код остаётся непокрытым |
| Указаны пакеты обоих файлов | `current_for_human_review` | Оба файла представлены для человека |
| Принята посторонняя правка Windows, ревизия 1 → 2 | `current_for_human_review` | Основания обоих файлов сохранены |
| Поддержка кода заменена замечанием | `blocked` | Сводка кода блокирована, сводка документа текущая |
| Тайм-аут изменён с 30 до 40 секунд, ревизия 2 → 3 | `blocked`, `stale_read` | Общее чтение устарело для обоих файлов |

После изменения тайм-аута повтор завершённой композиции вернул тот же ID с `replayed=true`; новое предложение не появилось. Оба источника и составное предложение остались `proposed`. Отдельные вызовы `Store.accept` приняли только две фоновые правки вымышленных claims. Выпуск не создавался; человеческое заключение не имитировалось, предложенный код не исполнялся.

Сохранены три набора: до собственной формальной проверки, с неполным покрытием и с полным покрытием; также сохранены последующие оценки и редакторский экспорт. В журнале 2 пакета, 5 решений и 11 событий. [Отчёт](../../examples/composed-review/results/report.md) связывает все материалы и указывает наблюдённые потоки. Это конкретный прикладной запуск, без измерений качества LLM, предельной ёмкости и ускорения.

## 11. Дальнейшие инженерные шаги

1. Определить подтверждённые личности и роли, области полномочий, отзыв и срок действия допуска. Самозаявленный `actor_kind` для этого недостаточен.
2. Описать содержательное покрытие: какие фрагменты каждого файла рассмотрены, какие утверждения связаны между файлами, кто проверяет полноту такого отображения.
3. Выбрать обязательную политику и авторитетную точку принятия. Условия, влияющие на запись знаний, должны проверяться вместе с ней либо в явно описанном протоколе согласования.
4. Добавить ограниченный LLM-адаптер с сохранением входа, модели, параметров, инструкции, бюджета и результата. Сгенерированный текст продолжает поступать через proposal.
5. На отдельно размеченных материалах сравнить обычный diff, отдельные досье и общий набор по труду редактора, пропускам ошибок и ложным блокировкам при одинаковом бюджете.
6. Оптимизировать выборку журнала и зависимости после измерений. Затем исследовать обратное давление, тематические очереди и большее число исполнителей.

Нынешняя работа показывает проверяемое происхождение составной правки и полноту заявленного покрытия. Мировое первенство, независимость рецензентов, преимущество качества и промышленная масштабируемость не установлены. [Дорожная карта](roadmap.md) отделяет реализованные механизмы от исследовательских гипотез.
