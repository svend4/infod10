# Перенос описи обещаний между изменениями

Девятый этап продолжает [покрытие объявленных обещаний](promise-coverage.md). Предыдущий инструмент проверяет одну опись относительно одного сохранённого анализа обязательств. При следующей правке автору приходится выяснять, какие описания ещё подходят, какие требуют изменения и почему прежний результат нельзя просто перенести.

Добавлен план переноса описи между двумя закреплёнными основаниями: прежним отчётом покрытия и новым отчётом обязательств. Это материал для составления новой описи. Он не переносит редакторские решения, результат прежнего рассмотрения или право принятия.

## 1. Какой разрыв устраняет этап

Документ может получить вводный абзац, переместиться в другой файл или изменить существенное обещание. Все три изменения меняют байты, но требуют разной работы редактора:

| Изменение | Что нужно установить |
|---|---|
| Перед неизменной цитатой добавлен абзац | Сохранились ли сама цитата, выбранные поля и их основания |
| Переименованы файл и правило | Указал ли автор точное соответствие старых и новых ID |
| Лимит попыток изменён с 3 на 4 в обоих файлах | Совпадение новой пары не разрешает перенос старого описания без рассмотрения |
| Поля совпадают, но прочитанная зависимость устарела | Новый снимок сохраняет собственное препятствие независимо от совпадения |

Повторное создание всех описаний увеличивает труд, а безусловное копирование скрывает изменения основания. План показывает пригодность каждого прежнего описания по ограниченным, явным правилам. Выигрыш времени и качество такого подхода пока не измерены.

## 2. Входы и граница снимка

Входы алгоритма:

1. Один исторический отчёт `coverage-1`, содержащий прежнюю опись и исходный анализ обязательств.
2. Один целевой отчёт `obligations-1` с новым набором рассмотрения и его препятствиями.
3. Необязательное явное соответствие ID артефактов и обязательств.

Данные берутся из этих сохранённых входов. План не перечитывает runtime, редакторский журнал, checkout или внешний сайт. Старое и новое основания хранятся в нём по одному разу; старый отчёт остаётся историческим документом.

Все выводы относятся к двум захваченным состояниям. `live_state_checked=false` и `atomic_capture=false` сохраняются: общий момент чтения двух живых баз здесь не устанавливается. Если с момента захвата что-либо изменилось, сначала нужен новый комплект рассмотрения и анализ обязательств.

## 3. Явное соответствие идентификаторов

Соответствие задаёт только переименования ID:

- `artifact_ids`: прежний ID документа или кода → целевой ID;
- `obligation_ids`: прежний ID обязательства → целевой ID.

Это точные идентификаторы, а не шаблоны замены строк. Переименование артефакта не меняет имя Python-константы, путь JSON-поля, маркер блока, тип, область или отношение. Для изменения таких метаданных требуется новое рассмотрение описания.

Пример файла соответствий:

~~~json
{
  "schema_version": 1,
  "artifact_ids": {
    "docs/contract.md": "docs/contract-v2.md",
    "code/client_config.py": "code/client_config_v2.py"
  },
  "obligation_ids": {
    "allowed-methods": "allowed-methods-v2"
  }
}
~~~

Соответствие ID описывает отношение между кандидатами. Оно само не перемещает и не удаляет файлы в Store или Git. В прикладном сценарии альтернативные пути заранее существуют в исходном снимке, а новые предложения записывают кандидатов по этим путям.

Неуказанный ID сохраняется буквально. Источник явного соответствия должен использоваться прежней описью и существовать в прежнем основании; его целевой ID должен существовать в целевом основании. Если неявно сохранённый ID уже не разрешается, это отражается в результате по обещанию. Явные переименования проверяются вместе с используемыми неявными соответствиями ID самим себе: нельзя незаметно слить два прежних объекта в один целевой объект. Допускается до 200 соответствий артефактов и до 100 соответствий обязательств.

Механизм не ищет похожие строки, не угадывает перемещение по тексту и не выбирает «ближайшее» правило. Если ID изменился, автор указывает соответствие. Даже корректное соответствие не заменяет проверки цитаты, селекторов, значений и зависимостей.

## 4. Когда описание можно предложить к повторному использованию

`reusable_descriptor` означает, что ограниченная проверка обнаружила неизменное основание описания с учётом явно заявленных переименований. Для этого необходимы одновременно:

1. Прежняя цитата однозначно находится в прежнем и целевом отображённых документах.
2. Обе стороны требования разрешаются: поле документа и константа кода.
3. После применения соответствий совпадают оба селектора, область, тип и направление отношения.
4. Указанные обязательства соответствуют этим метаданным в обоих основаниях.
5. Выбранные нормализованные значения определённого типа не изменились между основаниями.
6. Не изменились карты контрольных сумм зависимостей, от которых зависит отображение выбранных артефактов.

Прежнее описание также должно иметь проверенную цитату, корректную связь и `match` в старом отчёте. Историческая ошибочная или непроверенная связь не становится пригодной только потому, что новый файл выглядит подходящим.

Совпадение значений документа и кода в новом снимке недостаточно. Если документ и конфигурация одновременно перешли с 3 на 4 попытки, новое отношение может иметь `match`, но прежнее описание не получает статус пригодного к переносу.

Нормализация следует определённому типу. Например, перестановка элементов `string_set` не меняет выбранного множества; изменение исходного фрагмента при этом остаётся видимым. Точная цитата проверяется буквально, без такого преобразования.

Проверка опирается на ограниченный экстрактор [межфайловых обязательств](cross-file-obligations.md). Предложенный Python не исполняется. Вычисляемые выражения, вызовы, мутации и неподдержанные конструкции не превращаются в известное значение только потому, что похожи на прежний литерал.

## 5. Текст, смещения и зависимости

План различает существенные основания выбранного поля и изменения полного текста:

- полные отображённые байты документа могли измениться;
- цитата могла переместиться из-за вводного абзаца;
- выбранное значение и точная цитата могли сохраниться;
- значения привязанных claims могли измениться даже при одинаковом выбранном поле.

Изменение полного документа и смещения цитаты показываются отдельно. Само смещение не означает изменения цитаты. Однако одинаковая цитата не оправдывает перенос, если изменилось выбранное типизированное значение или основание отображения.

Сравниваются объявленные зависимости. Необъявленная смысловая связь с другим абзацем не обнаруживается автоматически. Сохранение всех выбранных полей не устанавливает неизменность поведения программы, полноту обещания или достаточность источников.

Проверка оснований консервативна: она учитывает все bindings выбранного артефакта. Изменение привязанного claim вне выбранного поля также может потребовать нового рассмотрения описания.

## 6. Результат по каждому обещанию

| Статус | Значение |
|---|---|
| `reusable_descriptor` | Прежнее описание подходит как кандидат по текущим ограниченным правилам |
| `needs_review` | Обнаружено изменение или несоответствие; описание требует пересмотра |
| `unresolved` | Данных или поддержки экстрактора недостаточно для вывода |

Результат содержит причины, привязанные к конкретному прежнему обещанию. По нему можно восстановить, какие ID сопоставлены, что изменилось и какое основание осталось неизвестным. Ни один статус не означает, что человек уже рассмотрел содержание.

Препятствия прежнего и целевого оснований разделены. Прежнее `stale_read`, замечание или неполное покрытие сохраняется как историческая информация. Препятствия целевого анализа действуют для нового рассмотрения. Согласованность выбранных значений не устраняет целевой `stale_read`, а прежний успешный результат не разрешает новое предложение.

## 7. Черновик сохраняет знаменатель

Главная опасность переноса — получить красивую долю покрытия, удалив всё затруднительное. Поэтому черновик сохраняет **все прежние ID обещаний, порядок и число записей**.

Для описания, пригодного к повторному использованию, сохраняются перенесённые связи. Для остальных записей список ссылок на обязательства очищается. Запись остаётся в описи и требует явного действия редактора. Нельзя повысить долю покрытия простым исчезновением неудобного обещания из результата переноса.

Черновик ещё не является новым отчётом покрытия. После рассмотрения автор исправляет цитаты, требования и ссылки, при необходимости дополняет перечень, затем выполняет `coverage analyze` на целевом отчёте обязательств. Именно этот отдельный шаг показывает новое покрытие, отношения и действующие препятствия.

Сам план уже содержит наблюдение `draft_coverage` по сформированному черновику. Это производная внутри плана, а не ещё один полный вложенный отчёт. `migration_state` показывает пригодность описаний; общий `state` дополнительно учитывает покрытие черновика и препятствия целевого основания. Поэтому `all_descriptors_reusable` совместимо с общим `blocked`.

Сохранение старого знаменателя также **не обнаруживает новые обещания**. Если на страницу добавлено новое условие, которого не было в прежней описи, оно не возникает из переноса автоматически. Полноту новой страницы требуется рассмотреть отдельно, включая существенные условия за пределами ограниченного языка полей.

## 8. История решений и полномочия

Перенос описания не переносит решения из редакторского журнала. Решение относится к точному пакету с собственными текстом, источниками, правилами и контрольной суммой. Если новый proposal получил новое основание, его рассмотрение остаётся отдельной работой.

План сохраняет `requires_human_review=true` и `auto_accept=false`. Он не вызывает `Store.accept`, не добавляет голос, не изменяет старый отчёт и не публикует выпуск. Полномочия редактора и обязательная политика в транзакции принятия остаются отдельными задачами.

Повторное использование подходит для распределения работы: автор документа уточняет цитату, автор кода подтверждает селектор, интегратор заявляет переименование, редактор рассматривает различия. Число участвующих ID не является мерой независимости; одинаковая модель способна повторять один и тот же пропуск.

## 9. Формат и воспроизводимость

Версия правил — `rebase-1`. Загрузка исторического отчёта проверяет его производные по закреплённым правилам и вложенным входам. Неизвестная версия явно не поддерживается; прежний вывод не должен молча измениться после обновления алгоритма.

Строгий JSON ограничен 25 МБ. Контрольные суммы связывают входы и выводы; они не подтверждают авторство, истинность или полноту описи. Сохранение создаёт новый файл и сохраняет прежние результаты. Техническое время создания записывается в UTC.

Python API:

~~~python
from agentwiki.inventory_rebase import (
    plan_rebase,
    load_mapping,
    load_report,
    save_report,
)
~~~

`plan_rebase(previous_coverage, target_obligations, mapping=None)` принимает загруженные отчёты. Загрузчики исходных форматов остаются в соответствующих модулях `coverage` и `obligations`; `load_mapping` читает отдельное соответствие ID, `load_report` — сохранённый план, `save_report` создаёт новый файл.

Реализация находится в [agentwiki/inventory_rebase.py](../../agentwiki/inventory_rebase.py). Она работает с переданными снимками и не предоставляет нового пути записи в runtime.

## 10. Команды

Из корня существующего checkout, указав реальные файлы:

~~~sh
python3 -m agentwiki inventory-rebase plan \
  --previous "$PREVIOUS_COVERAGE_JSON" \
  --target "$TARGET_OBLIGATIONS_JSON" \
  --mapping "$ID_MAPPING_JSON" \
  --output /tmp/agentwiki-rebase-plan-01.json

python3 -m agentwiki inventory-rebase show \
  --input /tmp/agentwiki-rebase-plan-01.json

python3 -m agentwiki inventory-rebase export-draft \
  --input /tmp/agentwiki-rebase-plan-01.json \
  --output /tmp/agentwiki-rebased-inventory-01.json
~~~

`--mapping` необязателен, когда ID сохранились. Для каждого сохранения задавайте новый путь. Команды используют только файлы снимков; результат `show` не является проверкой актуальной рабочей базы.

Обычный прикладной сценарий:

~~~sh
python3 -m agentwiki inventory-rebase-demo \
  --workspace /tmp/agentwiki-rebase-my-run-01 \
  --workers 3
~~~

Используйте новый пустой каталог. [Сохранённый отчёт сценария](../../examples/inventory-rebase/results/report.md) должен читаться вместе с конкретными входами и состояниями, а не как измерение максимальной ёмкости или ускорения.

## 11. Выполненный сценарий

Обычный CLI-запуск `inventory-rebase-demo` выполнен с пулом 3 в `/tmp/infod10-rebase-development-01`. Два программных автора подготовили семь вкладов, интегратор создал четыре композиции. Для семи точных редакторских пакетов два программных проверяющих записали четырнадцать решений. [Отчёт](../../examples/inventory-rebase/results/report.md) связывает исходную опись, обязательства, планы и черновики.

| Целевой вариант | `reusable_descriptor` | `needs_review` | `unresolved` | Обещаний в черновике | Общий результат |
|---|---:|---:|---:|---:|---|
| Вводное пояснение перед прежними обещаниями | 2 | 0 | 0 | 2 | `current_for_human_review` |
| Явное соответствие других путей кандидатов и ID правил | 2 | 0 | 0 | 2 | `current_for_human_review` |
| Цитата и значения лимита изменены с 3 на 4 | 1 | 0 | 1 | 2 | `blocked` |
| Фоновый timeout изменён с 30 на 40 | 0 | 2 | 0 | 2 | `blocked` |

В первом варианте изменились байты документа и расположение цитат, но сами цитаты, выбранные значения и зависимости сохранились. Во втором автор явно сопоставил ID. Альтернативные пути существовали в начальном снимке отдельно; операция перемещения или удаления файлов Store либо Git не выполнялась.

В третьем варианте новый документ и код оба задают 4 попытки, поэтому целевое отношение совпадает. Однако прежняя цитата обещает 3 попытки и больше не находится. Запись получила `unresolved`, её прежние ссылки очищены, ID и место в описи сохранены. Описание методов осталось пригодным. Это различие между согласованностью новой пары и переносом прежнего описания.

В четвёртом варианте заново захвачено основание после отдельного принятия фонового claim. Выбранные методы и лимит совпадают, но их зависимости отображения изменились; оба описания получили `needs_review`. Исходный `stale_read` также сохраняет блокировку. Обещания не исчезли из черновика.

Сохранены 7 исходных предложений, 4 композиции, 5 наборов рассмотрения, 5 анализов обязательств, 1 прежний отчёт покрытия и 4 плана переноса с черновиками. Редакторский экспорт содержит 7 пакетов, 14 решений и 25 событий. Все 11 предложений файлов остались `proposed`; принят только один фоновый вымышленный claim на ревизии 2. Выпуск не создавался.

Внешние LLM не вызывались, код из предложений не исполнялся, человеческое заключение не имитировалось. Участники самозаявленные. Рабочие SQLite-файлы остаются вне Git. Время прикладного отчёта указано в Europe/Berlin, технические события — в UTC. Сценарий не измеряет независимую полноту описи, труд редактора или предельную ёмкость системы.

## 12. Практическая область и дальнейшая работа

Для технического портала перенос помогает сохранить повестку рассмотрения после редактирования и перемещения файлов. Он особенно полезен там, где разные авторы поддерживают документацию, конфигурацию и правила связи. Он не выбирает за предметного редактора, какие обещания существенны и достаточно ли сравнивать именно эти поля.

Параллельно подготовлен [реальный контракт Retry из urllib3 2.5.0](real-contract-urllib3.md) с [официальными снимками и авторским адаптером](../../corpora/urllib3-retry-v2.5.0/README.md). В нём выбраны набор методов по умолчанию и значение `total=10` конструктора. Важны ограничения смысла: `total` считает повторы, а отсутствие POST в наборе по умолчанию не является универсальным запретом повторять POST.

Перевод этих двух выбранных значений в литералы адаптера выполнен авторами вручную. Реальный Python-модуль не поддерживается грамматикой текущего экстрактора и не исполнялся. На девятом этапе корпус ещё не был подключён к прикладному сценарию переноса, который использует вымышленные данные. [Десятый этап](inventory-amendment.md) подключает ручной адаптер и оформляет явный пересмотр изменившейся цитаты. Разбор произвольной прозы в обязательства остаётся ручной работой. Официальный снимок сам по себе не является независимой разметкой человеком или оценкой полезности механизма.

Для [гипотезы H8](roadmap.md) по-прежнему требуется отдельно размеченный перечень существенных обещаний, случаи за пределами экстрактора и сравнение при одинаковом времени редактора. План переноса добавляет вопрос о стоимости сопровождения: сколько труда экономится на неизменных описаниях и сколько ошибок возникает при повторном использовании. Эти показатели не измерены текущим прикладным сценарием.

Следующий инженерный шаг определяется наблюдённым предметным пробелом. Новые форматы, большее число агентов и дополнительные контрольные суммы сами по себе не доказывают улучшения содержания.
