# Анализ влияния: от изменённого утверждения к работе агентов

Этот этап добавляет адресную перепроверку документов и кода: явные зависимости по утверждениям, шаблонам, чтениям и запросам.
Свободное понимание смысла текста граф не заменяет.

Подробности первого прототипа находятся в [руководстве](README.md), общая модель — в [теоретическом анализе](theory.md).
Практический пример этого этапа выполнен и сохранён отдельно: [отчёт](../../examples/impact-analysis/results/report.md).
Он использует шесть Python workers и вымышленные источники; LLM не вызывались, предложенный код не исполнялся.

## 1. Какую задачу решает новый этап

Пусть один агент изменил допустимый тайм-аут клиента.
Другой ранее подготовил справочник, третий — пример программы, четвёртый — эксплуатационное руководство.
Часть материалов использует подстановку параметра, часть содержит самостоятельное объяснение.
Задача координатора: определить, что можно пересобрать, что нужно перечитать и что препятствует выпуску.

Факт принятия документа в прошлом не означает, что его основание остаётся актуальным после новых изменений.
Поэтому проверка на принятии предложения и проверка готовности выпуска решают разные задачи.
Первая защищает момент записи; вторая выявляет устаревание уже принятых материалов.

Текстовый diff показывает изменённые строки; граф влияния показывает зарегистрированные основания других артефактов.
Редактор затем оценивает содержательную достаточность основания там, где формальная проверка заканчивается.

## 2. Какие зависимости можно зарегистрировать

| Связь | Пример | Что объясняет |
|---|---|---|
| Источник → утверждение | Цитата спецификации → `api.timeout_seconds` | Происхождение структурированного значения |
| Утверждение → файл через binding | Тайм-аут → `docs/reference.md` | Необходимость повторной подстановки |
| Прочитанный объект → принятый файл | Руководство зависит от прочитанного параметра | Необходимость редакционного пересмотра |
| Объект области → запрос | Windows входит в `platforms:api-v1` | Влияние состава и содержания перечня |
| Запрос → файл | Перечень платформ → руководство | Зависимость от полного результата запроса |
| Параметры → правило | Тайм-аут, попытки, бюджет | Необходимость повторной оценки ограничения |
| Принятое содержание → производные файлы | Знания → индекс поиска | Необходимость пересборки производных данных |
| Производные данные → выпуск | Файлы и индекс → manifest | Обновление согласованного снимка |

Направление стрелки: от основания к потребителю.
Один узел может иметь несколько входящих оснований и несколько потребителей.
Связь с источником означает зарегистрированное происхождение; она не подтверждает истинность цитаты.

~~~mermaid
flowchart TD
    S[Источник и подтверждающий фрагмент] --> C[Утверждение]
    C --> B[Подстановка в шаблоне]
    B --> F[Документ или Python-файл]
    C --> R[Сохранённое чтение]
    R --> F
    C --> Q[Результат запроса области]
    Q --> F
    C --> P[Общее ограничение]
    F --> I[Индекс поиска]
    F --> M[Выпуск и manifest]
    I --> M
    P --> M
~~~

Это схема модели; фактические типы рёбер и объяснения находятся в машинном плане.
Она не означает, что правило само переписывает каждую зависимую страницу.

## 3. Три разных результата анализа

**Повторная генерация.** Значение структурированного утверждения изменилось, а файл использует placeholder.
Подстановка может дать новую версию Markdown или Python из неизменённого шаблона.
Это операция над явно связанной частью текста.

**Повторное рассмотрение.** Файл опирался на прочитанный объект или полный результат запроса.
Система может обнаружить изменение основания, но не знает, как исправить авторское объяснение.
Требуется новое предложение с актуальными основаниями и отдельное решение координатора.

**Повторная оценка ограничения.** Изменение одного параметра может нарушить правило между несколькими записями.
Например, `timeout × attempts ≤ budget` оценивается по общему состоянию.
Само наличие маршрута к правилу не означает, что нарушение действительно возникло.

Один файл может одновременно требовать генерации и рассмотрения.
Например, тайм-аут в нём подставляется автоматически, а описание совместимости основано на полном списке платформ.
Пересборка первой части не обновляет смысл второй.
Поэтому множества `render_files` и `review_files` могут пересекаться.

## 4. Почему запросы требуют отдельного контроля

Представим принятую страницу: «Поддерживается Linux».
Автор прочитал Linux и выполнил запрос всех платформ API v1.
Позже принят claim о Windows; сама запись Linux не изменилась.
Проверка только Linux ничего не обнаружит, хотя утверждение о полноте перечня устарело.

Digest зарегистрированного запроса учитывает состав результата и содержимое его элементов.
Добавление записи, удаление и изменение существенного тела записи меняют digest.
Поэтому зависимость хранится на запрос целиком, а не только на ранее найденные идентификаторы.

Для сравнения двух выпусков нужна информация обеих сторон.
Иначе удалённый объект или объект, покинувший область запроса, исчезнет вместе со своим старым маршрутом влияния.
Объединение кандидатов из старого и нового графа позволяет объяснить такие изменения.

Запросы прототипа ограничены зарегистрированными областями.
Произвольный SQL, естественно-языковые вопросы и семантический поиск не получают такую гарантию автоматически.
Если результат изменился и затем полностью вернулся к прежнему содержимому, digest совпадёт.
Этот вариант ABA не фиксирует историю промежуточных состояний.

## 5. Сохранение оснований после принятия

До этого этапа `readset` и `queries` использовались при проверке предложения.
Для последующей работы нужно восстановить, какое принятое предложение создало текущую версию файла.
Из него берутся сохранённые чтения, digests запросов и список записываемых объектов.
Зависимость относится к версии артефакта, а не к последнему предложению в базе.
Поле `baseline_revision` указывает состояние сразу после атомарного принятия этого предложения.
Сохранённые основания приводятся к этому состоянию; соседние записи одного пакета продолжают учитываться.

Проверка исходного digest собственного файла нужна при принятии: другой автор не должен незаметно занять его путь.
После принятия этот digest относится к старому содержимому и не должен делать файл немедленно устаревшим.
Такие предобразы записи требуют отдельной обработки при построении долгоживущих зависимостей.

Bindings сохраняют особый смысл: их актуальные значения подставляются при выпуске.
Изменение binding само по себе не требует переписывать тот же placeholder автором.
Однако свободный абзац рядом с ним может устареть, даже если placeholder обновился.
Автор обязан явно объявлять дополнительные основания и учитывать границу этой модели.

Материалы bootstrap не имеют обычного авторского предложения.
Отсутствие записи о чтении означает отсутствие наблюдаемого основания, а не доказательство независимости материала.
Такая граница должна оставаться видимой при интерпретации плана.

## 6. Проверка перед выпуском

Координатор принимает изменения в SQLite по прежнему протоколу.
Дополнительно экспорт проверяет основания уже принятых артефактов, включая документы, код и claims.
Изменённое небиндинговое чтение или изменённый сохранённый запрос препятствуют публикации устаревшего материала.
Работа остальных агентов при этом может продолжаться: блокировка выпуска не отменяет новые знания.

Порядок исправления:

1. Получить свежий снимок базы.
2. Прочитать актуальный результат запроса и затронутые утверждения.
3. Подготовить исправленный шаблон с актуальными `readset` и `queries`.
4. Отправить новое предложение через обычное задание и аренду.
5. Получить review точного digest предложения.
6. Принять предложение с повторной проверкой оснований и ограничений.
7. Повторить экспорт из нового согласованного снимка.

Выключение проверки или прямое редактирование базы не является исправлением основания.
Автоматическое одобрение смысловых изменений в этот этап не входит.
Сохранённый выпуск остаётся неизменяемым; новый выпуск получает собственный manifest.

## 7. Сравнение выпусков и проверяемость входа

Выпуск схемы 2 содержит файл зависимостей наряду со знаниями, источниками, документами и индексом.
Manifest связывает эти файлы по размеру и SHA-256.
Загрузчик сравнения сначала проверяет целостность входов, затем строит план влияния.
Анализатор не должен объяснять изменения на основании произвольно смешанных файлов разных выпусков.

Предыдущие выпуски схемы 1 остаются историческими артефактами.
В них можно восстановить bindings из шаблонов, но нет нового полного набора принятых чтений и запросов.
Совместимость загрузчика не превращает отсутствующую provenance в существующую.
Для такого сравнения требуется оговорка о неполном покрытии зависимостей.
Исторический выпуск схемы 1 оставлен без изменений; чтение и поиск по нему выполнены после обновления загрузчика.
Добавление `dependencies.json` меняет идентификатор нового выпуска даже при той же ревизии знаний.

Контрольный хеш обнаруживает несоответствие данным manifest.
Если злоумышленник может заменить и содержимое, и manifest, сам хеш не подтверждает автора выпуска.
Подпись и доверенная доставка manifest относятся к отдельному этапу.
Проверка не исполняет Python-файлы, предложенные агентами.

## 8. Теория замыкания влияния

Пусть `G = (V, E)` — ориентированный граф зарегистрированных зависимостей.
Пусть `C` — множество изменённых объектов при сравнении двух снимков.
Замыкание `I(C)` содержит `C` и все узлы, достижимые из него по рёбрам основания к потребителю.
По достижимым типам узлов строятся задания генерации, рассмотрения и оценки правил.

При обходе очередью с множеством посещённых узлов стоимость составляет `O(|V| + |E|)` для исследуемого графа.
Это оценка самого обхода без сортировки и выдачи полных объясняющих путей. Текущая реализация хранит пути явно: их суммарная длина добавляется к расходам и в длинной цепочке может достигать `O(|V|²)`. Компактные ссылки на предшественников и ограничение размера отчёта нужны для дальнейшего масштабирования.
Подготовка снимков, хеширование больших текстов и файловый ввод-вывод добавляют собственные расходы.
Короткий маршрут объясняет включение файла в план, но не доказывает существование смысловой ошибки.

Полнота вычисленного замыкания условна: все существенные зависимости должны быть заявлены и корректно представлены.
Неявная ссылка в свободной прозе, пропущенная цитата или неучтённый внешний API останутся вне графа.
Поэтому уменьшение размера плана нельзя само по себе считать уменьшением числа ошибок.
Это необходимое ограничение при любых заявлениях об экономии работы.

## 9. Как получить граф и план

Команды читают существующую базу первого демонстратора:

~~~sh
python3 -m agentwiki impact --workspace /tmp/agentwiki-my-run-01 --changed api.timeout_seconds
python3 -m agentwiki graph --workspace /tmp/agentwiki-my-run-01 --format mermaid
~~~

Вместо `--workspace` можно указать `--release` с каталогом проверенного выпуска.
Аргумент `--changed` можно повторять; известные графу источники задаются как `source:<id>`, запросы — как `query:<scope>`.
Отсутствующее основание, уже представленное в графе, адресуется полным именем `artifact:<id>`.
Команда `compare --before КАТАЛОГ --after КАТАЛОГ` сама определяет изменения двух выпусков.
Множество кандидатов в её плане и фактически изменённые байты файлов — разные результаты.
Выполненный пример и относительные пути сохранены в [отчёте](../../examples/impact-analysis/results/report.md).

## 10. Выполненный практический сценарий

Новый запуск начал с ревизии 9 первого демонстратора и сохранил три выпуска схемы 2:

| Шаг | Ревизия | Результат |
|---|---:|---|
| Исходное состояние, тайм-аут 40 секунд | 9 | `r9-58b57cc435622fed` |
| Принят тайм-аут 30 секунд | 10 | `r10-abbdcd6b3af7436c` |
| Принята новая платформа macOS | 11 | Экспорт остановлен: `release_needs_review` |
| Список платформ заново прочитан и исправлен | 12 | `r12-923d5e5a41d54b48` |

Перед изменением тайм-аута граф выбрал три из шести файлов документов и кода:
`code/client_config.py`, `docs/reference.md`, `docs/retries.md`.
После принятия изменения фактически изменились те же три файла; их шаблоны обновлять не потребовалось.
Значения подставлены из общей ревизии; бюджетное ограничение оценено обычным протоколом принятия.
Остальные три файла документов и кода сохранили свои байты.
Метаданные выпуска и производный индекс по-прежнему формировались из полного снимка.

Затем добавлен claim о macOS, и граф указал на необходимость review `docs/platforms.md`.
Старый документ был принят корректно, но его полный перечень Linux/Windows устарел.
Проверка выпуска обнаружила `stale_accepted_query` для сохранённого запроса `platforms:api-v1`.
После нового авторского предложения со свежим query digest документ принят на ревизии 12 и выпуск разрешён.
При сравнении выпусков ревизий 10 и 12 изменился один файл документов и кода: `docs/platforms.md`.

~~~sh
python3 -m agentwiki impact-demo --workspace /tmp/agentwiki-impact-new-01 --workers 6
~~~

Для нового выполнения нужен свободный workspace; существующие результаты сохраняются.
Совпадение трёх кандидатов с тремя изменёнными файлами относится к одному контролируемому сценарию.
Оно не измеряет ускорение, качество LLM или полноту обнаружения смысловых зависимостей.

## 11. Как использовать план для нескольких агентов

1. Координатор получает два проверенных снимка и вычисляет изменение.
2. Планировщик группирует результаты по файлам, видам работы и общим основаниям.
3. Генератор обрабатывает подстановки; редактор разбирает содержательные зависимости.
4. Проверяющий ограничений оценивает общие инварианты.
5. Авторы получают задания с закреплёнными входными digests.
6. Координатор принимает только предложения с актуальными основаниями.
7. Экспорт повторно контролирует уже принятые файлы и строит единый выпуск.

План не требует отдельного агента на каждое ребро.
Общие основания разумно объединять, чтобы несколько исполнителей не выполняли одинаковый сбор сведений.
Уровень параллелизма выбирается по независимости заданий, очереди ревью и бюджету.
Число узлов графа не является измеренной ёмкостью пула workers.

## 12. Что исследовать следующим шагом

Сравнивать следует три стратегии: полную перепроверку, общую инвалидизацию и адресное замыкание.
Для них нужны одинаковые исходные материалы и одинаково размеченные изменения.
Считать следует пропущенные зависимости, лишние задания, труд редактора и полную стоимость принятого результата.
Отдельно нужны случаи изменения области запроса, отсутствующего объекта и свободного текста с незаявленным основанием.

Затем можно добавить размеченные смысловые регрессии: единицы, версии, отрицания и обязательность требований.
LLM может предлагать недостающие рёбра как отдельные проверяемые гипотезы.
Предложенное моделью ребро не становится достоверным только из-за высокой уверенности ответа.
Редакционная политика должна определять, когда такое ребро принимается и как оспаривается.

Следующая перспектива — планировать работу по ожидаемому риску и цене исправления.
Пока нет измерений и корпуса, это исследовательское направление, а не подтверждённое преимущество системы.
Границы эксплуатации и дальнейшие этапы описаны в [дорожной карте](roadmap.md).
