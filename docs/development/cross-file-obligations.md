# Межфайловые обязательства документа и конфигурации

Седьмой этап развивает [составное рассмотрение](composed-review.md): к перечню файлов добавляется явное отношение между конкретным полем документа и константой программной конфигурации. Инструмент работает с одним сохранённым `review-set`, разбирает данные без исполнения кода и сохраняет проверяемое основание каждого результата. [Прикладной пример](../../examples/cross-file-obligations/results/report.md) находится отдельно от прежних запусков.

Реализация ограничена явно размеченным JSON в Markdown и литеральными присваиваниями в Python. Она помогает находить определённые несоответствия конфигурации. Семантика свободного текста, поведение произвольной программы и истинность энциклопедического утверждения требуют других оснований.

## 1. Какой разрыв закрывает этот этап

Полное покрытие `writes` отвечает на вопрос, представлен ли каждый изменяемый файл для рассмотрения. Формальная review проверяет основания и инварианты предложения. Редакторский журнал хранит относящиеся к точным пакетам мнения. Эти механизмы сами по себе не сравнивают обещанный в руководстве перечень операций с объявленным в клиенте перечнем.

Рассмотрим предметную область повторных запросов. Документация разрешает повтор для `GET` и `HEAD`; конфигурация клиента содержит `GET`, `HEAD` и `POST`. Оба файла могут иметь актуальные read sets, полные пакеты и положительные мнения. Для обнаружения конкретного расхождения требуется отдельное отношение: объявленные в коде операции должны входить в допустимый документом перечень.

Теперь такое отношение можно выразить явно и привязать к данным обоих файлов. При этом остаются три разных вопроса:

1. **Что именно сравнили?** Поле конкретного блока документа и именованную константу конкретного файла.
2. **Выполняется ли объявленное отношение?** Равенство или включение для значений определённого типа.
3. **Актуально ли основание предложения?** Это отдельный результат захваченного `review-set`.

Совпадение полей не устраняет `stale_read`, замечание проверяющего или непокрытую запись. Анализ содержимого и состояние предложения показаны отдельно, чтобы локальное совпадение не стало разрешением на принятие.

## 2. Контур данных

~~~mermaid
flowchart TD
    R[Сохранённый review-set] --> P[Точное предложение и захваченные claims]
    R --> U[Наблюдённые препятствия рассмотрения]
    P --> T[Отображение предлагаемых шаблонов]
    S[Явная спецификация обязательств] --> J[Выбор поля fenced JSON]
    S --> C[Выбор литеральной константы Python]
    T --> J
    T --> C
    J --> V[Строгое сравнение типов и отношения]
    C --> V
    V --> O[Отчёт: match / mismatch / unresolved]
    U --> O
    O --> H[Рассмотрение человеком]
~~~

Чтение работающих runtime и журнала в этом контуре не выполняется. Вход — уже сохранённый набор. Сначала он загружается и проверяется, затем выбранные шаблоны отображаются с помощью значений claims из его контекста. Оба сравниваемых файла должны входить в `writes` этого предложения; случайный файл из checkout не может незаметно стать второй стороной проверки.

Обязательства задаются отдельным JSON. В нём нет исполняемых выражений или инструкции модели. Каждая связь явно указывает документ, блок, путь поля, программный файл, символ, тип и отношение. `scope` описывает заявленную область действия; инструмент не выводит её из текста и не устанавливает, что она исчерпывает все условия применимости.

## 3. Формат обязательства

Ниже показана спецификация для перечня операций. Это самостоятельный пример формы; пути и имена нужно согласовать со своим proposal:

~~~json
{
  "schema_version": 1,
  "obligations": [
    {
      "id": "retry-methods",
      "description": "Объявленные операции клиента входят в документированный перечень.",
      "scope": {"api": "v1"},
      "relation": "code_subset_of_document",
      "value_type": "string_set",
      "document": {
        "artifact_id": "docs/reference.md",
        "fence_id": "retry-policy",
        "path": ["retry", "allowed_methods"]
      },
      "code": {
        "artifact_id": "code/client_config.py",
        "symbol": "RETRY_METHODS"
      }
    }
  ]
}
~~~

Документ содержит явно помеченный JSON-блок:

````markdown
```json agentwiki:retry-policy
{"retry": {"allowed_methods": ["GET", "HEAD"]} }
```
````

Код объявляет литеральную конфигурацию:

~~~python
"""Конфигурационные данные примера клиента."""
RETRY_METHODS = ["GET", "HEAD", "POST"]
~~~

Путь `path` идёт только по ключам JSON-объектов. Он не является JSONPath, запросом, поиском по тексту или обращением к элементам массива. `symbol` — имя верхнеуровневой константы. Обязательство не может оценить произвольное Python-выражение ради получения этого значения.

Документ остаётся шаблоном Store: пары `{{` и `}}` зарезервированы для подстановок. Вложенный JSON следует форматировать с пробелом между соседними закрывающими фигурными скобками, как в примере, либо размещать их на разных строках. Валидность JSON сама по себе не отменяет ограничений исходного формата шаблона.

Идентификатор блока должен однозначно выбирать явную метку `json agentwiki:<fence_id>`. Поддержаны ограждения из обратных кавычек или тильд длиной не менее трёх символов, с отступом до трёх пробелов. Закрывающее ограждение использует тот же символ и имеет не меньшую длину. Чужие ограждённые блоки учитываются, чтобы пример внутри другого блока не стал фактическим основанием. Отсутствие, неоднозначность, незакрытое ограждение, некорректный JSON или отсутствующий ключ сохраняются как невозможность разрешить обязательство. Неоднозначность нельзя скрыть выбором первого удобного фрагмента.

Спецификация ограничена 100 обязательствами с различными ID. `scope` — объект строковых меток, явно заданных автором, например версия API. Сопоставление меток с реальными условиями работы приложения автоматически не подтверждается.

### 3.1. Типы и отношения

| `value_type` | Допустимое значение | Смысл `equals` |
|---|---|---|
| `string` | Строка | Точное равенство строк |
| `boolean` | Только логическое значение | Одинаковое логическое значение |
| `integer` | Целое число, исключая логические значения | Точное равенство целых |
| `string_set` | Список различных строк | Равенство множеств без учёта порядка |

В Python `True == 1`, но для этого протокола логическое значение и целое число имеют разные типы. Дублирующиеся элементы не становятся молчаливо допустимым множеством. Строка с числом не приводится к числу, регистр и пробелы не нормализуются без объявления такого правила.

`code_subset_of_document` определён для `string_set`. Направление включения фиксировано: **код ⊆ документ**. Для кода `["GET", "HEAD", "POST"]` и документа `["GET", "HEAD"]` условие не выполняется: `POST` отсутствует в документированном перечне. Обратное включение проверяло бы другое обязательство и не должно подменять исходное.

Единицы измерения, диапазоны, даты, условия, отрицания и модальности не входят в этот узкий язык. Например, целое `30` не получает автоматически смысл секунд. Преобразование единиц реализовано в отдельном [парном инструменте](semantic-corpus.md); перенос его возможностей на межфайловое обязательство потребует явного расширения схемы и правил.

## 4. Почему анализ Python ограничен всем модулем

Поддерживаемый файл — конфигурационные данные: необязательная начальная строка документации и простые присваивания различным именам литеральных значений. Модуль разбирается через AST; его импорт или исполнение не выполняются.

Вызов, импорт, функция, условие, повторное присваивание, изменение объекта или другое неподдержанное выражение делают извлечение неразрешённым. Это относится и к конструкции после выбранной константы. Например:

~~~python
RETRY_METHODS = {"GET", "HEAD"}
RETRY_METHODS.add("POST")
~~~

Чтение только первого присваивания скрыло бы изменение множества. Текущий инструмент отказывается выдавать его за итоговое значение. Он также не пытается интерпретировать последовательность операторов, частично исполнить программу или угадать результат вызова.

Даже успешно извлечённая константа описывает объявленную конфигурацию. Анализ не доказывает, что клиент использует её, что библиотека учитывает её именно так или что повтор `POST` безопасен. Для проверки поведения нужны отдельная модель исполнения, условия применения и программные доказательства либо разрешённая программа верификации.

## 5. Что сохраняет основание результата

Отчёт содержит захваченный `review-set` и спецификацию обязательств по одному разу. Каждое разрешённое сравнение фиксирует связь со своим артефактом и выбранным фрагментом. В основании сохраняются контрольные суммы исходного тела, отображённого текста и фрагмента, а также его позиция и извлечённое типизированное значение.

У таких данных разные назначения:

- digest тела связывает результат с точной записью proposal;
- digest отображённого текста фиксирует использованные значения подстановок;
- digest фрагмента и позиция показывают, откуда извлечено сравниваемое значение;
- тип, отношение и версия правил объясняют, как получен вывод.

Позиция относится к захваченному отображённому тексту. Смещения отсчитываются в символах Unicode Python; строки нумеруются от 1. Обработка переводов строк учитывает LF, CRLF и отдельный CR. При редактировании файла позиция не обязана оставаться прежней; перемещение блока не предоставляет права переносить прежний результат на новые байты. Наличие хеша само по себе не удостоверяет автора, доверенность источника или полноту выбранного обязательства.

Отчёт имеет собственные идентификатор, digest и время создания в UTC. Сохранение создаёт новый файл и не перезаписывает прежний. JSON-входы и отчёт ограничены 25 МБ; выбранный шаблон и отображённый текст — 1 МБ UTF-8. Дополнительно ограничены глубина структуры, число узлов и разрядность целого: AST до 20000 узлов, декодированный JSON до 200000 узлов, глубина до 64, целое до 256 бит. Это границы локального формата, без измеренной производительности или гарантии обработки документа любого размера.

## 6. Три результата сравнения и отдельное состояние основания

| Результат обязательства | Значение |
|---|---|
| `match` | Для извлечённых значений объявленного типа отношение выполнено |
| `mismatch` | Значения извлечены, но объявленное отношение не выполнено |
| `unresolved` | Сторону нельзя однозначно извлечь или тип/конструкция не поддержаны |

`unresolved` не равен установленному противоречию. В частности, динамическая программа может вести себя корректно, но выбранный инструмент не имеет достаточного основания для вывода. `match` также не означает одобрение: он относится только к заявленному отношению.

В отчёте сохраняются состояние и препятствия исходного набора рассмотрения. Например, документ и конфигурация могут оба отображать актуально захваченное значение `40`, а proposal ожидал digest прежнего значения `30`. Межфайловое равенство тогда выполняется, но основание proposal уже устарело. Требуется новый proposal или восстановление его оснований по действующему процессу; само новое совпадение не устраняет конфликт.

Анализ является наблюдением сохранённого снимка: `live_state_checked=false`, `render_basis="captured_candidate_current_claims"`. Для отображения используются наблюдённые текущие claims захваченного контекста; устаревший readset proposal при этом не исправляется. Отчёт не подтверждает, что сейчас в runtime остались те же значения и решения. Для нового наблюдения сначала создают актуальный `review-set`, затем новый отчёт обязательств.

Загрузка старого отчёта сохраняет его исторический предмет. Для известной версии `obligations-1` проверяется записанное основание: выбранные фрагменты, типы, нормализация и объявленное отношение. Это проверка результата по зафиксированным правилам, без подмены старого вывода новыми. Неизвестная версия правил явно отклоняется как неподдерживаемая; будущая версия потребует собственного валидатора.

Во всех результатах остаются `requires_human_review=true` и `auto_accept=false`. Изменения в `Store.accept`, полномочия журнала и публикация выпуска через этот модуль не выполняются.

## 7. Команды

Обычный прикладной сценарий запускается из корня checkout в новом каталоге:

~~~sh
python3 -m agentwiki obligations-demo \
  --workspace /tmp/agentwiki-obligations-my-run-01 \
  --workers 3
~~~

Для уже сохранённых входов:

~~~sh
python3 -m agentwiki obligations analyze \
  --review-set "$REVIEW_SET_JSON" \
  --input "$OBLIGATIONS_JSON" \
  --output /tmp/agentwiki-obligations-my-report-01.json

python3 -m agentwiki obligations show \
  --input /tmp/agentwiki-obligations-my-report-01.json
~~~

Переменные обозначают реальные JSON-файлы. `analyze` читает сохранённый набор, а не путь к рабочей SQLite-базе. Для повторного сохранения нужен новый путь результата. `show` загружает исторический отчёт и не выполняет запросов к runtime или редакторскому журналу.

Python API находится в [agentwiki/obligations.py](../../agentwiki/obligations.py). Центральная операция — `analyze_obligations(review_set, spec)`; для файлов предназначены `load_spec(path)`, `load_report(path)` и `save_report(report, path)`. Спецификация проверяется по строгой схеме, сохранённый отчёт — также по контрольным суммам. Полные снимки входов позволяют восстановить проверяемое основание.

## 8. Применение к порталу, вики и энциклопедии

Для технического портала полезны небольшие явные обязательства: поддерживаемые методы, включённые возможности, режим совместимости, целочисленный параметр. Автор документа размечает поле, автор кода объявляет константу, интегратор включает оба файла в предложение, редактор рассматривает и отношение, и достаточность его формулировки.

Для вики такая форма подходит к явно структурированной карточке версии продукта, если сравниваемый программный артефакт также входит в предложение. На произвольную статью она не переносится автоматически. Равенство двух полей не подтверждает биографию, причинное объяснение, дату из внешнего источника или нейтральность изложения.

Особенно важен риск неполной спецификации: автор может связать удобное поле и оставить существенное обещание в соседнем абзаце. Полнота покрытия файлов и полнота перечня обязательств — разные свойства. Текущий модуль показывает объявленные связи; отсутствие необъявленного противоречия им не установлено.

Несколько агентов могут предлагать разные обязательства, но количество голосов не исправляет ошибку области, типа или отношения. Редактору нужны понятные фрагменты и основания. Для внешних LLM предполагаемые привязки следует сохранять как предложения; модель не должна самостоятельно превращать догадку о связи в доверенное правило.

## 9. Масштаб и стоимость

Седьмой этап не меняет число активных авторов, сериализацию SQLite или лимиты `Store.compose`. Он добавляет работу на этапе рассмотрения: загрузку общего набора, отображение выбранных шаблонов, разбор текста и сравнение полей. Практическая стоимость зависит от размеров файлов, числа обязательств и повторного обращения к одним артефактам.

Общий захваченный набор уменьшает риск смешения оснований. Его присутствие в каждом новом отчёте также увеличивает объём хранения. Для большого портала могут понадобиться выборочные снимки, переиспользуемые результаты разбора по digest и индекс связей. Их полезность следует измерять до усложнения протокола; измерений пропускной способности или выигрыша относительно ручного diff здесь нет.

Большой пул авторов может производить предложения быстрее, чем люди рассматривают новые связи. Следовательно, рост числа workers не обеспечивает рост темпа принятого качественного материала. Нужны отдельные измерения очереди, конфликтов, стоимости рассмотрения и доли действительно полезных обязательств.

## 10. Выполненный сценарий

Обычный `obligations-demo` выполнен с пулом 3 в `/tmp/infod10-obligations-development-01`. Четыре авторских задания подготовили документ и три варианта конфигурации; программный интегратор создал три отдельные композиции. Компоненты и композиции получили собственные formal reviews, два редакторских ID записали по одному решению на каждый из четырёх пакетов. Внешние LLM не вызывались, предложенный Python не исполнялся, человеческое заключение не имитировалось.

| Этап | Исходный `review-set` | Объявленные отношения | Общий результат |
|---|---|---|---|
| Конфигурация объявляет лишний `POST` | `current_for_human_review` | `relations_mismatch` | `blocked` |
| Новый вариант объявляет только `GET` и `HEAD` | `current_for_human_review` | `declared_relations_match` | `current_for_human_review` |
| В другом варианте после литерала расположен `.add("POST")` | `current_for_human_review` | `unresolved` | `blocked` |
| После изменения timeout 30 → 40 снова захвачен исправленный вариант | `blocked`, `stale_read` | `declared_relations_match` | `blocked` |

В первом состоянии полное пофайловое рассмотрение и программные одобрения не выявляли отношение между перечнями: дополнительное обязательство обнаружило отсутствующий в документе `POST`. Исправление сохранено новым предложением и новой композицией; исходные записи остались в истории. Пакет неизменившегося документа переиспользован явно и не считается новым независимым рассмотрением.

Динамический вариант не получил фиктивный вывод по начальному литералу: последующая мутация делает весь модуль неподдерживаемым. Его редакторская пара отдельно описывает начальный перечень с `complete=false`; это авторские метаданные, не результат вычисления поведения программы. В последнем состоянии совпадение перечней не скрыло устаревшего чтения общего тайм-аута.

Сохранены 4 исходных предложения, 3 композиции, 4 набора рассмотрения, 4 отчёта обязательств и редакторский экспорт с 4 пакетами, 8 решениями и 18 событиями. Все семь предложений файлов остались `proposed`. `Store.accept` вызван только для одного фонового вымышленного claim тайм-аута, после чего база перешла на ревизию 2. Выпуск не создавался. [Отчёт запуска](../../examples/cross-file-obligations/results/report.md) связывает входы и результаты; это прикладной сценарий, без измерений качества, нагрузки или предельного числа агентов.

## 11. Следующий содержательный шаг

Полезное продолжение выходит за пределы добавления ещё одного слоя упаковки: установить, насколько полно люди и модели находят необходимые связи между файлами.

1. Выбрать один реальный предметный договор: например, правила повторных запросов конкретного клиента и версии API.
2. Выделить утверждения, которые можно проверить конфигурацией, и отдельно обещания о поведении. Назначить редактора, подтверждающего границу каждой группы.
3. Подготовить независимую разметку: какие межфайловые отношения существенны, какие значения их нарушают и какие случаи остаются неоднозначными.
4. Сравнить обычный diff, полный `review-set` и обязательства при одинаковом времени редактора. Учесть не только найденные противоречия, но и пропущенные связи, лишние замечания и время проверки самих привязок.
5. По результатам выбрать одно расширение языка: например, совместимость перечислимых режимов или параметр с явной единицей. Каждое расширение должно иметь область, типы и границы разрешимости.

Эта программа описана как новая гипотеза H8 в [дорожной карте](roadmap.md), а не как выполненная оценка. Следующие инженерные условия внешнего применения остаются прежними: подтверждённые личности и роли, обязательная политика в авторитетной точке принятия, обработка отзыва решения и отдельная программа верификации. Одно лишь новое правило сопоставления этих условий не заменяет.
