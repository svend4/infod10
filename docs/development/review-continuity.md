# Сохранение силы рассмотрения при изменении несвязанного раздела

Шестнадцатый этап развивает [маршрутизацию по разделам](content-routing.md). Отдельно включаемый режим `continuity` позволяет учитывать прежнее редакторское решение после изменения другой части каталога, если его собственное основание осталось тем же на каждом разрешённом переходе.

Полный пакет содержания продолжает закреплять актуальные поколения и хеши политик. Исходное решение сохраняет свой прежний пакет и ID. Для повторного использования добавляется проверяемая связь между исходным рассмотрением, текущим локальным основанием и историей изменений каталога.

Это локальная модель на SQLite с доверенными приложением, владельцем базы и часами хоста. Она проверяет формальные условия пригодности зарегистрированного мнения; личность человека, независимость моделей, внимательное чтение и истинность документации требуют дополнительных оснований.

Практические материалы: [запуск и файлы](../../examples/review-continuity/README.md), [отчёт выполнения](../../examples/review-continuity/results/report.md). Фактические числа и исходы конкретного запуска находятся в отчёте. Пределы формата ниже не являются измерениями ёмкости портала.

## 1. Какой разрыв закрывается

В предыдущем режиме весь каталог входит в адрес пакета. Если A/B/C и D не пересекаются, изменение описания только D всё равно повышает общие поколения содержания и governance. Поля и результаты A/B/C могут остаться прежними, но старое одобрение больше не совпадает с новым полным пакетом.

Для портала с несколькими редакционными направлениями это создаёт дополнительное рассмотрение из-за административного изменения несвязанной области. Одновременно простого сравнения старого и нового результата недостаточно: между ними мог измениться сам раздел A, а затем вернуться к прежнему описанию. Проверяющий не рассматривал этот промежуточный договор.

Новый режим отдельно проверяет:

1. Совпадение локального основания исходного и текущего пакетов.
2. Каждый промежуточный переход политики, разрешённый для такого сохранения.
3. Нынешнюю действительность исходного допуска проверяющего и его последнего мнения.
4. Остальные условия формального рассмотрения и принятия.

Из этого не следует автоматическое создание нового голоса. Сохранённое мнение продолжает иметь прежние `decision_id`, grant, время записи, rationale и ссылку на исходный полный пакет.

## 2. Режим включается явно

Для активации нужны уже действующие governance, authorship и политика содержания schema 2. Администратор указывает точное текущее поколение governance. В той же SQL-транзакции приложение повышает это поколение и сохраняет границу активации.

Поколение активации далее обозначено `G₀`. Оно входит в новые записи о рассмотрении. Голоса, созданные до `G₀`, не получают новое основание задним числом. Для начала работы в режиме нужны свежие решения по актуальному полному пакету.

| Условие | Поведение |
| --- | --- |
| Режим ещё не включён | Сохраняется прежняя глобальная инвалидизация по поколениям |
| Отсутствует governance, authorship или каталог schema 2 | Активация отклоняется |
| Credential не разрешает администрирование | Активация отклоняется |
| Ожидаемое поколение не совпало | Активация не применяется |
| Режим уже включён | Повторное включение не создаёт новую границу |
| После включения предлагается политика schema 1 | Обновление отклоняется с `continuity_schema_required` |

Операции выключения нет. Прежние базы сохраняют прежнее поведение, пока администратор явно не включит режим. Исторические пакеты и квитанции не переоформляются.

## 3. Полный пакет и локальное основание

Пакет содержания schema 2 остаётся прежним. Его `packet_id` имеет вид `cgp_<sha256>`, а тело содержит общие ссылки на политики и вложенные результаты выбранных разделов. При обновлении каталога полный адрес меняется.

Для continuity из тела пакета исключаются **только шесть полей**:

~~~text
packet_id
packet_digest
content_policy_generation
content_policy_digest
governance_policy_generation
governance_policy_digest
~~~

Всё остальное входит в локальное основание, в том числе:

- ID и digest неизменяемого предложения.
- Версии формата, правил маршрутизации, извлечения JSON и AST.
- Реальные записи и полный требуемый комплект.
- Прямой выбор разделов, транзитивное замыкание и сведения о непокрытых файлах.
- Все выбранные разделы, их ID и хеши политик.
- Результаты обязательств, обещаний, цитат и объявленных сопоставлений.
- Ожидаемые и фактические read/query основания.
- Хеши зависимостей отображения шаблонов.
- Признак пригодности, причины отказа и объявленные границы интерпретации.

Digest вычисляется по каноническому JSON этого основания. Его адрес имеет вид `rcb_<sha256>`. Структурное сравнение должно различать JSON `true` и число `1`; простая подстановка равенства Python для таких данных недостаточна.

Полный пакет и основание отвечают на разные вопросы. Первый фиксирует конкретное наблюдение под конкретными общими поколениями политик. Второе позволяет проверить, остался ли тем же предмет локального рассмотрения. Совпадение основания само по себе ещё не разрешает учитывать голос: далее проверяется вся допустимая цепочка переходов.

## 4. Что записывает новое решение

При активном режиме новое решение governance имеет schema 3. Оно по-прежнему требует точный текущий `expected_content_packet_digest`, актуальное поколение governance, разрешённый grant и CAS по предыдущему решению данного principal для записи.

Дополнительно сохраняется `review_continuity`:

| Поле | Назначение |
| --- | --- |
| `rules_version` | Правила `review-continuity-1` |
| `activation_generation` | Граница явного включения режима |
| `basis_id` | Адрес локального основания `rcb_…` |
| `basis_digest` | Digest основания |

Исходная привязка `content_packet` остаётся в том же решении. Полный исходный пакет сохраняется в неизменяемом хранилище содержания; отдельная копия оснований в новой базе не требуется.

Явная привязка сообщает, что операция была разрешена по этому предмету рассмотрения. Она не подтверждает, что человек прочитал пакет, понял все последствия или независимо проверил факты. В прикладном прототипе решения могут быть сформированы программным сценарием.

## 5. Какие переходы разрешают сохранение голоса

Каждое разрешённое ребро истории создаётся только при `content_set_policy`, в той же SQL-транзакции, где записаны новая политика содержания и новое поколение governance.

Ребро закрепляет исходные и целевые поколения и хеши обеих политик. У него есть собственный канонический адрес `rct_…`. История не редактирует исходный голос и не заменяет его grant.

Для конкретного решения приложение проверяет последовательность от поколения исходного пакета до текущего пакета:

1. Все необходимые шаги присутствуют без пропусков.
2. Каждый шаг относится к действующей границе continuity.
3. Переход содержания соединяет правильные соседние записи каталога.
4. Обе исторические governance-политики имеют тот же точный договор: кворум, разделение координатора и остальные поля.
5. Обе стороны каждого изменения каталога сохраняют выбранный локальный контекст данного предложения.
6. Последний шаг заканчивается именно текущими ссылками полного пакета.

Верхний каталог может изменяться. Сохранение проверяется для конкретного неизменяемого предложения и его реальных writes. Одно и то же административное обновление может быть несвязанным для D и существенным для A/B/C.

### 5.1. Сравнивается полный выбранный контекст

Для исторической политики заново вычисляется структурный маршрут по writes исходного предложения: все прямые совпадения и транзитивное замыкание пересечений. Затем сопоставляются маршрут, полный требуемый набор файлов и полные нормализованные политики выбранных разделов.

Здесь не выбирается только одно поле, которое случайно осталось равным. Изменение обязательства, цитаты, описи, scope, ID выбранного раздела или состава его комплекта меняет контекст. Добавление раздела, связанного через общий файл, также меняет замыкание и препятствует сохранению.

Исторический проход использует сохранённые политики и предложение. Он не обращается к нынешним значениям документов, чтобы задним числом получить другой результат старого извлечения.

### 5.2. Смена governance является отдельным барьером

Прямая операция `governance_set_policy` не создаёт разрешённого ребра continuity. Это относится и к записи идентичного тела политики с новым поколением.

Так администратор сохраняет возможность потребовать свежего рассмотрения независимо от того, совпали ли q и прочие поля. После такого барьера старые голоса не становятся действующими из-за последующего изменения только D. Новые решения, записанные уже после барьера, могут участвовать в последующих разрешённых переходах.

При фиксации ребра используется governance-политика, актуальная непосредственно перед обновлением каталога. Номер из старой записи содержания не подставляется вместо неё: между двумя редакциями каталога мог происходить отдельный сброс governance.

## 6. Почему возврат политики не оживляет старое мнение

Рассмотрим последовательность:

~~~text
G₄: A исходный, D исходный; записано одобрение A
G₅: изменён A
G₆: A возвращён к исходному описанию
~~~

На концах последовательности локальное основание может снова совпасть. Проверка каждого ребра обнаруживает изменение A на промежуточном шаге. Прежний голос не переносится через эту историю; требуется свежая операция проверяющего.

Это защита от возврата **политики рассмотрения** к прежнему значению после её существенного изменения. Она не вводит новый журнал всех промежуточных правок содержимого артефактов. Прежняя модель read/query остаётся основанной на digests: если данные вернулись к тем же байтам и зарегистрированные основания снова совпадают, действуют прежние правила runtime. Нельзя описывать эту возможность как обнаружение любой промежуточной правки текста или программы.

## 7. Нынешние полномочия остаются обязательными

Сохранение основания не продлевает срок credential и не восстанавливает отозванный grant. Учитываемое мнение должно оставаться последним решением principal по этому proposal и артефакту.

Сохраняются проверки:

- Исходного grant, роли reviewer и точного scope.
- Отзыва и срока действия grant на момент финальной авторизации.
- Совпадения principal и grant с записанным мнением.
- Актуальной головы решения; вытесненное мнение не возвращается.
- Подлинного локального происхождения proposal.
- Глобального исключения авторов и интеграторов из согласования собственного кандидата.
- Разделения координатора и проверяющих по текущей политике.
- Кворума по каждой записи и действующих возражений.

Повторная выдача credential тому же principal создаёт другой grant. Она не делает старое решение подходящим. Проверяющий должен создать свежее мнение с актуальными параметрами и CAS на прежнюю голову.

Локальный bearer подтверждает владение допуском, без удостоверения человека или модели. Разные principal и несколько мнений не устанавливают независимость экспертизы.

## 8. Возражения и предел истории

Одно правило continuity применяется ко всем verdicts: `approve`, `request_changes` и `abstain`. Действующее `request_changes` сохраняет veto после доказанно несвязанного изменения D. Для него не вводится облегчённое правило исчезновения, когда одобрения могут сохраняться.

Одна проверка проходит не более 64 переходов. Это ограничение объёма работы, без утверждения о предельном числе редакций портала за всё время. После слишком длинной цепочки можно записать свежие решения по текущему полному пакету, получив новое исходное поколение для дальнейшего рассмотрения.

При длинном исходном интервале допускается ограниченный просмотр последних 64 переходов: найденный в этом хвосте известный разрыв governance позволяет установить барьер без прохода всей более ранней истории. Если хвост не даёт такого основания и оставшаяся история превышает предел, результатом становится `continuity_history_limit`.

Отсутствующее ребро отдельно сопоставляется с таблицей политик содержания. Если следующее поколение governance связано с записанным обновлением содержания, переход должен существовать: его отсутствие означает `continuity_history_invalid`. Такой пробел нельзя считать установленным прямым сбросом governance. Проверка действует и при последовательном проходе, и при просмотре ограниченного недавнего хвоста.

Если у иначе действующего мнения на текущей голове история не подтверждена из-за предела или повреждённого исторического основания, приложение добавляет препятствие уровня предложения `continuity_reconsideration_required`. Это относится к `continuity_history_limit` и `continuity_history_invalid`. Такое мнение нельзя просто отбросить: среди непроверенной истории может находиться действующее возражение. Наличие свежего кворума от других участников само по себе не снимает это препятствие.

Для восстановления требуется явная свежая замена соответствующей головы или отзыв её допуска с обычной политикой ответственности за такой отзыв. Подтверждённое изменение локального контекста, другое основание или известный разрыв governance делают прежнее мнение неактуальным по своему договору. Эти установленные причины отличаются от невозможности проверить историю. Неограниченное сохранение veto через произвольную историю не заявляется.

## 9. Наблюдение и финальное принятие

`governance observe` показывает каждое исходное решение и результат его текущей проверки `continuity_match`: `valid`, `reasons` и `proof`. Исходные поля остаются историческими. В proof видны режим `exact_packet` либо `preserved_catalog`, `old_packet`, `current_packet`, поколения, основание, хеш выбранного контекста и переходы. Успешное наблюдение не резервирует будущую ревизию.

Общая сводка `review_continuity.used_decisions` содержит подготовленные доказательства только по фактически выбранным одобрениям кворума. История других мнений остаётся в `decisions`, включая действующие возражения и причины непригодности. Наличие proof не заменяет проверки grant и головы.

~~~mermaid
flowchart TD
    P[Текущий полный пакет] --> B[Совпадение локального основания]
    O[Исходный сохранённый пакет] --> B
    B --> T[Каждый переход каталога сохраняет выбранный контекст]
    T --> D[Последние мнения и подготовленные доказательства]
    D --> A[Свежая проверка координатора и допусков]
    A --> Q[Кворум, возражения, происхождение и runtime]
    Q --> R[Одна транзакция принятия и квитанция]
~~~

В финальном write-транзакционном пути приложение заново вычисляет текущий пакет и происхождение, проверяет выбранные решения и их ограниченные цепочки. Только после этих обходов фиксируется свежий `authorization_time` и проверяются координатор, исходные reviewer grants, heads, scopes и сроки.

Так срок допуска, истёкший во время длинного исторического прохода, не оценивается по слишком раннему времени. Запись фиксирует момент авторизации внутри транзакции; обещания о действительности допуска после этого момента до произвольного будущего действия не даётся.

Формальная review, проверка read/query и runtime-инвариантов остаются самостоятельными условиями. Пригодность локального основания не снимает `stale_read`, mismatch, unresolved, непокрытые writes или отсутствие формального рассмотрения.

## 10. Квитанция schema 4

Новое принятие в активном режиме создаёт квитанцию governance schema 4. Она содержит точный текущий полный пакет и подготовленное доказательство continuity по фактически использованным decision IDs.

В нём сохраняются:

- Граница активации и адрес локального основания.
- Использованные исходные decision IDs.
- Ссылки на исходные и текущие полные пакеты.
- Исходные и текущие поколения governance.
- ID и digests разрешённых переходов.
- Digest агрегированной цепочки.

Исходный пакет в голосе и текущий пакет в квитанции могут иметь разные адреса при одном локальном основании. Это различие остаётся видимым для аудита. Совпадение basis не подменяет полную историю решения.

`chain_digest` — внутренний хеш записи, без внешней подписи или независимого заверения полноты базы. Владелец SQLite остаётся доверенным.

Каноническая квитанция ограничена 4 МБ. Превышение даёт `continuity_receipt_too_large` и откат транзакции, вместо частичного принятия. Свежие мнения уменьшают длину требуемой цепочки. Прежние квитанции schema 1/2/3 сохраняются в исходном виде.

## 11. Исторический повтор, сохранение и новое мнение

| Действие | Результат |
| --- | --- |
| Повтор того же operation ID решения с прежними точными параметрами | После текущей авторизации возвращает исходное историческое решение; нового мнения нет |
| Проверка continuity старого решения в текущем рассмотрении | Определяет, допустимо ли учесть прежний голос под нынешним пакетом |
| Новое решение по текущему пакету | Создаёт новое мнение, требует текущие параметры, действующий grant и CAS по голове |
| Повтор принятия уже принятого proposal | Возвращает прежнюю ревизию и квитанцию после проверки текущих прав координатора; нового принятия нет |

Исторический replay не получает stamp задним числом. Повтор старой операции до включения continuity может вернуть её прежний результат, но не делает прежний голос пригодным для нового режима. Аналогично accepted replay не накладывает новый договор на уже совершившийся факт.

## 12. Команды оператора

Команды используют существующую базу. В примерах `N` — актуальное поколение governance; ID и digests нужно брать из результатов своей базы. Показанные пути credential являются обозначениями закрытых файлов, а не созданными здесь допусками.

Посмотреть действующее состояние:

~~~bash
python3 -m agentwiki governance status --workspace /tmp/my-agentwiki
python3 -m agentwiki content status --workspace /tmp/my-agentwiki
~~~

Однократно включить режим:

~~~bash
python3 -m agentwiki continuity enable \
  --workspace /tmp/my-agentwiki \
  --credential /tmp/private/admin.credential \
  --expected-policy-generation N
~~~

Наблюдать активацию и историю, либо основание конкретного предложения:

~~~bash
python3 -m agentwiki continuity status --workspace /tmp/my-agentwiki

python3 -m agentwiki continuity status \
  --workspace /tmp/my-agentwiki \
  --proposal PROPOSAL_ID
~~~

Для нового голоса используется прежняя команда governance. Здесь показано первое мнение данного principal по указанной записи:

~~~bash
python3 -m agentwiki governance decide \
  --workspace /tmp/my-agentwiki \
  --credential /tmp/private/reviewer.credential \
  --proposal PROPOSAL_ID \
  --artifact docs/a.md \
  --verdict approve \
  --rationale 'Рассмотрен текущий пакет объявленных связей и оснований.' \
  --expected-proposal-digest PROPOSAL_DIGEST \
  --content-packet-digest CURRENT_PACKET_DIGEST \
  --expected-policy-generation N \
  --operation review-a-001
~~~

Для замены добавляется `--previous-decision PREVIOUS_DECISION_ID`; отсутствие параметра означает ожидание пустой головы. Новый голос нельзя направлять с digest старого пакета под видом автоматического продолжения рассмотрения.

Состояние пригодности всего кандидата и авторизованный приём:

~~~bash
python3 -m agentwiki governance observe \
  --workspace /tmp/my-agentwiki \
  --credential /tmp/private/coordinator.credential \
  --proposal PROPOSAL_ID \
  --expected-policy-generation N

python3 -m agentwiki governance accept \
  --workspace /tmp/my-agentwiki \
  --credential /tmp/private/coordinator.credential \
  --proposal PROPOSAL_ID \
  --expected-policy-generation N
~~~

Полные исторические пакеты остаются доступны через `content show --packet cgp_…`. `continuity status` не заменяет наблюдение governance и не выдаёт права принятия.

Публичный status сообщает границу активации, общий `transition_count`, до 100 полных записей переходов и `transitions_truncated`. Для `--proposal` он добавляет `current_packet`, адрес текущего основания `current_basis` и `advisory_only=true`. Он не выдаёт сам по себе заключение о кворуме, veto или праве координатора.

Credential читается из закрытого POSIX-файла. Его содержимое и SHA не передаются в shell, отчёт или Git. Публичные поля пакетов, включая произвольные ключи scope, сохраняются при очистке CLI-вывода; иначе внешний пересчёт digest потерял бы предмет проверки.

## 13. Прикладной сценарий

Новый пустой workspace сохраняет отдельный результат:

~~~bash
python3 -m agentwiki continuity-demo \
  --workspace /tmp/agentwiki-continuity-example-01 \
  --workers 3
~~~

Предмет сценария — кандидат A и несвязанный раздел D. [Выполненный запуск](../../examples/review-continuity/results/report.md) сохранил три авторских задания, одну композицию, 21 этап, 23 решения, 70 изменений каталога и 277 событий. Четыре ожидаемых отказа API и восемь заблокированных принятий зафиксированы явно. Несвязанное изменение сохранило исходные ID одобрений и локальное основание. После 65 переходов свежий кворум не устранил непроверяемую голову возражения C: понадобилось явное новое решение. Один кандидат принят на ревизии 2 с квитанцией schema 4; все четыре использованных одобрения сохранены через последний несвязанный переход. Восемь [дополнительных CLI-команд](../../examples/review-continuity/README.md) сохранили исторический пакет и квитанцию после ещё одного обновления каталога; событий стало 280, ревизия осталась 2. Полные тела всех восьми записанных пакетов сохранены отдельно для проверки ссылок.

Число `--workers 3` обозначает размер пула локальных Python workers. Оно не равно числу независимых экспертов или LLM. Предлагаемый код хранится и разбирается как данные без исполнения; все решения прикладного примера могут быть запрограммированы. Человеческая экспертиза и сравнительная оценка качества не имитируются.

Человекочитаемые отметки отчётов используют Europe/Berlin; технические события и epoch имеют явную техническую шкалу. Существующие результаты прошлых этапов не перезаписываются. Частная SQLite и credentials находятся за пределами публикуемых JSON/Markdown.

## 14. Что это даёт многоагентному порталу

Разные команды могут одновременно готовить и рассматривать правки разных разделов. Если административная редакция D не меняет договор A и его фактические основания, проверяющим A не требуется создавать новые мнения только из-за общего номера каталога. Их прежние решения остаются привязаны к исходному предмету, а текущая квитанция объясняет допустимое сохранение.

Такое поведение может уменьшить повторную работу редактора. Величина эффекта зависит от связности комплектов, частоты смены политик, числа активных мнений и стоимости исторической проверки. История требует вычислений и ограниченного чтения; она тоже входит в стоимость принятого результата.

Мировая новизна, выигрыш качества, пропускная способность и поддерживаемое число агентов не установлены. Для оценки нужны сопоставимые задачи, одинаковый бюджет рассмотрения, независимо размеченные существенные изменения и учёт ложного сохранения либо лишней инвалидизации решений.

## 15. Границы и дальнейшие шаги

| Граница | Практическое следствие |
| --- | --- |
| До 64 переходов на проверку | Длинная история требует свежего рассмотрения; неизвестное возражение не исчезает молча |
| Переход до 16 КБ, в status до 100 записей и полный счётчик | Выдача истории ограничена; усечение не означает, что более ранних записей нет |
| Сохраняются прежние пределы каталога и пакета | До 8 разделов, 32 различных артефактов, 32 вхождений обязательств, 32 обещаний суммарно и пакет до 4 МБ |
| Квитанция до 4 МБ | Большой набор доказательств может потребовать свежих мнений |
| Основания описаны явно | Необъявленное существенное утверждение не появляется в проверке автоматически |
| Выбранные разделы сравниваются целиком | Изменение даже описательного поля выбранной политики может потребовать свежего решения |
| Байтовая модель актуальности данных сохраняется | Новый режим не фиксирует все промежуточные правки содержимого |
| Случайный bearer и principal локальны | Личность, организационная независимость и квалификация не удостоверены |
| SQLite, приложение и часы доверенные | Внешнее заверение, распределённое время и защита от владельца БД не предоставляются |
| Приём в SQLite и внешняя публикация различаются | Git и портал требуют своего протокола восстановления и подтверждения |

Следующие работы:

1. Назначить ответственного за полноту описи и смысловую связь прозы с полями; подтвердить предметную пригодность правил на отдельных материалах.
2. Сохранять понятное редактору объяснение: какое мнение учтено, какой переход оказался существенным и какое новое действие требуется.
3. Определить внешний источник учётных записей и управление жизненным циклом допусков без вывода независимости из числа ID.
4. Оценить стоимость просмотра истории и объём квитанций на реальных редакционных потоках, отдельно от времени подготовки текста моделью.
5. Развить согласование SQLite, Git и портала с устойчивыми намерениями, повторяемыми шагами и восстановлением после частичного сбоя.
6. Расширять договор continuity только по конкретному предметному пробелу. Удаление поля из основания ради большего числа сохранённых голосов требует отдельного анализа того, какие ошибки перестают обнаруживаться.

Общий порядок развития описан в [дорожной карте](roadmap.md). Исходники режима находятся в [review_continuity.py](../../agentwiki/review_continuity.py); транзакционное согласование и квитанции — в [governance.py](../../agentwiki/governance.py), включение и переходы каталога — в [content_gate.py](../../agentwiki/content_gate.py), публичные операции — в [Store](../../agentwiki/store.py) и [CLI](../../agentwiki/review_continuity_cli.py).
