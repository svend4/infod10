# Покрытие объявленных обещаний документации

Восьмой этап развивает [межфайловые обязательства](cross-file-obligations.md). К сохранённому анализу отношений добавляется отдельная опись обещаний, которые автор считает существенными для выбранной правки. Инструмент показывает, каким обещаниям соответствуют проверенные связи документа и конфигурации, а какие остались без такой связи. [Прикладной сценарий](../../examples/promise-coverage/results/report.md) сохраняется отдельно от прежних результатов.

Опись составляется явно. Программа не извлекает все обещания из прозы, не подтверждает достаточность выбранной области и не измеряет качество содержания. Полнота относительно описи и полнота документа — разные свойства.

## 1. Почему совпадения всех правил недостаточно

Предположим, руководство обещает два условия: повторяются только `GET` и `HEAD`, максимальное число попыток равно трём. Автор задаёт одно обязательство для методов. Код объявляет подходящий перечень, поэтому все заданные обязательства имеют `match`. При этом `MAX_ATTEMPTS` может быть равен четырём: обещание о числе попыток вообще не участвовало в сравнении.

Для обнаружения этого пробела нужен знаменатель: перечень обещаний, которые ожидалось рассмотреть. Добавление ещё одного совпавшего правила о методах не покрывает число попыток. Положительные мнения по файлам также не устанавливают, что существенное условие вошло в перечень проверок.

Новая опись делает этот выбор видимым. Она сохраняет точную цитату обещания, ожидаемые стороны отношения и ссылки на обязательства. Сопоставление по ID недостаточно: необходимо совпадение обоих селекторов, области, типа и направления отношения.

При этом автор может выбрать только удобные обещания и получить полное покрытие выбранного перечня. Следовательно, даже значение 100% требует пояснения знаменателя и отдельного рассмотрения полноты описи. Инструмент делает пропуск в заявленной описи наблюдаемым; наличие всех существенных обещаний в самой описи он не устанавливает.

## 2. Четыре независимых вопроса

| Вопрос | Основание | Что результат не устанавливает |
|---|---|---|
| Какие обещания включены в рассмотрение? | Явная опись с цитатами и требованиями | Все ли существенные условия документа перечислены |
| Есть ли для них подходящие обязательства? | Точное соответствие селекторов и метаданных | Выполняется ли объявленное отношение |
| Выполняются ли отношения? | `match`, `mismatch`, `unresolved` исходного анализа | Использует ли программа константу и выполняет ли обещание в работе |
| Допустимо ли продолжать рассмотрение proposal? | Сохранённые блокеры исходного набора | Актуально ли состояние живой базы сейчас и есть ли полномочие принятия |

Полное покрытие может сопровождаться `mismatch`. Совпадение всех связанных значений может сопровождаться `stale_read`. Пустая опись не считается доказательством полноты: знаменатель равен нулю, доля отсутствует, итог блокируется.

## 3. Контур данных

~~~mermaid
flowchart TD
    R[Сохранённый отчёт obligations-1] --> S[Один захваченный proposal и набор рассмотрения]
    R --> O[Спецификация и результаты отношений]
    R --> U[Сохранённые блокеры]
    I[Опись обещаний] --> A[Точные цитаты документа]
    I --> E[Ожидаемые селекторы и отношения]
    S --> A
    E --> M[Сопоставление обязательств]
    O --> M
    A --> C[Отчёт покрытия]
    M --> C
    U --> C
    C --> H[Рассмотрение человеком]
~~~

Вход — один сохранённый отчёт обязательств и одна опись. Runtime, редакторский журнал, файлы checkout и внешние источники повторно не читаются. Предлагаемые документы и конфигурация берутся из захваченного основания исходного отчёта. Нельзя незаметно взять цитату из новой версии файла, сохранив прежние результаты отношений.

Отчёт сохраняет исходный анализ и опись по одному разу. Сводка ссылается на конкретное предложение и его digest, исходный отчёт, обещания и обязательства. Это исторический снимок рассмотрения, а не наблюдение текущего runtime.

## 4. Опись обещаний

У каждой записи есть следующие части:

- `id`: уникальное имя обещания внутри описи;
- `description`: авторское пояснение, не результат автоматического понимания текста;
- `anchor`: документ и точная цитата из его предлагаемого отображённого текста;
- `requirement`: область, отношение, тип и оба ожидаемых селектора;
- `obligation_ids`: ссылки на обязательства исходной спецификации.

Например, запись для числа попыток имеет такую форму. Это пример схемы; имена и цитата должны совпадать со своим предложением:

~~~json
{
  "schema_version": 1,
  "promises": [
    {
      "id": "maximum-attempts",
      "description": "Документированное число попыток связано с конфигурацией.",
      "anchor": {
        "artifact_id": "docs/reference.md",
        "quote": "Максимальное число попыток — 3."
      },
      "requirement": {
        "scope": {"api": "v1"},
        "relation": "equals",
        "value_type": "integer",
        "document": {
          "artifact_id": "docs/reference.md",
          "fence_id": "retry-policy",
          "path": ["retry", "max_attempts"]
        },
        "code": {
          "artifact_id": "code/client_config.py",
          "symbol": "MAX_ATTEMPTS"
        }
      },
      "obligation_ids": ["retry-max-attempts"]
    }
  ]
}
~~~

Цитата должна встречаться однозначно в выбранном документе. Позиция и контрольные суммы позволяют показать, какой именно фрагмент использован. Простое присутствие слов не подтверждает, что автор правильно перевёл их смысл в требование. Например, формулировка «до трёх повторов» может отличаться от «три попытки вместе с первой»: инструмент не разрешает такую неоднозначность по одной цитате.

Селектор документа должен указывать на реально разрешимое поле помеченного JSON-блока в предлагаемом документе. Селектор кода указывает на конкретный файл и константу. Ожидаемые селекторы и область нельзя заменить ссылкой на любое совпавшее обязательство. Для `code_subset_of_document` направление остаётся прежним: код ⊆ документ.

Сами значения могут изменяться, сохраняя ту же связь. Если документ обещает `3`, код объявляет `4`, а оба селектора и метаданные совпали с требованием, связь покрыта, но отношение не выполнено. Покрытие не означает правильность значения.

Пустой список `obligation_ids` показывает отсутствие заявленной связи. Неизвестный ID не создаёт покрытия. Известный ID с другим символом, полем, типом, областью или отношением не становится пригодным только потому, что его собственный результат равен `match`.

## 5. Повторы и общий источник проверки

Переименование одной записи не создаёт новую независимую проверку. `counts.total` и `coverage_fraction` считают записи описи, включая повторы; копирование удачного случая действительно способно изменить эту долю. Поэтому отчёт отдельно показывает `duplicate_requirements`, `counts.unique_requirements` и `counts.covered_unique_requirements`: различные ID с точным совпадением метаданных требования не скрываются. Эта группировка сравнивает метаданные буквально, не определяет смысловую эквивалентность разных формулировок.

`unique_requirement_fraction` имеет своим знаменателем число различных требований по точному digest метаданных, а числителем — число таких требований, для которых есть покрытая запись. Повтор уже покрытого требования не повышает эту долю. Для пустой описи она равна `null`. Наличие второй доли не означает независимости правил: разные требования могут использовать общий источник основания. Непокрытая или неверно связанная запись также сохраняет собственный блокер, даже когда другое описание того же требования покрыто.

Аналогично, одно обязательство может быть указано несколькими записями. Это общий источник проверки, а не несколько независимых подтверждений. Отчёт показывает такие связи. Число записей описи, число различных требований и число различных использованных обязательств имеют разные смыслы.

Обязательства, на которые не ссылается ни одно обещание, перечисляются отдельно. Они могут быть полезны, но не повышают покрытие описи. В частности, добавление десяти правил об одном перечне методов не компенсирует непокрытое число попыток.

`shared_obligations` показывает использование одного ID несколькими обещаниями, включая отдельно те связи, которые действительно соответствуют ожидаемому требованию. `unmapped_obligation_ids` перечисляет обязательства, не имеющие корректной привязки к описи; `unknown_obligation_ids` — ссылки на отсутствующие ID.

Отчёт не оценивает обещания по важности. Неравнозначные условия нельзя считать равноценными только потому, что они образуют одинаковое число записей. Долю следует читать вместе с непокрытыми требованиями, фрагментами, общими правилами и объяснением выбранной области.

## 6. Результат и сохранение препятствий

Отчёт отдельно показывает покрытие, результаты использованных отношений и исходные препятствия рассмотрения. Причины не теряются при переходе между уровнями.

Основные счётчики имеют следующий смысл:

| Поле `counts` | Что считается |
|---|---|
| `total` | Все записи описи |
| `assigned` | Записи с непустым списком ссылок |
| `mapped` | Записи, у которых все ссылки существуют и точно соответствуют требованию |
| `anchor_verified` | Записи с однозначной цитатой и разрешённым полем документа |
| `covered` | Записи, удовлетворяющие одновременно `mapped` и `anchor_verified` |
| `matching`, `mismatch`, `unresolved` | Результат отношений только среди покрытых записей |
| `uncovered` | Записи без назначенных обязательств |
| `invalid_mapping` | Записи с неизвестной или несоответствующей ссылкой |
| `unresolved_anchor` | Записи, для которых не подтверждена цитата либо поле документа |
| `unique_requirements` | Различные требования по точным метаданным |
| `covered_unique_requirements` | Такие требования, имеющие хотя бы одну покрытую запись |

`coverage_fraction` сохраняет числитель `covered` и знаменатель `total`, без округления; для пустого перечня это `null`. `coverage_state` имеет значения `no_declared_promises`, `declared_coverage_incomplete` или `declared_promises_covered`. Последний статус описывает только покрытие описи и может сопровождаться `mismatch` или исходным блокером. Общий `state` остаётся `blocked`, пока есть препятствия; иначе он равен `current_for_human_review`.

| Ситуация | Вывод о покрытии | Содержательное следствие |
|---|---|---|
| В описи есть число попыток, но для него нет обязательства | Есть непокрытое требование | Совпадения методов недостаточно |
| В качестве проверки числа попыток указан другой символ | Неверная привязка | Чужое совпадение не подтверждает это обещание |
| Связь числа попыток правильна, значения 3 и 4 различаются | Требование связано с проверкой | Расхождение блокирует результат |
| Все требования связаны и значения совпали, readset устарел | Покрытие не устраняет препятствие | Требуется восстановить основание proposal |
| Опись пуста | Нет определённой доли покрытия | Полнота не заявляется |

В каждом отчёте сохраняются `requires_human_review=true`, `auto_accept=false`, `atomic_capture=false` и `live_state_checked=false`. Новый формат не вызывает `Store.accept`, не записывает редакторское решение и не публикует выпуск. Человеческое заключение не возникает из наличия цитат, контрольных сумм или согласия программных проверяющих.

Для актуального рассмотрения сначала захватывают новый `review-set`, затем создают новый анализ обязательств и отчёт покрытия. Старые результаты не переписывают и не представляют актуальными после изменения входов. Решение о принятии остаётся отдельным процессом.

## 7. Формат сохранения и ограничения

Версия правил покрытия — `coverage-1`. Исторический отчёт проверяется по закреплённым правилам вместе с исходным анализом `obligations-1`; неизвестная версия явно не поддерживается. Загрузка не должна молча переинтерпретировать прежний результат будущим алгоритмом.

JSON-входы и полный отчёт ограничены 25 МБ. Строгая загрузка отклоняет неоднозначные дубли ключей и неподдержанные значения. Контрольные суммы связывают сохранённые данные и их производные; они не удостоверяют автора, независимость разметки, истинность обещаний или полноту описи.

Опись содержит не более 100 обещаний с различными ID; каждая цитата — от 1 до 4000 символов Unicode, пояснение — до 2000. В одной записи можно указать не более 100 различных ID обязательств. Якорь и ожидаемое поле должны относиться к одному документу. Ограничения типов, глубины данных и разбора выбранных артефактов наследуются от [формата обязательств](cross-file-obligations.md).

Сохранение создаёт новый файл, сохраняя прежний результат. Время создания снимка фиксируется в UTC; оно не является временем исполнения предложенного кода или датой подтверждения документа человеком. Полный вложенный исходный отчёт помогает восстановить основание и увеличивает размер снимка. Производительность и выигрыш от такого хранения пока не измерены.

## 8. Команды

Прикладной сценарий запускается из корня checkout в новом каталоге:

~~~sh
python3 -m agentwiki coverage-demo \
  --workspace /tmp/agentwiki-coverage-my-run-01 \
  --workers 3
~~~

Для сохранённых входов:

~~~sh
python3 -m agentwiki coverage analyze \
  --obligations "$OBLIGATIONS_REPORT_JSON" \
  --input "$PROMISE_INVENTORY_JSON" \
  --output /tmp/agentwiki-coverage-my-report-01.json

python3 -m agentwiki coverage show \
  --input /tmp/agentwiki-coverage-my-report-01.json
~~~

Переменные обозначают реальные файлы, не рабочие базы. `analyze` читает исходный отчёт обязательств и опись; `show` загружает исторический результат без запросов к runtime. Для нового сохранения используйте новый путь.

Реализация находится в [agentwiki/coverage.py](../../agentwiki/coverage.py), команды — в [agentwiki/coverage_cli.py](../../agentwiki/coverage_cli.py), прикладной сценарий — в [agentwiki/coverage_demo.py](../../agentwiki/coverage_demo.py).

Python API: `analyze_coverage(obligation_report, inventory)`, `load_inventory(path)`, `load_report(path)` и `save_report(report, path)`. Валидатор отчёта сверяет сохранённую сводку с вложенными входами по правилам `coverage-1`; сохранение не заменяет прежний файл.

## 9. Применение к документации, вики и энциклопедии

Для технического портала опись полезна как проверяемая повестка рассмотрения: какие параметры, режимы и ограничения авторы обязались связать с конфигурацией. Автор документа указывает цитату, автор кода показывает объявленное значение, интегратор связывает точные артефакты, редактор проверяет достаточность области и отношений.

Разные агенты могут предлагать дополнения к описи. Однако общий контекст и одинаковая модель способны приводить их к одним и тем же пропускам. Число копий одного требования и число поддержавших его ID не оценивают независимость поиска. Необходимы отдельные основания для того, кто вправе подтвердить полноту и сколько работы он фактически выполнил.

Для энциклопедии этот узкий механизм применим лишь к подходящим структурированным связям. Утверждение о биографии, причинности, спорной интерпретации или достоверности источника не становится проверенным после ссылки на программную константу. Для таких утверждений нужны другие типы оснований, атрибуция и предметное рассмотрение.

Число агентов на этом этапе не увеличивается автоматически. Дополнительная опись требует времени авторов и редактора; рост числа правил может повышать труд рассмотрения. Нет измерений максимальной ёмкости, скорости моделей, точности поиска обещаний или выигрыша качества.

## 10. Выполненный сценарий

Обычный CLI-запуск `coverage-demo` выполнен с пулом 3 в `/tmp/infod10-coverage-development-01`. Программные авторы подготовили документ и два варианта конфигурации вымышленного клиента; интегратор сохранил две композиции, получившие собственные formal reviews. Опись явно содержит два обещания: допустимые методы и максимум попыток. [Сохранённый отчёт](../../examples/promise-coverage/results/report.md) связывает точные входы и результаты.

| Состояние | Покрытие записей описи | Результаты отношений | Общий `state` |
|---|---|---|---|
| Приложено только обязательство методов | 1/2 | Методы совпали; лимит не связан с проверкой | `blocked` |
| Приложены оба подходящих обязательства | 2/2 | Оба совпали | `current_for_human_review` |
| Лимиту ошибочно назначено обязательство методов | 1/2 | `invalid_mapping` у лимита | `blocked` |
| Код объявляет `MAX_ATTEMPTS = 4`, документ — 3 | 2/2 | Лимит имеет `mismatch` | `blocked` |
| Фоновый timeout изменён с 30 на 40, заново захвачен исправленный вариант | 2/2 | Оба отношения совпали; исходный `stale_read` сохранился | `blocked` |

Первое состояние показывает пропуск внутри уже объявленной описи: наличие второго обещания не зависит от того, создал ли автор для него правило. Во втором состоянии добавлена точная связь `max_attempts` → `MAX_ATTEMPTS`. В третьем совпавшее чужое обязательство не прошло сопоставление селекторов. В четвёртом связь осталась корректной, но равенство значений нарушилось. В пятом совпадения не исправили устаревшее чтение предложения.

В этом примере оба требования различны по точным метаданным; доли записей и различных требований совпадают. Возможность обнаруживать смысловые дубли или пропущенные в самой описи обещания не демонстрировалась. Редакторские пары содержат отдельно заданные метаданные методов, а не автоматическую оценку всего документа и лимита попыток.

Сохранены 3 исходных предложения, 2 композиции, 3 набора рассмотрения, 4 анализа обязательств и 5 отчётов покрытия. Редакторский экспорт содержит 3 пакета, 6 решений и 14 событий. Все пять предложений файлов остались `proposed`; явно принят только один фоновый вымышленный claim, после чего runtime перешёл на ревизию 2. Выпуск не создавался.

Внешние LLM не вызывались, предложенный код не исполнялся, человеческое заключение не имитировалось. Имена и виды участников самозаявленные. Рабочие SQLite-файлы остались вне Git. Время прикладного отчёта указано в Europe/Berlin, технические события — в UTC. Это выполненный прикладной сценарий, без независимой оценки полноты, качества или предельной ёмкости.

## 11. Следующий содержательный шаг

Реализация даёт видимый перечень и проверяет связи внутри него. Чтобы понять пользу этого перечня, требуется отдельная предметная работа:

1. Выбрать один реальный контракт документации с зафиксированными версией продукта, источниками и областью.
2. Независимо перечислить существенные обещания; сохранить авторов разметки, разногласия и случаи, которые нельзя проверить конфигурацией.
3. Сопоставить авторскую опись с этой разметкой: какие обещания отсутствуют, раздроблены, повторены или неправильно переведены в отношения.
4. Сравнить обычное рассмотрение и опись при одинаковом времени редактора, учитывая труд создания и проверки связей.
5. После этого рассмотреть ограниченный поиск кандидатов в обещания с явной проверкой предложений человеком. Предложение LLM не должно само становиться подтверждением полноты.

Это продолжение [гипотезы H8](roadmap.md), а не выполненная независимая оценка. Расширять язык полей и добавлять новые упаковки имеет смысл после обнаруженного предметного пробела. Полномочия участников, обязательная политика в момент принятия и общая модель согласования хранилищ остаются отдельными инженерными задачами.
