# Корпус смысловых изменений и редакционное рассмотрение

Этот этап расширяет [анализ влияния](impact-analysis.md) описанием смысла изменения.
Граф отвечает, какие зарегистрированные потребители затронуты.
Новый анализ пары отвечает, чем различаются два явно структурированных утверждения.
Он даёт объяснение редактору и сохраняет отказ от вывода там, где основание недостаточно.

Корпус содержит вымышленные примеры проекта, локальные фрагменты источников и авторские аннотации. Их подготовили ИИ-агенты в ходе разработки; экспертное рассмотрение человеком не проводилось.
Это учебный и редакционный материал; аннотации не считаются внешней истиной.
Внешние LLM, поиск в интернете и автоматическое принятие изменений сюда не входят.

## 1. Зачем недостаточно текстового сравнения

Строки «30 секунд» и «30000 миллисекунд» различаются, хотя задают одну длительность.
Строки «в среднем 30 секунд» и «не более 30 секунд» похожи, но выражают разные свойства.
Изменение одной частицы может поменять разрешение на обязанность или отрицание.
Замена версии API меняет область применимости даже при прежнем числе.

Для документации это влияет на инструкции пользователя и обещания продукта.
Для программного кода — на типы параметров, условия и предполагаемые ограничения.
Синтаксически допустимый Python-файл может использовать значение из неверной версии спецификации.
Поэтому разбор синтаксиса, контроль оснований и смысловое рассмотрение выполняют разные задачи.

Задача этапа ограничена: сравнить явно переданные поля двух записей.
Из произвольного абзаца программа сама эти поля не извлекает.
Если автор неверно разметил текст, аккуратное сравнение разметки сохранит эту ошибку.

## 2. Представление утверждения

Утверждение описывается субъектом, свойством, значением и контекстом.
Контекст включает область, версию, время, обязательность, отрицание и атрибуцию.
Для числа сохраняется единица, для перечня — характер полноты.
Отдельно фиксируются вид утверждения и ссылка на поддерживающий фрагмент.

Минимальный смысловой каркас можно записать так:

~~~text
C = (subject, property, value, scope, kind, modality, polarity, attribution, evidence, text)
scope = {version: "v1", ...явно заданные условия области...}
~~~

Это пояснение модели, а не сокращённая JSON-схема входного файла.
Точные имена и допустимые значения полей определяются [реализацией](../../agentwiki/semantic.py).
Готовый корректный вход удобнее брать из корпуса через команду show.

Поле evidence сохраняет source_id, source_digest и quote; text сохраняет исходный текст.
Значение имеет явный тип quantity, set, boolean, date или text.
Совпадение цитаты с локальным источником подтверждает только буквальное присутствие фрагмента.
Логическая достаточность, авторитетность и независимость основания требуют отдельного решения.

## 3. Сравнение пары и слияние трёх версий

Отношение двух утверждений описывает различие before → after.
Возможные наблюдения: эквивалентное число, новое значение, новая область или обязательность.
Одно изменение может затронуть несколько измерений одновременно.
Вывод должен сохранять причины, а не скрывать их за одним общим баллом.

Трёхстороннее слияние решает другую задачу: даны base, left и right.
Сначала нужно установить изменения каждой ветви относительно общей базы.
Затем — проверить совместимость двух изменений и общие ограничения результата.
Эквивалентность пары не разрешает автоматически объединять две конкурирующие ветви.

~~~text
base ── left:  timeout 30 → 40
base ── right: attempts 3 → 4
combined:      40 × 4 > 120
~~~

Оба изменения имеют ясный смысл, а их совместный эффект нарушает бюджет.
Такое ограничение проверяет существующий координатор, а не анализатор пары.
Новый слой не заменяет атомарное принятие и не создаёт путь прямой записи в SQLite.
Совпавший read set означает актуальность прочитанного состояния в момент принятия.
Он не устанавливает истинность источника или правильность сделанного из него вывода.

## 4. Эквивалентность единиц

Для сравнения количеств нужна нормальная форма и совместимая размерность.
Перевод секунд в миллисекунды допустим только для поддерживаемых единиц времени.
Длительность нельзя приравнивать к пропускной способности или безразмерному числу.
Неизвестную единицу нужно сохранить и передать редактору, а не угадывать.

Точное преобразование 30 s → 30000 ms не требует статистического предположения.
Округление, погрешность измерения, интервалы и численная близость требуют отдельной политики.
Этот этап не вводит универсальную допустимую погрешность.
Равенство чисел после нормализации ещё не означает равенство утверждений целиком.

Чтобы считать записи эквивалентными, должны совпадать существенные условия контекста.
Обещание «максимум 30 секунд» не становится наблюдением «в среднем 30000 ms».
Различие вида утверждения сохраняет необходимость рассмотрения даже при одинаковом числе.

## 5. Версии, области и время

Значение API v1 не переносится на API v2 только потому, что их имена похожи.
Утверждение для Linux не означает совместимость со всеми платформами.
Расширение области может превратить подтверждённый частный случай в необоснованное обобщение.
Сужение области тоже содержательно: из документа исчезает часть прежнего обещания.

Две записи о разных периодах не обязаны противоречить друг другу.
Историческое значение сохраняет смысл после появления новой спецификации.
Редактор должен отличать замену действующего правила от добавления исторической записи.
Текущий анализ отмечает переданные различия и не выводит интервалы из свободных дат в прозе.

Неуказанная версия не означает «любая версия».
Неуказанное время не означает «всегда».
Недостающие поля остаются видимым ограничением интерпретации.

## 6. Обязательность, отрицание и атрибуция

«Можно», «следует» и «обязательно» задают разные требования.
Замена рекомендации на обязанность требует пересмотра инструкций и кода проверки.
Числовая неизменность не отменяет этого изменения.
Явное отрицание также рассматривается отдельно от значения.

Отсутствие записи о Windows не является утверждением «Windows не поддерживается».
Для такого вывода нужна политика закрытого перечня либо явное отрицательное основание.
Молчание источника и запрет в источнике должны сохраняться разными случаями.

Фраза «поставщик сообщает X» и утверждение редакции «X» имеют различную атрибуцию.
Удаление атрибуции усиливает ответственность документа за чужое заявление.
Несколько агентов, пересказавших один фрагмент, не создают независимые подтверждения.
Смена атрибуции фиксируется даже при буквальном совпадении остального текста.

## 7. Полные и открытые перечни

Перечень «Linux, Windows» может быть исчерпывающим или состоять из примеров.
Добавление macOS в открытый список не доказывает ошибочность прежних примеров.
Для полного списка новое значение меняет заявленное множество.
Поэтому характер полноты должен быть задан явно и относиться к определённой области.

Полнота источника также не равна полноте мира.
Снимок вымышленной спецификации может задавать полный перечень внутри сценария.
Этот статус нельзя переносить на реальные платформы или актуальные продукты.
Полнота не выводится из того, что поисковый запрос больше ничего не вернул.

Здесь смысловой анализ связан с query digest существующего runtime.
Query digest обнаруживает изменение зарегистрированного результата.
Аннотация полноты объясняет, почему это изменение существенно для автора текста.
Оба механизма зависят от корректно объявленной области.

## 8. Отказ от вывода

Наличие свободной прозы, неподдерживаемых единиц или отсутствующего происхождения требует осторожного исхода.
Анализатор возвращает undetermined и объяснение недостаточности.
Undetermined — полезный результат маршрутизации: материал передаётся человеку или отдельному исследователю.
Он не означает ни подтверждение, ни опровержение утверждения.

Обнаруженные различия полей можно сохранить как подсказки для рассмотрения.
Подсказки не должны превращаться в окончательное решение об эквивалентности.
Нельзя маскировать отсутствие основания высоким числом уверенности.
Новые правила расширяют поддерживаемую область только после явного описания их условий.

## 9. Как устроен корпус

[Корпус](../../corpora/semantic-v1/cases.jsonl) содержит 24 авторских случая: пары и пояснения разметки.
Вместе с ним хранятся локальные основания и статус авторской аннотации.
Примеры охватывают единицы, версии, области, обязательность, полноту, отрицание, атрибуцию и время.
Пограничные случаи нужны, чтобы показать границу автоматического вывода.

Корпус не является готовым benchmark и не сообщает accuracy.
Правила и примеры разработаны в рамках одного проекта и не образуют независимой оценки.
Разметка не прошла внешнее экспертное согласование.
Систематическая оценка качества остаётся будущей отдельной работой.

Источники корпуса — fixtures для вымышленного продукта, встроенные в sources каждого случая.
Их допустимо использовать для изучения формата и маршрута рассмотрения.
Они не подтверждают факты о коммерческих системах и не заменяют реальные первоисточники.

## 10. Команды для редактора

Выполняйте из корня репозитория; Python использует стандартную библиотеку:

~~~sh
python3 -m agentwiki corpus list
python3 -m agentwiki corpus show --case units-equivalent-seconds-milliseconds
python3 -m agentwiki corpus analyze --case units-equivalent-seconds-milliseconds
python3 -m agentwiki review-pair --input /tmp/my-claim-pair.json
~~~

Идентификатор из примера уточняйте по выводу list.
Show раскрывает исходную пару, основание и авторское пояснение без исполнения предложенного кода.
Дополнение show --pair выделяет только before, after и sources для входа review-pair.
Analyze формирует редакционное описание случаев по текущим правилам.
Review-pair читает самостоятельно подготовленный JSON и не принимает изменения в runtime.
Вход review-pair содержит before, after и sources: словарь source_id → {text, sha256}.
Команда analyze требует --case; list допускает фильтр --category, а все команды корпуса — --path.

Отношение structured_equivalent означает равенство поддерживаемой структурированной части.
Different_context сообщает различие областей, не утверждая их непересечение.
Review_required фиксирует содержательные изменения; undetermined сохраняет недостаточность основания.
Поле requires_human_review всегда true, а auto_accept — false, включая эквивалентные записи.

Запуск этих команд не создаёт новых знаний в SQLite и не публикует выпуск.
Вывод анализа можно приложить к предложению как дополнительное объяснение.
Решение координатора по-прежнему связано с точным digest, актуальностью чтений и ограничениями.
Новая схема пар не встроена в Store: её отчёт сам по себе не меняет решение прежнего review.

## 11. Результаты четырёх выполненных разборов

Команда list прочитала 24 случая в 10 категориях из одного снимка корпуса.
Для четырёх выбранных иллюстраций выполнена обычная команда analyze.
Полные входы, выводы и условия сохранены в [отчёте запуска](../../examples/semantic-review/results/report.md).

| Случай | Наблюдаемый результат | Что объясняет |
|---|---|---|
| units-equivalent-seconds-milliseconds | structured_equivalent | 30 s и 30000 ms имеют точно равную структурированную величину |
| kind-measurement-to-guarantee | review_required | Найдено measurement_to_guarantee: измерение заменено гарантией |
| scope-distinct-versions | different_context | Версии различаются; пересечение областей не определяется |
| provenance-quote-not-in-source | undetermined | Цитата отсутствует в снимке: quote_absent |

Во всех четырёх выводах requires_human_review = true и auto_accept = false.
Дополнительно выполнены show --pair и отдельный review-pair по сохранённому JSON.
Это четыре прикладных разбора из авторского корпуса; остальные случаи этим запуском не оценивались.
Метрики точности и проценты успешности не вычислялись; внешние модели не вызывались.

## 12. Пошаговая работа нескольких агентов

1. Координатор задаёт предметную область, версию источника и вопрос изменения.
2. Исследователь сохраняет фрагмент источника с идентификатором и происхождением.
3. Автор выделяет структурированные поля, не заменяя ими исходный текст.
4. Другой участник проверяет соответствие полей цитате и отмечает неопределённости.
5. Анализатор пары объясняет формальные различия и собственные ограничения.
6. Граф влияния выбирает зарегистрированных потребителей изменения.
7. Авторы документов и кода готовят предложения по свежему снимку.
8. Проверяющий рассматривает основания, смысловой отчёт и совместимость результата.
9. Координатор повторяет проверки актуальности и принимает допустимое предложение.
10. Экспорт формирует согласованный выпуск либо объясняет, какие основания устарели.

Для такой работы можно выделить 2–4 авторских роли и одного редактора.
Это пример организации, а не измеренное оптимальное число исполнителей.
Один человек или одна модель могут выполнять несколько ролей, но независимость от этого не появляется.
Текущие программные workers не становятся LLM при добавлении смысловой разметки.

Авторы разметки, её рецензенты и runtime-исполнители — разные учитываемые категории.
Количество потоков нельзя выдавать за количество независимых экспертов.
Если разметку проверял только её автор, это должно оставаться видимым в статусе случая.
Число согласившихся участников без происхождения их аргументов не является мерой истинности.

## 13. Дальнейшее развитие

Пакеты оснований и история решений реализованы следующим, четвёртым этапом: [редакторский журнал](editorial-decisions.md). Пакеты неизменяемы; исправление создаёт новый пакет, а мнения сохраняются отдельными записями.
Затем можно расширять типы значений: интервалы, погрешности и ограниченные предикаты областей.
Для свободного текста понадобится отдельный адаптер извлечения с сохранением исходной цитаты.
Его предложение разметки должно проходить такое же рассмотрение, как предложение нового факта.

Будущая оценка качества потребует независимого материала, нескольких разметчиков и учёта разногласий.
Нужны отдельные измерения пропущенных различий, лишних блокировок и труда редактора.
Сегодняшний корпус создаёт прозрачный словарь и рабочий интерфейс для такой деятельности.
Заявлять выигрыш, полноту семантики или мировую уникальность по нему преждевременно.
