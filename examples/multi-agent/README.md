# Работа нескольких агентов: запускаемый пример

Этот пример показывает, как несколько исполнителей готовят документы и код, а координатор принимает предложения в общую ревизию. Это локальная программа на стандартной библиотеке Python. Источник и спецификация API вымышлены. LLM и внешние сервисы не вызываются; предложенный программный код записывается как текст и не выполняется.

В репозитории уже сохранены [отчёт выполненного запуска](results/report.md), [JSON с событиями](results/report.json) и [выпуск ревизии 9](results/release/r9-a450bcf40a40dc20/manifest.json). Следующие команды создают ваш собственный запуск.

Из корня репозитория, Python 3.10 или новее:

~~~bash
python3 -m agentwiki demo --workspace /tmp/agentwiki-example-01 --workers 6
python3 -m agentwiki status --workspace /tmp/agentwiki-example-01
python3 -m agentwiki export --workspace /tmp/agentwiki-example-01 --output /tmp/agentwiki-export-01
~~~

Укажите новый пустой каталог. Программа не очищает существующие данные. Повторный `demo` для завершённого примера читает сохранённый `report.json` и не добавляет задания; изменение `--workers` при таком вызове не запускает сценарий заново. Для другой конфигурации выберите другой каталог. Если прошлый запуск оборвался до записи отчёта, исследуйте его базу через `status` и используйте новый каталог для повторного примера.

## Что выполняется

1. В SQLite сохраняется вымышленная спецификация и исходные claims: timeout 30 секунд, 3 попытки, бюджет 120 секунд, поддержка Linux.
2. Из одной исходной ревизии готовятся шесть заданий: справочник API, конфигурация на Python, руководство по повторным попыткам, документ Linux, полный список платформ и claim поддержки Windows.
3. `ThreadPoolExecutor` запускает workers. Каждый захватывает задание с lease, отправляет предложение и проходит review. Только координатор принимает изменения после завершения этой фазы.
4. Сначала принимается Windows. Старый полный список платформ отклоняется: он прочитал запрос по платформам, который теперь возвращает другой набор. Четыре независимых документа и код принимаются. Новый список строится по свежей ревизии и принимается.
5. Ещё три задания читают одну ревизию. Изменения timeout на 40 и числа попыток на 4 по отдельности проходят review: `40 × 3 = 120` и `30 × 4 = 120`. После принятия timeout изменение числа попыток отклоняется, потому что совместный результат `40 × 4 = 160` превышает бюджет 120. Документ, читавший timeout 30, также отклоняется как устаревший.
6. Lease отдельного задания немедленно истекает. Новый worker получает другой token. Попытка старого worker отправить результат отклоняется с `lease_lost`; результат нового принимается. Повторное принятие того же proposal не создаёт ревизию.
7. Публикуется согласованный локальный release документов, текстов кода, claims и поиска. Каждый шаблон рендерится из одной принятой ревизии; документы и конфигурация получают timeout 40 и число попыток 3.

`report.md` содержит фактически возвращённые результаты в порядке координации. `report.json` дополнительно содержит задания, события, идентификаторы предложений, счётчики, измерения worker section и release. Эти результаты появляются после запуска; этот README не является отчётом о выполненном запуске.

В `report.json` поле `release.path` указывает конкретный каталог `r<revision>-<digest>` внутри `release/`. Он содержит `manifest.json`, `knowledge.json`, `sources.json`, `search-index.json`, `docs/` и `code/`. Передайте именно этот каталог для поиска:

~~~bash
python3 -m agentwiki search --release /tmp/agentwiki-example-01/release/rREVISION-DIGEST --query timeout
~~~

Замените `rREVISION-DIGEST` значением из выполненного запуска. Поиск текстовый и привязан к выбранному release; embeddings и переключения общего live-указателя здесь нет.

## Сколько агентов работает

`--workers N` задаёт максимальный размер пула локальных Python потоков, от 1 до 32. Можно выполнить тот же сценарий с одним worker: логические задания и проверки конфликтов сохранятся. При шести workers начальные задания подготавливаются конкурентно, но принятие изменений сериализуется транзакциями хранилища.

Число потоков не означает число одновременно занятых CPU. SQLite, планировщик ОС и интерпретатор влияют на фактическое выполнение. Отчёт записывает наблюдавшееся число потоков и максимум заданий внутри worker section; эта величина включает ожидание операций хранилища. Предел 32 является ограничением интерфейса примера, а не результатом измерения вместимости системы. Здесь нет измерений производительности LLM, распределённого кластера или обещания конкретного ускорения.

## Почему обычного объединения файлов недостаточно

| Ситуация | Что отслеживается | Что происходит |
| --- | --- | --- |
| Новые независимые документы | Отсутствие собственного пути и digests прочитанных claims | Предложения общей исходной ревизии принимаются по очереди |
| Изменение прочитанного claim | `readset` с digest из одного snapshot | Устаревшее предложение отклоняется |
| Новая платформа | Digest результата query по scope | Отклоняется неполный список даже при неизменности Linux |
| Разные claims нарушают общее правило | Инвариант `timeout × attempts ≤ budget` на результирующем состоянии | Второе изменение отклоняется без конфликта строк |
| Истёкший worker возвращает результат | Lease и новый token | Старый token не позволяет отправить proposal |
| Повторный запрос принять proposal | Сохранённый результат принятия | Возвращается тот же результат и ревизия |

Proposal содержит `readset`, `queries`, `writes` и обоснование. Каждый записываемый идентификатор включён в `readset`, в том числе с `null` для нового артефакта. Документы и код содержат явные bindings к claims. Это позволяет показать проверяемую семантическую зависимость на ограниченном примере; понимание произвольного естественного языка не реализовано.

## Границы примера

- Проверка точной цитаты подтверждает наличие фрагмента в сохранённом источнике. Она не доказывает, что источник прав, и не проверяет логическое следование произвольного текста.
- Роли workers описывают задания и не являются границей авторизации. Это процесс одного пользователя, а не изоляция недоверенных исполнителей.
- Сохранённый Python файл — артефакт, а не выполняемый плагин. Числа и другие значения подставляются рендерером; запуск произвольного кода отсутствует.
- Отдельные процессы, внешние LLM, GitHub pull requests, семантический поиск с embeddings и редакционный веб-интерфейс здесь не подключены.
- Истечение lease и повтор принятия показаны явно. Автоматическое восстановление всего сценария после падения процесса и завершение частично записанного отчёта не заявляются.
