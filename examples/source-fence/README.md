# Постоянный запрет записи в источнике

Двадцать первый этап закрепляет остановку исходной базы по свежему частному плану восстановления. Обновлённый Store продолжает читать историю, но блокирует новые изменения и публикацию. Карантин старых снимков сохраняется.

- [Анализ и контракт](../../docs/development/source-fence.md).
- [Фактический отчёт](results/fence-report.md), [машинный отчёт](results/fence-report.json).
- [Предыдущий этап: сверка восстановления](../recovery-reconciliation/README.md).

## Запуск

Python 3.10+ и стандартная библиотека, POSIX-права частных файлов. Из корня существующего checkout:

~~~sh
python3 -m agentwiki source-fence-demo --workspace /tmp/agentwiki-fence-01 --workers 3
~~~

Укажите новый пустой каталог. Сначала выполняются прежние сценарии backup и сверки; их результаты сохраняются рядом с новыми файлами `fence-*`. Базы, credentials, планы и частные контрольные суммы остаются вне публичных результатов.

## Протокол

1. Проверить частный план и существующий источник.
2. Получить `BEGIN IMMEDIATE`, проверить текущего администратора и полный отпечаток SQL.
3. Атомарно сохранить метку остановки и одно событие.
4. Вернуть безопасную квитанцию с локальным ID и поколением источника.
5. При точном повторе вернуть прежнюю квитанцию без нового события.
6. Блокировать последующие записи через Store, включая исторические повторы и публикацию.

Публикация удерживает ту же очередь SQLite writer lock до завершения файловых действий и очистки. Поэтому она либо завершает эффекты до установки запрета, либо отклоняется после него. Изменение политики сериализации увеличивает время удержания writer lock; скорость здесь не измеряется.

## Сохранённый запуск

Обычная команда с тремя Python workers завершилась 20 октября 2026 года в 14:10:32 Europe/Berlin. Сохранены 97 публичных файлов: 78 оснований прежних сценариев и 19 новых файлов. Восемь новых этапов включают четыре CLI-процесса, одно событие seal, точный replay и 18 ожидаемых отказов, из них восемь обычным записывающим операциям Store.

В этом запуске публикация завершилась, а источник затем сохранил запрет: 62 → 63 события при ревизии 2. Новый publish был отклонён без создания каталога. Историческая копия сохранила 52 события и карантин. Перекрытие попыток блокировки не измерялось; точный порядок SQL commit не выводится из времён возврата потоков.

## Отдельные команды

~~~sh
python3 -m agentwiki store-fence seal --help
python3 -m agentwiki store-fence status --help
~~~

`seal` принимает `--workspace`, частный `--plan`, административный `--credential` и `--operation-id`. `status` читает существующий `--workspace`. Существующий запрос с другим входом конфликтует; команды снятия запрета нет.

## Граница результата

Барьер действует для участников, использующих обновлённый Store и одну каноническую базу. Доверенный владелец способен обойти его прямым SQL; старые версии приложения не знают метку. Локальное поколение источника не является глобальным механизмом единственного писателя.

Исторические чтения и квитанции доступны. Уже начатые backup или оценка способны завершить исторические файлы позднее; эти результаты сохраняют карантин или совещательные ограничения. Прежние внешние выпуски не отзываются. Активная замена базы и переоформление полномочий требуют следующего протокола.

Все роли локальные и программируемые. Число workers не означает число независимых моделей или измеренную ёмкость сервиса.
