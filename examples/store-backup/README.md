# Приватный снимок Store и восстановление для просмотра

Девятнадцатый этап сохраняет согласованную копию SQLite вместе с историей операций, аудитами и квитанциями. Сама копия помечается как изолированная: Store открывает её для чтения и блокирует новые изменения и выпуск.

- [Анализ и контракт](../../docs/development/store-backup.md).
- [Фактический отчёт](results/report.md), [структурированный отчёт](results/report.json).
- [Предыдущий этап: восстановление ответов](../review-history-recovery/README.md).

## Запуск

Python 3.10+ и стандартная библиотека, POSIX-права частных файлов. Из корня существующего checkout:

~~~sh
python3 -m agentwiki store-backup-demo --workspace /tmp/agentwiki-store-backup-01 --workers 3
~~~

Укажите новый пустой каталог. Исходная база, backup, восстановленная база и credentials остаются внутри `private/` с закрытыми правами. Публичные JSON и Markdown сохраняются отдельно рядом с ним.

## Последовательность

1. Программируемые авторы и интегратор готовят общий кандидат документа и кода; проверяющие сохраняют решения.
2. Три изменения несвязанного раздела создают историю; один аудит остаётся частично пройденным, одна авторская аренда — незавершённой.
3. Открытый читатель удерживает прежний SQLite-снимок, пока обычные API подтверждают принятие в WAL.
4. SQLite Backup API сохраняет подтверждённое состояние, включая квитанцию принятия.
5. Исходная среда продолжает работу: допуск отзывается, аудит продвигается, автор завершает задание.
6. Восстановленная копия показывает сохранённую квитанцию и прежние состояния допуска, аудита и аренды.
7. Store блокирует новые записи и выпуск из копии. Это действует и при прямом открытии backup-файла или переносе одной базы без sidecars.

Счётчики и точные наблюдения находятся в отчёте. Прикладной сценарий использует обычные API и приватные копии; разрушение базы и авария оборудования не моделируются.

## Сохранённый запуск

Команда с `--workers 3` завершилась 20 октября 2026 года в 13:04:19 Europe/Berlin. Сохранены 57 публичных файлов: девять этапов, шесть решений, один аудит и три checkpoints. Старый читатель оставался на ревизии 1; backup захватил принятую ревизию 2 и 52 события. После продолжения работы источника в нём стало 59 событий, а в восстановленной копии осталось 52.

Квитанция schema 4 и исходные одобрения сохранены. Семь попыток записи в копиях и четыре некорректные операции с bundle получили ожидаемые отказы. Четыре самостоятельных процесса CLI выполнили create, inspect, restore и повторный inspect. Это функциональный пример с тремя Python workers, без измерения максимального числа агентов.

## Отдельные команды

~~~sh
python3 -m agentwiki store-backup create --help
python3 -m agentwiki store-backup inspect --help
python3 -m agentwiki store-backup restore --help
~~~

`create` требует существующий исходный `--workspace`, административный `--credential` и новый `--destination`. Родитель назначения должен уже существовать и иметь частные права. `inspect` принимает `--bundle`. `restore` принимает `--bundle` и новый `--destination`; существующий каталог, включая пустой, не перезаписывается.

SQLite, intent, manifest и контрольные суммы приватны. Bundle содержит хеши допусков и другие исторические служебные данные; сохраняйте его целиком вне публикации. Credential-файлы хранятся отдельно. CLI возвращает только безопасную сводку без частных хешей.

## Что означает восстановление

Это исторический просмотр изолированного снимка. Более поздние отзывы допусков и изменения аренд принадлежат исходной среде. Сохранённые полномочия проверяются относительно копии и текущих часов; они не предоставляют права новых изменений в ней.

Исторические квитанции читаются через `governance_status`, аудиты — через read API. Восстановление не предоставляет API активации старого состояния. Владелец файла SQLite остаётся доверенным и способен обойти ограничения прямой записью в базу.

Все роли локальные и программируемые. Истинность прозы, полнота предметных связей, отказоустойчивость сервиса и максимальная нагрузка данным примером не устанавливаются.
