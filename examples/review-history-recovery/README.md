# Восстановление ответов и каталог аудитов

Восемнадцатый этап прототипа позволяет получить сохранённый результат операции по её известному ID и обнаружить аудиты через ограниченные страницы каталога.

- [Анализ и контракт](../../docs/development/review-history-recovery.md).
- [Фактический отчёт](results/report.md), [структурированный отчёт](results/report.json).
- [Предыдущий этап: пошаговый аудит](../review-history-audit/README.md).

## Запуск

Python 3.10+ и стандартная библиотека. Из корня существующего checkout:

~~~sh
python3 -m agentwiki history-recovery-demo --workspace /tmp/agentwiki-history-recovery-01 --workers 3
~~~

Укажите новый пустой каталог. SQLite и credentials создаются в `private/`; публичные JSON и Markdown сохраняются рядом. Для отдельных CLI-команд `--workspace` указывает на `private/`, содержащий `state.sqlite3`.

## Последовательность

1. Программируемые авторы и интегратор готовят общий кандидат документа и кода.
2. Проверяющие сохраняют одобрения и возражение; три изменения несвязанного D создают историю для аудита.
3. Отдельные процессы CLI выполняют `start` и `advance`; их stdout намеренно отбрасывается после выполнения.
4. Другие процессы `recover` находят прежние результаты по известным operation IDs.
5. Каталог закрепляет состав из трёх аудитов. Более поздний четвёртый аудит появляется при новом обходе.
6. Повтор первой страницы сохраняет ID участников прежнего состава и показывает изменившуюся голову аудита.
7. Явное редакторское решение устраняет возражение; обычное принятие сохраняет исходные одобрения.
8. После нового изменения каталога исторические восстановления возвращают прежние checkpoints и квитанцию.

Отбрасывание stdout моделирует потерю ответа клиента после сохранения результата. Сценарий не моделирует сетевую аварию, отказ диска или восстановление разрушенной базы.

## Сохранённый запуск

20 октября 2026 года выполнены 18 этапов, 15 отдельных процессов CLI и шесть решений проверяющих. Созданы четыре аудита и семь checkpoints. Два ответа CLI были отброшены; четыре вызова recover вернули сохранённые результаты, в том числе после принятия и позднего изменения каталога.

Восемь страниц каталога показали закреплённый состав из трёх аудитов, отдельный новый обход с четвёртым аудитом, изменение головы и сохранность пустого снимка. Двенадцать наблюдений чтения сохранили счётчик событий. Всего записано 59 событий и одно принятие на ревизии 2. Квитанция schema 4 использовала четыре исходных одобрения через три перехода каталога.

- [Исходы процессов CLI](results/cli-outcomes.json) и [восстановленные ответы](results/recoveries.json).
- [Страницы каталога](results/catalogue-pages.json) и [состав закреплённого обхода](results/catalogue-membership.json).

Все 54 файла в `results/` совпадают с публичными файлами этого запуска. Ошибки повреждённых записей рассмотрены статически; повреждение базы и нагрузка в прикладной сценарий не входили.

## Отдельные команды

~~~sh
python3 -m agentwiki history-audit recover --help
python3 -m agentwiki history-audit list --help
~~~

`recover` требует административный `--credential` и известный `--operation`. Полные параметры прежнего запроса восстанавливаются из неизменяемых записей и сверяются с сохранённым digest. Результат содержит прежний checkpoint и наблюдённую текущую голову; новые события или операции не создаются.

`list` публичен в рамках локального Store. Предел `--limit` — от 1 до 20, по умолчанию 10. Для продолжения используйте оба возвращённых поля `next_cursor`: `--after-seq` и `--snapshot-max-seq`. Состав обхода закреплён; состояния голов наблюдаются отдельно на каждой странице. Ошибки отдельных записей выдаются явно.

## Границы

Аудиты, восстановление ответов и каталог имеют совещательный статус. Принятие продолжает проверять текущие полномочия, основания, кворум и возражения. Владелец SQLite и локальные часы доверенные; хеши не являются внешним заверением полноты журнала или личности участника.

Все роли локальные и программируемые. Предложенный код сохраняется как данные. Истинность прозы, полнота объявленных связей, внешние LLM и предельная нагрузка этим сценарием не оцениваются. Публичные результаты хранятся отдельно от credentials, их хешей и частной базы.
